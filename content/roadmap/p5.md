## Scalability fundamentals

### Vertical scaling — bigger machine (more CPU, RAM, faster disk); simple but has hard limits and is expensive
Scale **up**: move to a larger instance. There's no code change, and it's often the right first step, especially for databases. Limits: there's a biggest machine, the price rises steeply at the top end, upgrades usually need downtime, and it's still one machine (a single point of failure).
**In the interview:** "Scale the DB vertically first, then add replicas, then shard." It shows pragmatism.

### Horizontal scaling — more machines; requires stateless design and coordination layer
Scale **out**: add more instances behind a load balancer. Capacity is practically unlimited and losing one node is survivable. It requires stateless services, a load balancer, and distributed data handling (replication, sharding, distributed caching) for the stateful parts.
**In the interview:** app tiers scale horizontally by default. The hard part is the data tier.

### Stateless services — no local state, any instance can serve any request; scale with load balancer
A stateless server keeps nothing between requests in local memory or disk. Sessions go to Redis or JWTs, files to S3, jobs to a queue. Any instance can serve any request, instances can be killed or added freely (autoscaling, rolling deploys), and the load balancer needs no stickiness.
**In the interview:** say "the API tier is stateless" early in every design.

### Stateful services — session affinity or external state store required
Services that hold state (WebSocket gateways, game servers, databases, in-memory caches) need either **affinity** (route a user back to the same instance) or **externalised state**, and deploys and scaling need care (draining connections, rebalancing). Kubernetes StatefulSets give them stable identities and storage.
**In the interview:** isolate stateful pieces and keep everything else stateless.

### Distributed session — store sessions in Redis with TTL, enables stateless web servers
A session ID cookie points to session data in Redis (`session:abc → {userId, roles…}`) with a sliding TTL. Any web server can read it, logout deletes it instantly, and the data can be large and server-side only. It costs a Redis lookup per request, and Redis must be highly available.
**In the interview:** compare it with JWT: revocable and simple, with one more dependency.

### JWT for stateless auth — token carries identity, no server-side session store needed
A signed token (header.payload.signature) carries claims (user ID, roles, expiry). Any service verifies the signature locally with the public key, with no lookup. Revocation is hard, so keep access tokens short-lived (5–15 min) and use refresh tokens. Never put secrets in the payload: it's only base64, readable by anyone.
**In the interview:** "JWT between gateway and services; short expiry plus refresh tokens."

### Twelve-factor app — config in env, statelessness, logs as streams, disposability
A checklist for cloud-native services. Points worth naming: one codebase, explicit dependencies, **config in environment variables**, backing services as attached resources, separate build/release/run stages, **stateless processes**, port binding, scale via processes, **disposability** (fast start, graceful shutdown), dev/prod parity, **logs written to stdout**, and admin tasks run as one-off processes.
**In the interview:** quoting 3–4 of these signals operational maturity.

### Back-of-envelope estimation — QPS, storage, bandwidth, memory: always show arithmetic
Quick, rounded maths to size a system and justify decisions: requests per second, storage per year, bandwidth and cache memory. Round hard (1 day ≈ 10⁵ s), state your assumptions out loud, and finish with what the number means for the design ("so we need a cache / sharding / a CDN").
**In the interview:** 3–5 minutes, right after requirements. See the full lesson for worked examples.

### QPS estimation — DAU × actions_per_day / 86400 seconds
Example: 50M DAU × 20 requests/day ÷ ~10⁵ s ≈ **10,000 QPS** average. **Peak ≈ 2–3×** (×10 for flash sales). Split reads from writes using the read:write ratio. Compare with single-node limits: an app server handles ~1–10K req/s, a Postgres node ~5–20K simple queries/s, a Redis node ~100K ops/s.
**In the interview:** always calculate peak, not just average.

### Storage estimation — rows/day × row_size × retention_days × replication_factor
Example: 10M orders/day × 1 KB × 365 days × 5 years × 3 replicas ≈ **55 TB**. Don't forget indexes (+20–50%), media in object storage (counted separately), and growth. The result decides single node vs sharding, and hot vs cold storage tiers.
**In the interview:** state the conclusion: "55 TB → sharded or a distributed store, with archival to S3 after 1 year."

### Bandwidth estimation — peak_QPS × average_response_size × peak_multiplier (×3–5)
Example: 20K req/s × 100 KB images = **2 GB/s** egress, which no origin should serve directly, so put a CDN in front. Ingress (uploads) is usually far smaller than egress. Cross-AZ and internet egress cost real money, so bandwidth affects cost, not just capacity.
**In the interview:** media-heavy systems (YouTube, Instagram) are dominated by egress, so the CDN is essential.

### Amdahl's Law — serial fraction limits maximum speedup: max = 1 / (S + (1-S)/N)
If 10% of the work is serial (S = 0.1), then even with infinite machines the speedup is capped at 1/0.1 = **10×**. With 16 machines it's about 6.4×. Serial bottlenecks (a single DB lock, a global counter, a coordinator) dominate at scale.
**In the interview:** use it to explain why removing serial chokepoints matters more than adding servers.

### Little's Law — L = λW: avg items in system = arrival rate × avg time in system
The average number of in-flight requests equals throughput × latency. At 1,000 req/s and 200 ms latency, you have **200 concurrent requests**, so you need about 200 threads or connections. If latency doubles to 400 ms, concurrency doubles to 400, which is how slow dependencies exhaust thread and connection pools.
**In the interview:** great for sizing pools and explaining cascading failures.

## Load balancing

### Round robin — equal distribution ignoring server load or capacity
Send each request to the next server in turn. It's simple and stateless, and works well when servers are identical and requests similar in cost. It ignores how busy each server actually is, so long requests can pile up on one server.
**In the interview:** the default. Mention it, then say when you'd pick something smarter.

### Weighted round robin — proportional to server CPU/memory/capacity
Round robin with weights: a server with weight 3 gets three times the requests of one with weight 1. Use it for mixed instance sizes, or **canary releases** (send 5% to the new version), or draining a region gradually.
**In the interview:** the canary use case is the best example.

### Least connections — route to server with fewest active connections (best for variable request duration)
Send the request to the server with the fewest open connections. It adapts to uneven request durations (uploads, reports, WebSockets, slow queries). The weighted variant accounts for capacity. The LB needs to track connection counts.
**In the interview:** "least connections for WebSocket gateways and long-running requests."

### IP hash — same client IP always routes to same server (sticky sessions without cookies)
`hash(client IP) % servers` picks the server, so the same client keeps going to the same backend. It gives stickiness without cookies. Downsides: users behind corporate or mobile NAT all land on one server (uneven), and adding or removing servers reshuffles everyone (consistent hashing helps).
**In the interview:** prefer stateless servers. Use hashing for cache locality, not sessions.

### Random with power of two choices — pick 2 random servers, route to least loaded (better than random)
Pick two servers at random and send the request to the less loaded one. This simple trick dramatically reduces the maximum load compared with pure random choice, needs no global state, and works well in distributed load balancers where each LB instance has only partial information. Used in Envoy, Nginx (`random two`) and HAProxy.
**In the interview:** a nice "I know modern LB algorithms" detail.

### Layer 4 LB — operates on TCP/UDP, fast, no HTTP awareness, no SSL termination
It routes by IP and port only, forwarding TCP or UDP connections without looking inside. It has very high throughput and low latency, works with any protocol (databases, MQTT, gaming, WebSockets passed straight through), and preserves end-to-end TLS. It can't route by URL or header, and can't retry at the HTTP level. Examples: AWS NLB, LVS, HAProxy in TCP mode.
**In the interview:** "NLB for raw TCP or extreme throughput; ALB for HTTP routing."

### Layer 7 LB — operates on HTTP, content-aware routing, SSL termination, rewrites
It terminates the connection and understands HTTP, so it can route by path, host or header (`/api/payments` → payment service), terminate TLS, rewrite and redirect, compress, use cookie stickiness, retry, split traffic for canaries, and act as a WAF. It costs more CPU and per-request latency than L4. Examples: AWS ALB, Nginx, Envoy, Traefik, HAProxy in HTTP mode.
**In the interview:** most microservice architectures sit behind an L7 load balancer or gateway.

### DNS load balancing — multiple A records for same domain, TTL-based, no health checks
Return several IPs for one name (rotating the order). Clients pick one. It's simple and cheap, but there's **no real health awareness** (basic DNS keeps returning dead IPs), resolvers cache for the TTL, and clients pick unevenly. Managed DNS with health checks (Route 53) improves on this.
**In the interview:** good for coarse distribution across regions, with a real LB inside each region.

### GSLB — Global Server Load Balancing, routes users to closest healthy datacenter
GSLB routes users to the best region by geography, latency or health, usually via smart DNS (GeoDNS with health checks) or anycast. If a region fails its checks, traffic shifts to the others. Examples: Route 53 latency/failover routing, Cloudflare Load Balancing, F5 GTM, Akamai GTM.
**In the interview:** the top layer in multi-region active-active designs.

### AWS ALB (L7) vs NLB (L4) vs Classic LB — ALB for HTTP/WebSocket, NLB for ultra-low latency TCP
**ALB**: HTTP/HTTPS/gRPC/WebSocket, path/host/header routing, Lambda and container targets, WAF integration. **NLB**: TCP/UDP/TLS, millions of requests per second, static IPs per AZ, keeps the client source IP, ultra-low latency. **Classic LB**: legacy, avoid it. (Gateway LB is for inline security appliances.)
**In the interview:** "ALB in front of the services; NLB for the TCP-based market-data feed."

### Health checks — active (periodic HTTP probe) vs passive (monitor real traffic error rates)
**Active**: the LB probes `/health` every few seconds, and after N failures it marks the target unhealthy and stops routing to it. **Passive (outlier detection)**: it watches real responses and ejects backends producing errors or timeouts. Keep health endpoints cheap but meaningful (can it reach its DB?), and avoid cascades where every instance fails a check because one shared dependency is down.
**In the interview:** distinguish liveness (restart me) from readiness (don't send me traffic yet).

### Connection draining — grace period to complete in-flight requests before removing instance
When an instance is deregistered (deploy, scale-in), the LB stops sending **new** requests but lets in-flight ones finish within a timeout (30–300 s). The app should handle SIGTERM gracefully: stop accepting new work, finish current work, close connections. For WebSockets, migrate clients gradually.
**In the interview:** part of how you achieve zero-downtime deploys.

### Slow-start mode — gradually ramp up traffic to newly added instances to warm caches
A brand-new instance has cold caches, an un-JITed JVM and empty connection pools. Hitting it with a full share of traffic causes latency spikes. Slow start ramps its traffic up over 30–300 s. Supported by ALB, Envoy and HAProxy.
**In the interview:** especially relevant for JVM services (JIT warm-up).

## Auto-scaling & compute

### Reactive auto-scaling — scale based on current CPU%, memory%, request count, queue depth
Add instances when a metric crosses a threshold (e.g. target 60% CPU). Choose the metric that actually reflects load: CPU for compute-bound services, **request count or latency** for I/O-bound ones, **queue depth or consumer lag** for workers. It lags behind sudden spikes (instance boot + warm-up), so keep headroom.
**In the interview:** "target tracking at ~60% CPU, plus queue-depth scaling for workers."

### Predictive auto-scaling — pre-scale based on historical patterns (Black Friday, match kicks off)
Scale **before** the load arrives, based on forecasts from historical patterns or known events: an IPL match start, a Big Billion Days sale, salary day, 9:15 AM market open. AWS has predictive scaling and scheduled actions. Combine it with reactive scaling as a safety net.
**In the interview:** essential for spiky, predictable events where boot time would be too slow.

### AWS Auto Scaling Groups — min/desired/max, scale-out fast, scale-in slow (cooldown)
An ASG maintains the desired number of EC2 instances within min and max bounds, replaces unhealthy ones, and spreads across AZs. Scaling policies (target tracking, step, scheduled, predictive) adjust the desired count. Scale out aggressively and scale in conservatively, with cooldowns and warm-up periods, to avoid flapping.
**In the interview:** "ASG across 3 AZs, min 3 for HA."

### Kubernetes HPA — Horizontal Pod Autoscaler based on CPU/memory or custom metrics
The HPA adjusts a Deployment's replica count to hit a target metric, such as 70% CPU of the *requests*, or custom metrics (requests per second, latency) via Prometheus Adapter. It reacts within about 15–30 s, with stabilisation windows to avoid flapping. Pods still need nodes, so pair it with the Cluster Autoscaler or Karpenter.
**In the interview:** "HPA on RPS with Cluster Autoscaler for nodes."

### Kubernetes VPA — Vertical Pod Autoscaler: right-sizes CPU/memory requests automatically
VPA watches actual usage and recommends (or applies) better CPU and memory **requests and limits**, restarting pods to apply changes. It fixes chronically over- or under-provisioned pods. Don't combine it with an HPA that scales on the same CPU or memory metric.
**In the interview:** niche. "VPA in recommendation mode to right-size requests."

### KEDA — Kubernetes Event-Driven Autoscaling: scale on Kafka lag, SQS queue depth, etc.
KEDA scales workloads on external event sources: Kafka consumer lag, SQS/RabbitMQ queue length, Redis lists, Prometheus queries, cron. It can **scale to zero** when idle and back up when messages arrive. That's ideal for queue workers, where CPU is a poor signal.
**In the interview:** "consumers scale on Kafka lag via KEDA, capped at the partition count."

### Spot / preemptible instances — 70–90% cheaper with 2-min interruption notice; use for stateless batch
Spare cloud capacity sold cheaply, which can be reclaimed with about 2 minutes' notice on AWS (30 s on GCP). Good for stateless, fault-tolerant work: batch jobs, CI, rendering, queue workers, part of a stateless web fleet. Diversify instance types, checkpoint work, and handle the termination notice.
**In the interview:** a cost-optimisation point. Never run the database primary on spot.

### Serverless auto-scaling — Lambda scales to thousands of concurrent executions automatically
Each request or event gets its own execution environment, and the platform scales concurrency automatically (with account limits and burst rates). There's no capacity planning, and you pay per invocation and per millisecond. Watch for cold starts, the 15-minute max duration, DB connection storms (use RDS Proxy) and downstream systems that can't scale as fast.
**In the interview:** good for spiky event processing such as S3 triggers, webhooks and cron jobs.

### Scale-to-zero — Lambda, Cloud Run: no instances running when no traffic (cold start tradeoff)
When idle, nothing runs and you pay nothing. The first request after idle pays a **cold start**: hundreds of milliseconds to seconds, especially for JVM apps. Mitigate with provisioned concurrency or min-instances, lighter runtimes, or SnapStart (Java on Lambda).
**In the interview:** great for internal tools and low-traffic APIs. Avoid it on latency-critical paths.

## Containers & Kubernetes

### Docker — image layers, Dockerfile best practices (multi-stage build, minimal base image)
An **image** is a stack of read-only layers, and a **container** is a running instance of it. Best practices: **multi-stage builds** (compile in a JDK image, run in a slim JRE or distroless image), minimal base images (smaller and fewer CVEs), order layers so dependencies are cached before code, run as non-root, one process per container, and use `.dockerignore`.
**In the interview:** basic hygiene: small, secure, reproducible images.

### Container vs VM — process isolation vs full OS, millisecond vs second startup time
**VMs** virtualise hardware, and each runs a full guest OS. Isolation is strong, but they're heavy (GBs) and boot in tens of seconds. **Containers** share the host kernel and isolate processes with namespaces and cgroups. They're light (MBs), start in milliseconds and pack densely, with weaker isolation. Sandboxed runtimes (gVisor, Firecracker microVMs) sit in between.
**In the interview:** "containers on Kubernetes for services; VMs underneath as nodes."

### Kubernetes control plane — API server (gateway), scheduler (pod placement), controller manager, etcd (cluster state)
The **API server** is the front door: everything (kubectl, controllers) talks to it. **etcd** stores all cluster state in a strongly consistent, Raft-replicated store. The **scheduler** picks a node for each new pod based on resources, affinity and taints. The **controller manager** runs reconciliation loops (Deployments, ReplicaSets, nodes) that drive actual state toward desired state.
**In the interview:** "declarative desired state + reconciliation loops" is the core idea.

### Kubernetes worker nodes — kubelet (runs pods), kube-proxy (network rules), container runtime (containerd)
Each node runs the **kubelet** (an agent that starts and stops pods as instructed and reports health), **kube-proxy** (programs iptables/IPVS rules so Service IPs route to pods; eBPF CNIs like Cilium can replace it) and a **container runtime** (containerd, CRI-O). A CNI plugin provides pod networking.
**In the interview:** rarely asked deeply at SDE-2. Know the names and roles.

### Pod, Deployment, Service (ClusterIP/NodePort/LoadBalancer), Ingress, ConfigMap, Secret, PVC
**Pod**: one or more containers sharing a network namespace. **Deployment**: manages replicas and rolling updates. **Service**: a stable virtual IP or DNS name, either ClusterIP (internal), NodePort (a port on every node) or LoadBalancer (a cloud LB). **Ingress**: L7 HTTP routing into Services. **ConfigMap/Secret**: configuration and credentials. **PVC**: a claim on persistent storage.
**In the interview:** enough vocabulary to describe how your service runs.

### Rolling update — replace pods gradually; rollback on failure
A Deployment replaces old pods with new ones a few at a time (`maxSurge`, `maxUnavailable`), waiting for **readiness probes** before continuing. If new pods fail, the rollout stalls, and `kubectl rollout undo` reverts. Old and new versions run side by side during the rollout, so APIs and schemas must be backward compatible.
**In the interview:** the default deploy strategy. Mention compatibility.

### StatefulSet — stable network identity, ordered deployment (Kafka, Cassandra, databases)
Pods get stable names (`kafka-0`, `kafka-1`), stable DNS, and their own persistent volumes that follow them across rescheduling. They're created, scaled and updated in order. Use it for clustered stateful systems. Operators (Strimzi for Kafka, CloudNativePG) automate the hard parts.
**In the interview:** "possible, but managed services are often simpler for production databases."

### DaemonSet — one pod per node (log collectors, node-level monitoring, Istio sidecar)
A DaemonSet guarantees one copy of a pod on every (selected) node, and new nodes get it automatically. Use it for node-level agents: log shippers (Fluent Bit), metrics exporters (node-exporter), security agents and CNI components. (Istio sidecars are injected per pod. Ambient mode uses per-node proxies.)
**In the interview:** know it's how observability agents get onto every node.

### Kubernetes resource requests vs limits — request = scheduling guarantee, limit = throttle ceiling
**Requests** are what the scheduler reserves: the pod is guaranteed that much and is placed on a node with room for it. **Limits** are the ceiling: exceeding the CPU limit means **throttling**, and exceeding the memory limit means the container is **OOM-killed**. Set requests from real usage. Setting memory limit = request is a common safe pattern, and many teams avoid CPU limits for latency-sensitive services.
**In the interview:** throttling and OOM kills are frequent causes of production latency and restarts.

### Node affinity, taints and tolerations — control which pods run on which nodes
**Node affinity** says "schedule me on nodes with label X" (GPU nodes, a specific AZ). **Pod affinity/anti-affinity** co-locates pods or spreads them apart (replicas across zones). **Taints** repel pods from a node unless they have a matching **toleration**, which reserves nodes for special workloads (spot nodes, GPU, system pods).
**In the interview:** "anti-affinity spreads replicas across AZs for HA."

### Service mesh (Istio/Linkerd) — sidecar Envoy proxy, mTLS between services, traffic management, observability
A proxy next to each service (an Envoy sidecar, or node-level proxies in ambient mode) intercepts all traffic and adds automatic **mTLS**, retries, timeouts, circuit breaking, traffic splitting (canaries), and uniform metrics and traces, with no library code. The costs are operational complexity and some latency and resource overhead.
**In the interview:** "a mesh for mTLS and consistent resilience policies across polyglot services."

### Helm — Kubernetes package manager, templated manifests, release management
**Charts** are templated Kubernetes manifests plus default values. Install them with environment-specific values files, upgrade them, and roll back releases. Public charts exist for Kafka, Redis, Prometheus and more. Alternatives: Kustomize (overlays without templates), and GitOps tools (Argo CD, Flux) that deploy charts from Git.
**In the interview:** one line: "Helm charts deployed via Argo CD."
