## Network models & core protocols

### OSI model — 7 layers and each layer's responsibility
A reference model that splits networking into 7 layers, each serving the one above: **1 Physical** (bits on a wire or radio), **2 Data link** (frames, MAC addresses, switches), **3 Network** (IP addressing and routing), **4 Transport** (TCP/UDP, ports, reliability), **5 Session** (opening and closing conversations), **6 Presentation** (encoding, encryption, compression), **7 Application** (HTTP, DNS, SMTP). Real stacks merge 5–7, but the numbers stick as vocabulary: an "L4 load balancer" routes on IP and port, and an "L7 load balancer" reads HTTP.
**In the interview:** use the layer numbers when you talk about load balancers, firewalls (L3/L4 vs WAF at L7) and where TLS sits.

### TCP/IP model — 4 layers and mapping to OSI
The model the internet actually uses: **Link** (OSI 1–2), **Internet** (OSI 3: IP), **Transport** (OSI 4: TCP/UDP), **Application** (OSI 5–7: HTTP, DNS, TLS, gRPC). Each layer wraps the one above in its own header (encapsulation): an HTTP request goes inside a TCP segment, inside an IP packet, inside an Ethernet frame.
**In the interview:** knowing that HTTP rides on TCP, which rides on IP, lets you explain why HTTP/3 moved to UDP (QUIC) to escape TCP's limits.

### IP addressing — IPv4, IPv6, CIDR, subnetting, NAT
**IPv4** addresses are 32-bit (about 4.3 billion, now exhausted). **IPv6** addresses are 128-bit and effectively unlimited. **CIDR** notation (`10.0.0.0/16`) means the first 16 bits are the network, which gives 65,536 addresses. **Subnetting** splits a network into smaller ranges (in a cloud VPC: public subnets for load balancers, private subnets for app servers and databases). **NAT** lets many private IPs (10.x, 192.168.x) share one public IP, so outbound traffic is translated and inbound traffic needs explicit rules.
**In the interview:** "Databases sit in private subnets with no public IP, reachable only from the app tier" is a standard security line.

### TCP — 3-way handshake (SYN → SYN-ACK → ACK)
Before any data flows, the client sends **SYN** (with its starting sequence number), the server replies **SYN-ACK** (its own sequence number plus an acknowledgement), and the client sends **ACK**. That costs **1 round trip** before the first byte of the request. Across continents that's 150+ ms.
**In the interview:** this cost is why we reuse connections (keep-alive, HTTP/2, connection pools such as HikariCP) and put servers near users (CDN, multi-region).

### TCP — 4-way teardown (FIN → FIN-ACK → FIN → ACK)
Each side closes its direction independently: A sends FIN, B ACKs it, B sends its own FIN, and A ACKs that. The side that closed first sits in **TIME_WAIT** (typically 60 s) so delayed packets aren't mistaken for a new connection. A busy server or proxy opening many short connections can run out of ports because of TIME_WAIT sockets.
**In the interview:** another reason to pool connections, and why load balancers keep long-lived connections to backends.

### TCP flow control — sliding window protocol
The receiver advertises a **window**: how many bytes it can buffer right now. The sender may have only that many unacknowledged bytes in flight, and the window slides forward as ACKs arrive. This stops a fast sender from overwhelming a slow receiver. Throughput ≈ window ÷ RTT, so long-distance links need big windows (window scaling).
**In the interview:** it explains why a single TCP connection across the globe is slower than one inside a datacenter, even with plenty of bandwidth.

### TCP congestion control — slow start, AIMD, CUBIC
Flow control protects the *receiver*; congestion control protects the *network*. **Slow start**: a new connection begins with a small congestion window and doubles it every RTT. **AIMD**: after that, it grows the window linearly and **halves it on packet loss**. **CUBIC** (the Linux default) grows faster on high-bandwidth links, and **BBR** (Google) models bandwidth and RTT instead of reacting to loss.
**In the interview:** slow start is why new connections are slow at first, which is one more argument for reusing warm connections.

### UDP — connectionless, no ordering, no guarantee, use cases
UDP just sends datagrams: no handshake, no retransmission, no ordering, and an 8-byte header. It's fast and simple. The app handles loss if it cares. Use it where **fresh beats complete**: live video and voice (WebRTC), online games, DNS lookups, metrics (StatsD), and QUIC/HTTP/3, which builds its own reliability on top of UDP.
**In the interview:** never pick UDP for anything that must not be lost, like chat messages or payments.

### DNS resolution — recursive vs iterative, root → TLD → authoritative
Your machine asks a **recursive resolver** (from your ISP, or 8.8.8.8 / 1.1.1.1) to "find api.example.com for me". The resolver does the legwork **iteratively**: it asks a **root** server ("ask the .com servers"), then the **.com TLD** server ("ask example.com's nameservers"), then the **authoritative** nameserver, which returns the IP. Every answer is cached at each level for its TTL, so most lookups are a single hop.
**In the interview:** DNS is the first hop of every request, and a common place for global load balancing (GeoDNS) and failover.

### DNS record types — A, AAAA, CNAME, MX, TXT, NS, PTR, SOA
**A**: name → IPv4. **AAAA**: name → IPv6. **CNAME**: an alias to another name (`www → myapp.cdn.net`). **MX**: mail servers for the domain. **TXT**: free text, used for SPF/DKIM email verification and domain-ownership proofs. **NS**: which nameservers are authoritative for the zone. **PTR**: reverse lookup, IP → name. **SOA**: zone metadata (primary server, serial number, default TTLs).
**In the interview:** CDNs and managed load balancers are usually wired in with CNAME records.

### DNS TTL — caching behavior, propagation delay
Each record carries a TTL telling resolvers how long to cache it. A **low TTL** (30–60 s) means changes and failovers take effect quickly, at the cost of more DNS queries. A **high TTL** (hours) means fewer queries, but a change can take hours to reach everyone ("propagation delay"), and some resolvers ignore TTLs anyway.
**In the interview:** before a planned migration, lower the TTL a day ahead. For DNS-based failover, keep TTLs short.

### Latency sources — propagation, transmission, queuing, processing
Total latency is the sum of four things. **Propagation**: distance ÷ speed of light in fibre, about 5 ms per 1,000 km one way, which no amount of engineering removes. **Transmission**: packet size ÷ link bandwidth. **Queuing**: waiting in router or server buffers, which explodes near saturation. **Processing**: CPU work in routers and in your application.
**In the interview:** distance gets fixed with CDNs and regions, queuing with capacity and load shedding, processing with caching and better code.

### Bandwidth vs throughput — why they differ in practice
**Bandwidth** is the pipe's maximum capacity (1 Gbps). **Throughput** is what you actually achieve, which is always less, because of TCP windows and slow start, packet loss and retransmissions, protocol overhead, congestion, and the slowest link on the path. **Latency** is a separate measure: how long one bit takes to arrive.
**In the interview:** a high-bandwidth, high-latency link can still give poor throughput per connection. Parallel connections or larger windows help.

### RTT (Round Trip Time) and its compounding effect on performance
RTT is the time for a request to reach the server and the reply to come back (Mumbai ↔ Virginia ≈ 200 ms). It **compounds**: a new HTTPS connection costs DNS + TCP (1 RTT) + TLS (1 RTT) + the request (1 RTT), so about 600 ms before any work happens. A page making 5 *sequential* API calls pays 5 RTTs on top of that.
**In the interview:** cut round trips by batching APIs, running calls in parallel, reusing connections, using TLS 1.3 / 0-RTT, and moving data closer to users (edge, CDN).

## HTTP versions & HTTPS

### HTTP/1.0 — new connection per request
Every request opened a fresh TCP connection and closed it after the response, so each image or script paid a full handshake. That was very slow for pages with dozens of resources. It's of historical interest only now.
**In the interview:** it's the starting point of the HTTP story: 1.0 (a new connection each time), then 1.1 (reuse), then 2 (multiplex), then 3 (QUIC).

### HTTP/1.1 — persistent connections, pipelining, keep-alive, Head-of-Line blocking
**Keep-alive** reuses one TCP connection for many requests. **Pipelining** let a client send several requests without waiting, but responses had to come back **in order**, so one slow response blocked all the others behind it (**head-of-line blocking**). Browsers disabled pipelining and instead opened about 6 parallel connections per host, which led to hacks like domain sharding and sprite sheets.
**In the interview:** HoL blocking is the problem HTTP/2 was designed to solve.

### HTTP/2 — multiplexing streams, header compression (HPACK), server push, binary framing
HTTP/2 uses one TCP connection carrying many **interleaved streams**, so responses no longer wait for each other at the HTTP level. Messages are split into **binary frames**, which are faster to parse than text. **HPACK** compresses repeated headers such as cookies and user agents. **Server push** (sending resources before they're asked for) proved hard to use well and is now mostly abandoned. One limit remains: a lost TCP packet still stalls **every** stream.
**In the interview:** gRPC runs on HTTP/2, which is how it gets multiplexing and streaming.

### HTTP/3 — QUIC over UDP, 0-RTT connection, built-in TLS 1.3, no TCP HoL blocking
HTTP/3 replaces TCP with **QUIC**, a reliable transport built on UDP. Loss in one stream doesn't block the others. Transport and TLS 1.3 handshakes are combined into 1 RTT, and returning clients can send data with **0-RTT**. Connections survive network changes (Wi-Fi to 4G) because they're identified by a connection ID rather than by IP and port. It's widely supported by CDNs and browsers, with a fallback to HTTP/2 when UDP is blocked.
**In the interview:** say it helps mobile users on lossy networks most.

### HTTPS — TLS handshake flow: ClientHello → ServerHello → Certificate → Key Exchange → Finished
1) **ClientHello**: the TLS versions and cipher suites the client supports, plus a random value and, in TLS 1.3, a key share. 2) **ServerHello**: the chosen cipher and the server's key share. 3) **Certificate**: the server proves its identity with a CA-signed certificate. 4) **Key exchange**: both sides derive the same symmetric session key using (EC)Diffie-Hellman. 5) **Finished**: each side confirms that the handshake wasn't tampered with. After that, everything is encrypted with fast symmetric crypto (AES-GCM / ChaCha20).
**In the interview:** TLS gives encryption, integrity and server identity. The handshake costs 1 RTT with TLS 1.3.

### TLS 1.2 vs TLS 1.3 — fewer round trips, no RSA key exchange (forward secrecy)
TLS 1.3 cuts the full handshake from **2 RTTs to 1** and supports 0-RTT resumption. It **removes RSA key exchange** and weak ciphers, so every connection uses ephemeral Diffie-Hellman. That gives **forward secrecy**: if the server's private key leaks later, recorded past traffic still can't be decrypted. More of the handshake is encrypted too.
**In the interview:** "TLS 1.3 everywhere" is a cheap way to improve both latency and security.

### Mutual TLS (mTLS) — both client and server authenticate with certificates
In normal TLS only the server shows a certificate. With **mTLS the client presents one too**, and the server verifies it against a trusted CA. It's used for **service-to-service** authentication inside a zero-trust network (often handled automatically by a service mesh such as Istio or Linkerd) and for **bank and partner APIs** (card networks, payment gateways). Certificate issuance and rotation must be automated.
**In the interview:** it's the standard answer to "how do internal services know who's calling them?"

### Certificate chains — root CA → intermediate CA → leaf certificate
Browsers and OSes ship with trusted **root CA** certificates. Roots sign **intermediate CAs** (and the root keys are kept offline), and intermediates sign your **leaf certificate** for `api.example.com`. The server sends leaf + intermediates, and the client walks the chain up to a root it trusts while checking expiry, hostname and revocation. A missing intermediate is a classic cause of "works in Chrome, fails in curl or Java".
**In the interview:** mention automated renewal (Let's Encrypt, ACM). Expired certificates cause real outages.

### HTTP methods — GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS and idempotency of each
**GET**: read (safe and idempotent). **HEAD**: GET without the body (safe and idempotent). **OPTIONS**: which methods are allowed, used by CORS preflight (safe). **PUT**: replace the whole resource (idempotent). **DELETE**: remove it (idempotent; deleting twice leaves the same state). **POST**: create, or a non-idempotent action. **PATCH**: partial update (not guaranteed idempotent, e.g. "increment by 1"). *Idempotent* means repeating the call has the same effect as making it once.
**In the interview:** clients and proxies may retry idempotent calls automatically. POST needs idempotency keys.

### HTTP status codes — 200, 201, 204, 301, 302, 304, 400, 401, 403, 404, 409, 422, 429, 500, 502, 503, 504
**2xx success**: 200 OK, 201 Created (with a Location header), 204 No Content. **3xx redirect**: 301 permanent (browsers cache it), 302 temporary, 304 Not Modified (use your cached copy). **4xx client error**: 400 bad request, **401 not authenticated**, **403 authenticated but not allowed**, 404 not found, 409 conflict (version clash, duplicate), 422 validation failed, 429 rate limited (send Retry-After). **5xx server error**: 500 bug, 502 bad gateway (the upstream returned garbage), 503 unavailable or overloaded, 504 gateway timeout (the upstream was too slow).
**In the interview:** use them precisely in your API design. 401 vs 403 and 502 vs 504 are common follow-ups.

### HTTP caching headers — Cache-Control, ETag, Last-Modified, If-None-Match, Vary
**Cache-Control** sets the policy: `max-age=3600`, `public`/`private`, `no-cache` (revalidate before use), `no-store` (never cache), `immutable`. **ETag** is a version fingerprint of the response. The client sends it back in **If-None-Match**, and the server answers **304** with no body if nothing changed. **Last-Modified** / If-Modified-Since does the same with a timestamp. **Vary** says which request headers change the response (e.g. `Accept-Encoding`), so caches store separate copies.
**In the interview:** versioned static files get a long `max-age` + `immutable`. APIs get short TTLs or ETags.

### CORS — same-origin policy, preflight OPTIONS, Access-Control-Allow-* headers
Browsers block JavaScript from reading responses from a different origin (scheme + host + port) unless that server allows it. For "non-simple" requests (custom headers, PUT/DELETE, JSON content type), the browser first sends a **preflight OPTIONS** request. The server must reply with `Access-Control-Allow-Origin`, `-Methods`, `-Headers` (and `-Credentials` if cookies are involved). CORS is a browser rule only: curl and servers ignore it.
**In the interview:** CORS is configured at the API gateway, and it doesn't replace authentication.

### Cookies — HttpOnly, Secure, SameSite (Strict/Lax/None), session vs persistent
**HttpOnly**: JavaScript can't read the cookie, which protects session tokens from XSS. **Secure**: only sent over HTTPS. **SameSite=Strict**: never sent on cross-site requests. **Lax** (the default): sent on top-level navigations but not on cross-site POSTs, which is a good CSRF defence. **None** requires Secure and is needed for legitimate cross-site use. **Session cookies** disappear when the browser closes; **persistent** ones have Expires/Max-Age.
**In the interview:** "session ID in an HttpOnly, Secure, SameSite=Lax cookie" is the safe default for web login.

### Content negotiation — Accept, Content-Type, Accept-Encoding
The client says what it can handle: **Accept** (`application/json`), **Accept-Encoding** (`gzip, br`) and **Accept-Language**. The server picks a format and labels it with **Content-Type** and **Content-Encoding**. Compression with gzip or Brotli typically shrinks JSON and HTML by 70–90%. Remember to add `Vary: Accept-Encoding` so caches keep separate copies.
**In the interview:** compression at the gateway or CDN is an easy bandwidth and latency win.

## APIs & real-time communication

### REST — 6 constraints: stateless, uniform interface, cacheable, layered, client-server, code on demand
REST is an architectural style with six constraints. **Client-server**: separated concerns. **Stateless**: each request carries everything needed, with no server-side session memory, which makes horizontal scaling easy. **Cacheable**: responses say whether they can be cached. **Uniform interface**: resources identified by URLs and manipulated with standard methods. **Layered system**: proxies, gateways and CDNs can sit in between transparently. **Code on demand** (optional): the server can send executable code.
**In the interview:** statelessness is the property that matters most, because it's what makes app servers horizontally scalable.

### REST idempotency — GET/PUT/DELETE idempotent, POST not; why it matters for retries
Networks fail after the server has acted but before the client hears back. If the operation is idempotent (GET, PUT, DELETE), the client can simply retry. If it's a **POST** (create order, charge card), a blind retry can **duplicate** the effect. The fixes are idempotency keys, client-generated IDs, or designing the endpoint as a PUT to a known ID.
**In the interview:** always say which endpoints are safe to retry and how you protect the rest.

### GraphQL — schema, queries, mutations, subscriptions, N+1 problem, DataLoader batching solution
A typed **schema** describes the data graph. Clients send **queries** asking for exactly the fields they need (no over- or under-fetching), **mutations** for writes, and **subscriptions** for real-time updates (usually over WebSockets). It all goes to one endpoint. The classic trap is the **N+1 problem**: fetching 50 posts and then each post's author issues 1 + 50 DB queries. **DataLoader** collects the IDs within one tick and runs a single batched `WHERE id IN (...)` query.
**In the interview:** good for many different clients (mobile, web, partners). Watch caching, query-complexity limits and N+1.

### gRPC — Protocol Buffers, unary/server-streaming/client-streaming/bidirectional streaming
gRPC is Google's RPC framework. You define services in a **.proto** file, messages are **Protocol Buffers** (compact binary with strict types), and client and server code is generated in many languages. It runs on HTTP/2. There are four call types: **unary** (one request, one response), **server streaming** (e.g. a price feed), **client streaming** (e.g. uploading telemetry) and **bidirectional streaming** (e.g. chat). Deadlines and cancellation propagate across services.
**In the interview:** it's the default choice for internal microservice calls that need low latency.

### gRPC vs REST — binary vs text, schema contract, streaming, use cases for each
**gRPC**: binary protobuf (smaller, faster to parse), a strict schema with generated clients, built-in streaming and HTTP/2. It's harder to debug and browsers need gRPC-Web. **REST/JSON**: human-readable, works everywhere (curl, browsers), easy HTTP caching, looser contracts (often OpenAPI). Use **REST for public and browser APIs** and **gRPC for internal service-to-service calls**.
**In the interview:** "REST at the edge, gRPC inside" is a common and well-received answer.

### WebSockets — full-duplex, ws:// upgrade from HTTP, heartbeat ping-pong, reconnection
A WebSocket starts as an HTTP request with `Upgrade: websocket`. The server replies **101 Switching Protocols**, and the same TCP connection then carries messages both ways at any time with tiny overhead. Use **ping/pong heartbeats** every 20–30 s to detect dead connections (mobile networks drop silently). Clients must **reconnect with exponential backoff** and resume from the last message ID. Connections are stateful, so you need a registry plus pub/sub to route messages between servers.
**In the interview:** use it for chat, live collaboration, multiplayer and trading screens.

### Server-Sent Events (SSE) — one-way server push over HTTP, auto-reconnect, use cases
SSE is a long-lived HTTP response with `Content-Type: text/event-stream` where the server keeps writing events. The browser's `EventSource` reconnects automatically and sends `Last-Event-ID` so it can resume. It's **one-way** (server → client), plain HTTP (proxy- and CDN-friendly) and simpler than WebSockets.
**In the interview:** pick it for notifications, live scores, dashboards, job progress and streaming LLM tokens, i.e. whenever the client doesn't need to send a stream back.

### Long polling — client holds connection until server has data, fallback for older clients
The client sends a request, and the server **holds it open** until there's new data or a timeout (~30 s), then responds. The client immediately sends the next request. That gives near-real-time updates over plain HTTP. The costs are an open connection per waiting client and a burst of reconnects after every message. It was the default before WebSockets and SSE, and is still a fallback.
**In the interview:** mention it as the fallback, or for low-frequency updates where WebSockets are overkill.

### Webhooks — event-driven callbacks, retry policy, HMAC signature verification
Instead of clients polling you, **you POST to their URL** when an event happens: Stripe/Razorpay sending `payment.succeeded`, GitHub sending `push`. Retry with exponential backoff (for hours or days) and send failures to a DLQ. Sign each payload with an **HMAC** using a shared secret and include a timestamp, so receivers can verify it's genuine and reject replays. Receivers must respond fast (queue the work) and be **idempotent**, because retries will deliver duplicates.
**In the interview:** used in every payment design, both for receiving PSP results and for notifying merchants.

### API versioning strategies — URL path (/v1/), query param, header, content negotiation
**URL path** (`/v1/orders`) is explicit, easy to route and cache, and the most common. **Query parameter** (`?version=2`) is easy but messy. **Custom header** (`API-Version: 2`) keeps URLs clean but is harder to test in a browser. **Content negotiation** (`Accept: application/vnd.acme.v2+json`) is the most "RESTful" and the least convenient. Whatever you choose, make additive changes without a version bump and keep old versions running during a deprecation window.
**In the interview:** "URL versioning, backward-compatible additions within a version" is a safe answer.

### Idempotency keys — safe retries for payments and mutations
The client generates a unique key (a UUID) per logical operation and sends it as an `Idempotency-Key` header. The server stores `key → result` under a **unique constraint**, ideally in the same transaction as the business write. A retry with the same key returns the **stored response** instead of executing again. An in-progress duplicate gets 409. Keys expire after about 24 h. Stripe, Razorpay and most payment APIs work this way.
**In the interview:** it's the core of every "how do you avoid charging twice?" answer.

### WebRTC — peer-to-peer video/audio, STUN (IP discovery), TURN (relay), ICE negotiation
WebRTC is a browser API for **peer-to-peer** real-time audio, video and data, usually over UDP. Peers first exchange connection offers through your **signalling server** (often a WebSocket). **STUN** servers tell each peer its public IP and port behind NAT. When a direct connection is impossible (strict NAT or firewalls), traffic is relayed through a **TURN** server, which is expensive bandwidth. **ICE** tries every candidate path and picks the best one. Group calls typically use an **SFU** that forwards streams instead of a full mesh.
**In the interview:** relevant for video-calling designs. Name STUN, TURN, signalling and SFU.

## Proxies, CDN & gateways

### Forward proxy — client-side, hides client identity, corporate firewalls
A forward proxy sits **in front of clients**: their outbound requests go through it to the internet. Uses include corporate filtering and logging, caching, bypassing geo-restrictions, and hiding client IPs (VPNs work on a similar idea). The destination server sees the proxy, not the user.
**In the interview:** contrast it with a reverse proxy. That one sentence is usually all that's asked.

### Reverse proxy — server-side, hides server topology (Nginx, HAProxy)
A reverse proxy sits **in front of servers**. Clients talk to it and it forwards requests to backends they never see. It handles **TLS termination**, **load balancing**, compression, caching, rate limiting, request buffering (protecting slow backends from slow clients) and a single public entry point. Examples: Nginx, HAProxy, Envoy, Traefik, AWS ALB.
**In the interview:** almost every design has one. Name it as the first box after DNS.

### API gateway — routing, auth enforcement, rate limiting, request aggregation, protocol translation
An API gateway is a reverse proxy specialised for APIs and the single entry point to your microservices. It does **routing** (`/payments/*` → payment service), **authentication** (validating JWT/OAuth once at the edge), **rate limiting and quotas**, **request aggregation** (one client call fanning out to several services), **protocol translation** (REST outside, gRPC inside), and logging and metrics. Examples: Kong, Apigee, AWS API Gateway, Spring Cloud Gateway.
**In the interview:** keep business logic out of it and run several instances so it isn't a single point of failure.

### CDN — PoPs (Points of Presence), edge nodes, origin server, pull vs push model
A CDN is a global network of cache servers (**edge nodes**) grouped in **PoPs** in hundreds of cities. Users hit the nearest PoP. On a miss, the edge fetches from your **origin** (S3 or your servers) and caches the result. **Pull CDN**: content is fetched lazily on first request (most common). **Push CDN**: you upload content in advance (big launches, large files). The benefits are lower latency, less load on the origin, cheaper bandwidth, and DDoS absorption.
**In the interview:** any design serving images, video or static assets must have a CDN.

### CDN cache invalidation — TTL expiry, immediate purge, cache-busting via URL versioning
There are three ways to update cached content. **TTL expiry**: wait for `max-age` to run out (simple, but stale until then). **Purge / invalidation API**: tell the CDN to drop specific paths now (it can take seconds to minutes, and providers may limit or charge for it). **Cache-busting**: put a version or hash in the URL (`app.3f9a2c.js`, `logo.png?v=7`), so a new version is simply a new object. That's instant and reliable.
**In the interview:** "hashed filenames with a 1-year TTL; HTML with a short TTL" is the standard answer.

### CDN for dynamic content — ESI (Edge Side Includes), Lambda@Edge, Cloudflare Workers
CDNs can do more than static files. **ESI** assembles a page from cached fragments plus small dynamic parts. **Edge compute** (Cloudflare Workers, Lambda@Edge, Fastly Compute) runs your code in the PoP: auth checks, A/B routing, personalisation, header rewriting, even whole APIs with edge KV stores. Even uncacheable requests benefit from the CDN's optimised backbone and TLS termination close to the user.
**In the interview:** useful for global low-latency reads such as URL-shortener redirects or geo-based routing.

### GeoDNS — route users to nearest datacenter based on client IP
A GeoDNS service (Route 53 latency/geo routing, Cloudflare, NS1) returns **different IPs depending on where the resolver is located**: Indian users get the Mumbai region, European users get Frankfurt. Combined with health checks, it removes an unhealthy region from answers. Its limits are DNS caching (TTL) and the fact that it locates the resolver, not the user.
**In the interview:** the usual first step for multi-region active-active designs.

### Anycast routing — same IP announced from multiple locations, routed to nearest
With anycast, the **same IP address is advertised via BGP from many locations**, and internet routing naturally delivers each packet to the topologically nearest one. It's how public DNS (8.8.8.8, 1.1.1.1) and CDNs like Cloudflare work. Failover is automatic (withdraw the route), and DDoS traffic is spread across all sites. It suits UDP and short TCP connections best.
**In the interview:** contrast it with GeoDNS: anycast works at the network layer with no DNS caching delay.
