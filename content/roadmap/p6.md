## Core theorems & consistency models

### CAP theorem — Consistency, Availability, Partition Tolerance: only 2 guaranteed when partition occurs
When a network **partition** splits replicas, a system must choose: stay **consistent** (refuse or stall requests it can't answer correctly) or stay **available** (answer from local, possibly stale data). Partitions are unavoidable in distributed systems, so it's really CP vs AP, chosen per operation. "Consistency" here means linearizability, not ACID consistency.
**In the interview:** don't just recite CAP. Pick C or A **per feature** and justify it.

### CP systems — prioritize consistency over availability during partition (ZooKeeper, HBase, etcd)
During a partition, the minority side refuses writes (and often reads) so nobody sees conflicting data. Examples: ZooKeeper, etcd and Consul (majority quorum), HBase, Spanner, and MongoDB with majority writes. Use CP for coordination, leader election, locks, balances, inventory and unique constraints.
**In the interview:** "payments and seat booking are CP. Better to fail a request than double-spend."

### AP systems — prioritize availability over consistency during partition (Cassandra, DynamoDB, CouchDB)
Every reachable node keeps accepting reads and writes during a partition. Replicas may diverge and reconcile later (last-write-wins, vector clocks, CRDTs). Examples: Cassandra, DynamoDB (default reads), Riak, CouchDB, DNS. Use AP for feeds, likes, carts, sessions, product catalogues and metrics.
**In the interview:** "the like count is AP, so a few seconds of staleness is fine."

### PACELC — when no Partition: tradeoff between Latency and Consistency (extends CAP)
"If **P**artition: choose **A** or **C**. **E**lse: choose **L**atency or **C**onsistency." Even when the network is healthy, strong consistency means waiting for replicas (and cross-region acks), which adds latency. DynamoDB and Cassandra are PA/EL. Spanner and CockroachDB are PC/EC. PACELC describes everyday behaviour better than CAP does.
**In the interview:** mention it after CAP to show depth.

### BASE — Basically Available, Soft state, Eventually consistent (NoSQL philosophy)
The opposite design philosophy to ACID. **Basically available**: the system answers even if some data is stale or partial. **Soft state**: state may change without input as replicas converge. **Eventually consistent**: given time without writes, replicas agree. It fits massive-scale, highly available systems where some staleness is acceptable.
**In the interview:** contrast it with ACID in one line when discussing SQL vs NoSQL.

### Linearizability — strongest: operation appears atomic at a single point in time, most recent write always visible
The system behaves as if there's **one copy** of the data and every operation takes effect instantly at some point between its start and end. Once a write completes, every subsequent read anywhere sees it. You need it for locks, leader election, unique usernames and balances. It's expensive: it requires consensus or a single leader, and adds latency.
**In the interview:** "strong consistency" usually means linearizable.

### Sequential consistency — operations appear in program order but no global real-time guarantee
All nodes see operations in **the same order**, and each client's operations appear in the order it issued them, but that order needn't match real time (a read may not reflect a write that just finished on another client). It's weaker than linearizability.
**In the interview:** rarely needed beyond the definition.

### Causal consistency — causally related operations ordered, concurrent operations may differ
If operation A could have influenced B (B read A's result, or the same client did A then B), everyone sees A before B. Unrelated, concurrent operations may appear in different orders on different nodes. Example: a reply never appears before the comment it answers. It's the strongest model that stays available during partitions.
**In the interview:** good for comments, chat and social features.

### Read-your-writes — you always see your own writes (weaker than linearizability)
A session guarantee: after **you** write, **your** reads reflect it, while others may see it later. Implement it by reading from the primary right after writes, tracking replication positions, or keeping a session sticky to one replica.
**In the interview:** the common fix for "my update disappeared after refresh" with read replicas.

### Monotonic reads — reads never go backwards in time (you never see older data after seeing newer)
Once you've seen a version, later reads never return an older one. It's violated when successive reads hit replicas with different lag. Fix it by pinning a user to one replica, or tracking the last version they saw.
**In the interview:** pairs with read-your-writes as session guarantees.

### Eventual consistency — given no new writes, all replicas converge to same value eventually
The weakest useful guarantee: replicas may disagree for a while, but converge once writes stop. "Eventually" is usually milliseconds to seconds, though not bounded in theory. It's highly available and fast. Use it for social counts, recommendations, caches, DNS and search indexes.
**In the interview:** say **how stale** is acceptable ("within a few seconds"), not just "eventual".

### Strong eventual consistency — concurrent updates resolve deterministically without coordination (CRDTs)
Eventual consistency **plus** a guarantee: any two replicas that have received the same set of updates are in the **same state**, whatever the order, with no conflicts left to resolve manually. CRDTs achieve this mathematically (merges are commutative, associative and idempotent). Used in collaborative editors and Redis Enterprise active-active.
**In the interview:** mention it for offline-first and multi-leader designs.

## Consensus algorithms & leader election

### Raft — leader election (randomized timeout, first to get majority votes), log replication, safety
Raft is a consensus algorithm designed to be understandable. One **leader** per **term** handles all writes and replicates log entries to followers. An entry is **committed** once a majority stores it. If the leader dies, followers time out and elect a new one by majority vote. Used by etcd, Consul, CockroachDB, TiKV and Kafka KRaft. A 3-node cluster tolerates 1 failure, and 5 tolerate 2.
**In the interview:** explain the 3 parts: election, replication, safety.

### Raft leader election — each node has random election timeout; first to expire sends RequestVote
Followers expect heartbeats from the leader. If none arrives within a **randomised** timeout (e.g. 150–300 ms), a follower becomes a candidate, increments the term, votes for itself and sends **RequestVote** to the others. Nodes vote for at most one candidate per term, and only for candidates whose log is at least as up to date as their own. A majority makes it leader. The randomness makes split votes rare.
**In the interview:** "random timeouts avoid simultaneous candidacies."

### Raft log replication — leader appends entry, replicates to majority, only then commits
A client write goes to the leader, which appends it to its log and sends **AppendEntries** to followers. Once a **majority** has persisted the entry, the leader marks it committed, applies it to the state machine and replies to the client. Followers apply committed entries in the same order, and inconsistent follower logs are overwritten to match the leader's.
**In the interview:** "a write is acknowledged only after a majority has it, so it survives a minority failure."

### Raft safety property — at most one leader per term, committed entries are never lost
Since each node votes once per term and a majority is needed, **two leaders can't exist in the same term**. A candidate can only win if its log contains every committed entry (the election restriction), so committed data survives leader changes. Stale leaders discover a higher term and step down.
**In the interview:** "quorum intersection is why consensus works."

### Paxos — prepare/promise phase → accept/accepted phase (conceptual, harder to implement than Raft)
The classic consensus algorithm (Lamport). **Phase 1**: a proposer sends *Prepare(n)*, and acceptors *promise* to ignore lower-numbered proposals, reporting any value they've already accepted. **Phase 2**: the proposer sends *Accept(n, v)*, and once a majority accepts, v is chosen. It's provably correct but notoriously hard to understand and build into a full system. Used in Chubby and Spanner.
**In the interview:** "Raft and Paxos solve the same problem; Raft is easier to reason about."

### Multi-Paxos — designate stable leader to avoid repeated prepare phase
Basic Paxos agrees on a single value with two round trips. For a replicated log, Multi-Paxos elects a **stable leader** that runs Phase 1 once and then needs only Phase 2 (one round trip) per entry until leadership changes. In practice it ends up very similar to Raft.
**In the interview:** niche. One line is enough.

### Zookeeper Atomic Broadcast (ZAB) — Zookeeper's proprietary consensus protocol
ZooKeeper's own leader-based protocol: the leader orders all writes (zxid = epoch + counter) and broadcasts proposals, which commit once a majority acknowledges. A recovery phase on leader change ensures that committed transactions survive. It's conceptually close to Raft and Multi-Paxos, and guarantees a total order of updates.
**In the interview:** "ZooKeeper uses ZAB, which is Raft-like" is enough.

### etcd — Raft-based distributed KV store, used by Kubernetes for all cluster state
A strongly consistent, highly available key-value store built on Raft. It has watches (get notified on changes), leases (keys that expire unless refreshed) and transactions (compare-and-swap). Kubernetes stores **all** cluster state in it. It's also used for service discovery, config, leader election and distributed locks. Keep data small: it's for coordination, not bulk storage.
**In the interview:** the modern alternative to ZooKeeper.

### Zookeeper — Apache, used for leader election (ephemeral znodes), distributed locks, config
A hierarchical key-value store of **znodes**. **Ephemeral** znodes disappear when the client's session dies, and **sequential** znodes get increasing suffixes. **Watches** notify clients of changes. It's the building block for leader election, locks, membership and config. Historically used by Kafka (before KRaft), HBase, Hadoop and Solr.
**In the interview:** "ZooKeeper or etcd for coordination, never for data."

### Leader election with Zookeeper — create sequential ephemeral znode, watch predecessor
Each candidate creates `/election/n_` as **ephemeral + sequential**. The one with the **lowest** sequence number is leader. Every other node **watches only its immediate predecessor**, which avoids a herd of notifications when the leader changes. If the leader's session dies, its znode vanishes and the next node becomes leader.
**In the interview:** the "watch your predecessor" detail is impressive.

### Epoch numbers / terms — monotonically increasing, stale leaders reject writes with old epoch
Every leadership change increments a number (a Raft term, a ZAB epoch, a Kafka controller epoch). Messages carry it. A node receiving a higher epoch knows it's stale and steps down, and requests with a lower epoch are rejected. That stops a paused or partitioned old leader from causing damage.
**In the interview:** the same idea as fencing tokens, at the protocol level.

### Fencing tokens — monotonically increasing token for storage writes, prevents stale leader writes
When a lock or lease is granted, it comes with an increasing **token** (33, then 34…). Every write to the protected resource includes the token, and the storage **rejects tokens lower than the highest it has seen**. A client that paused (GC) past its lease expiry wakes up with token 33, but storage has already seen 34, so its write fails safely.
**In the interview:** the key point about why distributed locks alone aren't safe.

### Split-brain — two nodes both think they are leader; prevent with fencing tokens + quorum
After a partition or a missed heartbeat, the old leader and a newly elected one both accept writes, and the data diverges. Prevent it by requiring a **majority quorum** to be leader (a minority side can't elect), using **leases** that expire, **fencing** the old leader at the storage layer, and, in some setups, STONITH (power off the old node).
**In the interview:** comes up with database failover and leader election.

## Clocks, ordering & time

### Physical clocks — NTP synchronization, drift up to 100ms between nodes
Every machine's quartz clock drifts. **NTP** periodically corrects it, typically to within a few milliseconds on a LAN, but it can be 10–100+ ms off across the internet or during problems. Corrections can make clocks **jump** (even backwards). Cloud providers offer better time sync (AWS Time Sync, Google's leap smearing).
**In the interview:** "we don't rely on wall clocks to order events across machines."

### Clock skew — two machines have different wall clock times, cannot use for ordering events
At any moment, two servers' clocks disagree by some skew. An event on server A stamped 10:00:00.005 may actually have happened *after* one on server B stamped 10:00:00.010. Using timestamps for ordering or last-write-wins can therefore **silently lose** the truly later write.
**In the interview:** why LWW is dangerous, and why sequence numbers or logical clocks are used.

### Lamport timestamps — logical clocks: increment on send, max(local,received)+1 on receive, establish happens-before
Each process keeps a counter: increment it on every event, attach it to messages, and on receiving set `counter = max(local, received) + 1`. If A happened-before B, then L(A) < L(B). The converse doesn't hold, so concurrent events can't be detected. Ties broken by node ID give a **total order** consistent with causality.
**In the interview:** "logical clocks order events without trusting wall time."

### Vector clocks — per-node counters: detect causality and concurrency, identify conflicting writes
Each node keeps a vector with one counter per node. Compare two vectors: if every component of A is ≤ B, then A happened-before B. If neither dominates, they're **concurrent**, i.e. a conflict. Dynamo-style stores use this to keep both "sibling" versions for the application to merge. The vectors grow with the number of nodes.
**In the interview:** "vector clocks detect concurrent writes; LWW just guesses."

### Version vectors — detect divergence during replica synchronization
Similar to vector clocks, but tracked per **replica of a data item** rather than per event. Each replica records how many updates it has seen from each replica. During sync, comparing version vectors shows whether one copy is strictly newer (fast-forward) or they've diverged (conflict). Used in Riak and file-sync systems.
**In the interview:** niche. Treat it as a close cousin of vector clocks.

### Hybrid Logical Clocks (HLC) — combine physical + logical: max(physical, last_hlc) + 1
A timestamp that stays close to wall-clock time (human-readable, roughly real time) but also captures causality like a Lamport clock: take the max of physical time and the last-seen HLC, adding a logical counter on ties. It's tolerant of moderate clock skew. Used by CockroachDB, YugabyteDB and MongoDB.
**In the interview:** "how CockroachDB gets ordering without TrueTime hardware."

### Google TrueTime — GPS + atomic clocks, returns [earliest, latest] uncertainty interval (~7ms)
Each Google datacentre has GPS receivers and atomic clocks. The TrueTime API returns an **interval** guaranteed to contain the true time, with an uncertainty of a few milliseconds. Knowing the bound lets Spanner order transactions globally by timestamp.
**In the interview:** a one-sentence mention when discussing Spanner.

### Commit wait (Spanner) — wait out TrueTime uncertainty before returning commit timestamp
Spanner assigns a commit timestamp `s = TT.now().latest`, then **waits until TT.now().earliest > s** before releasing locks and acknowledging. Any transaction starting afterwards is therefore guaranteed a larger timestamp, which gives external consistency. The cost is a few milliseconds of wait per write.
**In the interview:** "trading a few milliseconds of latency for global ordering."

### Happens-before (→) — a→b means a causally precedes b; defines partial order of events
Lamport's relation: a → b if they're on the same process and a came first, or a is a send and b the matching receive, or by transitivity. If neither a → b nor b → a, the events are **concurrent**. It's the formal basis for logical clocks and causal consistency.
**In the interview:** use the term when explaining why order matters (a reply after a question).

### Total order vs partial order — total: every pair comparable; partial: concurrent events possible
**Total order**: any two events can be compared, as in a single log (a Kafka partition, a Raft log). **Partial order**: some events are concurrent and incomparable, as with causality across nodes. Building a total order across a distributed system requires a sequencer or consensus, which limits throughput.
**In the interview:** "total order per partition (per account or per chat), not globally."

### Monotonic clock — use for measuring elapsed time; wall clock for human-readable timestamps
A **monotonic clock** (`System.nanoTime()`, `CLOCK_MONOTONIC`) only moves forward and isn't affected by NTP jumps, so use it for timeouts, latency measurement and rate limiters. The **wall clock** (`System.currentTimeMillis()`, `Instant.now()`) can jump, so use it only for human-facing timestamps and logs.
**In the interview:** a nice LLD detail: "the token bucket uses nanoTime."

## Replication, failure detection & recovery

### Quorum reads/writes — N replicas, write to W, read from R; W+R>N ensures overlap and consistency
Each key has N replicas. A write succeeds after W acknowledgements, and a read queries R replicas and returns the newest version. If **R + W > N**, every read set overlaps every write set, so a read includes at least one replica holding the latest acknowledged write. Tune for workload: W=1 for fast writes, R=1 for fast reads.
**In the interview:** the core of Dynamo and Cassandra consistency.

### Common quorum config — N=3, W=2, R=2: tolerates 1 failure, consistent reads
With 3 replicas, writing to 2 and reading from 2 gives overlap (2 + 2 > 3), and both operations still succeed with one replica down. That's QUORUM/QUORUM in Cassandra. For multi-DC setups, use LOCAL_QUORUM to keep latency regional.
**In the interview:** quote this exact configuration.

### Gossip protocol — epidemic broadcast: each node periodically exchanges state with random peers, O(log N) convergence
Each node periodically (~1 s) picks a few random peers and exchanges what it knows (membership, heartbeats, metadata). News spreads like an epidemic and reaches everyone in O(log N) rounds. It's decentralised, scalable and robust to failures. Used in Cassandra, Consul (Serf), Redis Cluster and DynamoDB internals.
**In the interview:** "membership and failure detection without a central coordinator."

### Phi accrual failure detector — adaptive: outputs suspicion value φ, not binary up/down judgment
Instead of a fixed timeout ("dead after 5 s"), it models the distribution of heartbeat arrival times and outputs **φ**, a suspicion level that grows the longer a heartbeat is overdue relative to normal. The application picks a threshold (Cassandra's default is 8). It adapts to network jitter and avoids false positives on slow networks.
**In the interview:** niche, but a good one to name in a key-value store design.

### Read repair — detect stale replica during read, return latest to client, async update stale replica
When a read sees replicas with different versions, the coordinator returns the newest and pushes it to the stale replicas (in the background or before responding). Frequently read data heals itself, while cold data needs anti-entropy.
**In the interview:** one of the three repair mechanisms in leaderless replication.

### Anti-entropy repair — Merkle tree comparison between nodes, repair differences in background
Replicas build **Merkle trees** over key ranges and compare root hashes. Where they differ, they descend to find exactly which ranges disagree and sync only those. That catches divergence that read repair and hints missed, such as long outages or lost hints. In Cassandra it runs as scheduled `nodetool repair`.
**In the interview:** "Merkle trees let replicas compare terabytes by exchanging a few hashes."

### Hinted handoff — store writes for unavailable nodes locally, replay when node recovers
If a target replica is down, another node accepts the write along with a **hint** naming the intended owner, and forwards it when the owner returns. Writes stay available during short outages (a "sloppy quorum"). Hints expire after a window, so longer outages need repair.
**In the interview:** "keeps writes available during transient failures."

### CRDTs — Conflict-free Replicated Data Types: G-counter, PN-counter, LWW-Register, OR-Set, 2P-Set
Data types whose replicas can be updated independently and merged automatically to the same result. **G-Counter**: per-node increment-only counters, summed. **PN-Counter**: one G-counter for increments, one for decrements. **LWW-Register**: highest timestamp wins. **OR-Set**: add/remove with unique tags, so a re-add after a remove works. **2P-Set**: add and remove sets, with removals permanent.
**In the interview:** "a like counter as a PN-counter CRDT in an active-active multi-region setup."

### At-most-once delivery — fire and forget, may lose messages (UDP, basic HTTP without retry)
Send once and never retry: acknowledge or commit before processing. No duplicates, but messages can be lost. Acceptable for metrics, logs and telemetry where occasional loss doesn't matter.
**In the interview:** name it only to contrast with the next two.

### At-least-once delivery — retry until ack; messages may be duplicated, require idempotent consumers
Keep retrying until the receiver acknowledges, and acknowledge **after** processing. Nothing is lost, but duplicates happen (a crash after processing but before the ack). This is the practical default for Kafka, SQS and RabbitMQ, made safe by **idempotent consumers**.
**In the interview:** "at-least-once + idempotency = effectively once."

### Exactly-once semantics — hardest: Kafka transactions + idempotent producer + consumer isolation
Each message affects the result exactly once. Kafka achieves it within Kafka: an **idempotent producer** (dedupes retries by sequence number), **transactions** (atomically write outputs and commit input offsets) and consumers using `isolation.level=read_committed`. Side effects outside Kafka (DB writes, emails, payments) still need idempotency or dedupe on your side.
**In the interview:** "true end-to-end exactly-once doesn't exist; we build it from at-least-once plus idempotency."

### Idempotency key pattern — include unique key in request; server deduplicates and returns same result
The client attaches a unique key per logical operation. The server records `key → outcome` with a unique constraint (in the same transaction as the effect), so retries return the stored outcome instead of executing again. It applies to APIs, message consumers (using the event ID) and calls to external providers.
**In the interview:** use it in every payment, booking and order design.

### Distributed locks — Redis Redlock (quorum on N instances), Zookeeper ephemeral node, etcd lease
Mutual exclusion across machines. **Redis**: `SET key token NX PX ttl`, released with a token-checked delete (Redlock spreads it across N nodes). **ZooKeeper**: ephemeral sequential znodes. **etcd**: leases plus transactions. Every lock needs an expiry (for crashed holders), and correctness-critical uses need **fencing tokens**. Often a DB row lock or unique constraint is simpler and safer.
**In the interview:** say which you'd choose and why: efficiency vs correctness.

### Distributed transactions — 2PC (coordinator blocks on failure), Saga (compensating transactions)
Atomic changes across several databases or services. **2PC** gives atomic commit with a coordinator, but it's blocking and slow. **Sagas** chain local transactions with compensating actions, giving eventual consistency, availability and loose coupling. Microservices almost always use sagas plus an outbox.
**In the interview:** "2PC inside a distributed DB, sagas across services."

### Two-phase commit — Phase 1: prepare (all vote), Phase 2: commit (if all yes) / abort (if any no)
The coordinator asks every participant to **prepare**: each one writes the changes durably, holds its locks and votes yes or no. If **all** vote yes, the coordinator records the commit decision and tells everyone to **commit**. If any votes no, everyone aborts. It's used in XA transactions and inside distributed databases.
**In the interview:** know the two phases and the blocking problem below.

### Two-phase commit blocking problem — if coordinator crashes after prepare, cohorts wait forever
Participants that voted yes can't decide alone: committing might contradict an abort decision, and aborting might contradict a commit. If the coordinator crashes after prepare, they **hold locks indefinitely** until it recovers. Making the coordinator itself fault-tolerant through consensus (as Spanner does) solves this, at a cost.
**In the interview:** the main reason 2PC is avoided between microservices.

### Saga pattern — sequence of local transactions with compensating transactions on failure
Split a business transaction into steps T1…Tn, each a local ACID transaction that emits an event or reply. If step k fails, run compensations Ck−1…C1 (refund, release stock, cancel order). There's no isolation, so intermediate states are visible: use status fields ("PENDING") and design compensations to be idempotent and retryable. Put irreversible steps last.
**In the interview:** the standard order or payment workflow answer.

### Saga choreography — services react to events published by previous service (loose coupling)
There's no central controller. Order publishes `OrderCreated` → Inventory reserves and publishes `StockReserved` → Payment charges and publishes `PaymentFailed` → Inventory releases… It's loosely coupled and simple for 2–3 steps, but the overall flow is implicit, hard to trace and change, and can grow cyclic dependencies.
**In the interview:** fine for short flows. Mention distributed tracing to follow it.

### Saga orchestration — central saga orchestrator explicitly calls each service (easier to monitor)
An orchestrator (a state machine) tells each service what to do, tracks progress, handles timeouts, and triggers compensations. The flow is explicit, easy to monitor, audit and change. The orchestrator is extra code, but durable workflow engines (Temporal, Camunda, AWS Step Functions) make it robust.
**In the interview:** "orchestration for payments and long flows, because auditability matters."

### Exponential backoff + jitter — prevent retry storms: wait = min(cap, base × 2^attempt) + rand(0, base)
Retry after increasing delays (100 ms, 200 ms, 400 ms… capped), so a struggling dependency gets breathing room. Add **randomness (jitter)** so thousands of clients don't retry in lockstep. "Full jitter" means sleeping a random time between 0 and the backoff value. Set a maximum number of attempts or a retry budget, and only retry idempotent operations.
**In the interview:** say it whenever you mention retries.
