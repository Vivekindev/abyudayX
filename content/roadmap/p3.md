## Replication

### Read replicas — offload read traffic, replicate asynchronously from primary
Copies of the primary that serve **read** queries. The primary streams its WAL or binlog to them asynchronously. Add replicas to scale reads (dashboards, listings, search pages) and for failover. Writes still go only to the primary, so replicas don't help write throughput.
**In the interview:** "reads → replicas behind a reader endpoint, writes → primary". Then deal with replication lag.

### Replication lag — async replica may be seconds behind; affects read-your-writes
With async replication, a replica applies changes slightly after the primary. That's usually milliseconds, but it can be seconds or minutes under load or during long transactions. A user who just updated something may read stale data from a replica. Monitor lag and take lagging replicas out of rotation.
**In the interview:** always follow "read replicas" with "and here's how I handle lag": read-your-writes routing.

### Synchronous replication — write not confirmed until replica acks (low lag, higher latency)
The primary waits until a replica confirms it has the write (durably) before acknowledging the client. You get **zero data loss** on failover, at the cost of extra latency on every write, and writes stall if that replica is slow or down (unless you have several sync candidates).
**In the interview:** payments and ledgers often use sync (or quorum) replication to a standby for RPO ≈ 0.

### Semi-synchronous replication — at least one replica must ack (MySQL)
MySQL's middle ground: commit waits until **at least one** replica has *received* the event (not necessarily applied it). It's much safer than async, and cheaper than waiting on all replicas. If no replica responds within a timeout, it falls back to async.
**In the interview:** a good default for important data on MySQL.

### Single-leader replication — all writes go to leader, replicated to followers
One node accepts writes and the others copy its log in the same order. It's simple and easy to reason about (no write conflicts), and it's the default for Postgres, MySQL, MongoDB replica sets and Redis. The leader's write capacity is the ceiling, and failover needs leader election.
**In the interview:** the default assumption for any relational store in your design.

### Multi-leader replication — writes to any datacenter, conflicts must be resolved
Several leaders (often one per region) each accept writes and replicate to each other asynchronously. You get low local write latency and writes keep working during a region outage. But two regions can edit the same record concurrently, which creates **conflicts** you have to resolve. Offline-first apps (each device acting as a leader) are a form of this.
**In the interview:** use it only when multi-region writes are a real requirement, and explain the conflict strategy.

### Leaderless replication — Dynamo style (Cassandra, Riak), any node accepts writes
There's no leader. The client or a coordinator sends each write to all N replicas and waits for **W** acknowledgements, and reads query **R** replicas and take the newest version. With **R + W > N**, reads overlap the latest write. Repair happens via read repair, hinted handoff and anti-entropy. It's very available, with no failover step.
**In the interview:** explain it via Cassandra's QUORUM reads and writes.

### Conflict resolution — last-write-wins (LWW), merge functions, custom CRDT
When concurrent writes collide: **LWW** keeps the one with the highest timestamp. It's simple, but silently drops data, and clock skew makes it worse. **Merge functions**: application logic combines the versions (e.g. union of shopping-cart items). **CRDTs**: data types designed to merge automatically and deterministically (counters, sets, text). **Ask the user**: present both versions (a Dropbox "conflicted copy").
**In the interview:** pick based on the data. Counters suit a CRDT, documents need a merge or user choice, and caches can live with LWW.

### Replication factor — number of replicas (typically 3 for fault tolerance)
RF = how many copies of each piece of data exist. **RF = 3** is standard: it survives one node failure while still having a majority (2 of 3) for quorum operations, and survives two failures for durability. Spread the copies across **availability zones** so one datacentre outage doesn't lose all of them.
**In the interview:** "RF = 3 across 3 AZs" for Kafka, Cassandra and similar stores.

### Read-your-writes consistency — user always sees their own writes, route writes and reads to same node
After a user writes, their **own** later reads must reflect it, even if other users see it a bit later. Implementations: read from the primary for N seconds after that user's write. Track the write's log position and read from a replica only once it has caught up. Or read the user's own profile from the primary and everything else from replicas.
**In the interview:** the standard fix for "I updated my profile but still see the old one".

### Monotonic reads — user never reads older data after reading newer data
A user mustn't see time go backwards: refreshing shows a new comment, refreshing again (from a more-lagged replica) and it's gone. The fix is to **pin each user to one replica** (hash the user ID), or track the latest position each user has seen.
**In the interview:** pairs with read-your-writes as the "session guarantees".

## Sharding strategies

### Horizontal sharding — distribute rows of a table across multiple DB instances
Split one table's **rows** across many databases by a shard key: users A–H on shard 1, I–Q on shard 2. Each shard holds a subset and handles its own reads and writes, so capacity grows nearly linearly. The costs: routing logic, cross-shard queries and transactions, and resharding.
**In the interview:** introduce it only once you've shown that replicas, caching and vertical scaling won't do.

### Vertical partitioning — split different tables into different DBs by domain
Split by **table or feature** instead of by row: users and auth in one database, orders in another, analytics events in a third. It often follows microservice boundaries (database per service). It's simpler than sharding, but each partition is still capped at one machine.
**In the interview:** usually the first scaling step before horizontal sharding.

### Range-based sharding — shard by key range (user_id 1–1M on shard 1), easy range queries but hotspots
Each shard owns a contiguous key range. Range scans (`created_at BETWEEN …`) hit one or a few shards, and adding a shard means splitting a range. The danger is **hot spots**: monotonically increasing keys (time, auto-increment IDs) send all new writes to the last shard. HBase, Bigtable and CockroachDB split ranges automatically.
**In the interview:** good for time-series data **if** you prefix keys to spread writes.

### Hash-based sharding — hash(key) % N, even distribution, range queries hard
`shard = hash(user_id) % N` spreads keys evenly and removes sequential hot spots. Range queries must hit every shard, and **changing N remaps almost every key**, so resharding means moving nearly all the data. Consistent hashing or many fixed logical shards fix that.
**In the interview:** say "hash sharding with consistent hashing (or 1,024 logical shards) so we can add nodes cheaply."

### Consistent hashing for sharding — only K/N keys migrate when adding/removing nodes
Nodes and keys are placed on a hash ring, and each key belongs to the next node clockwise. Adding a node takes over only one arc, roughly **K/N keys**, instead of reshuffling everything. Virtual nodes even out the load. Used by Cassandra, DynamoDB and Riak, and by many cache clients.
**In the interview:** the standard way to make hash sharding elastic.

### Directory-based sharding — lookup service maps key to shard, flexible but single point of failure
A lookup table (`tenant_42 → shard_7`) decides placement. You can move any tenant anywhere, rebalance big customers onto dedicated shards, and mix strategies. Every request needs that lookup, so the directory must be **highly available and cached** (otherwise it's a SPOF and a bottleneck).
**In the interview:** great for multi-tenant SaaS where tenants vary hugely in size.

### Resharding — data migration challenge, double-write period, consistent hashing minimizes movement
Moving data to new shards without downtime: **double-write** new data to the old and new locations, **backfill** historical data in batches, **verify** (checksums, row counts), switch reads, then stop the old writes and clean up. Pre-splitting into many **logical shards** mapped onto few physical machines turns resharding into moving whole logical shards. Tools: Vitess, Citus, or automatic splitting in Mongo, Cassandra and DynamoDB.
**In the interview:** "1,024 logical shards from day one" is a strong line.

### Hot spots — celebrity rows, popular keys hitting same shard; solution: add random suffix
One key gets disproportionate traffic: a celebrity's profile, a viral post, a flash-sale SKU. Fixes: **salt the key** (`post_123#0…#9` across shards; write to a random one, read all and merge), cache hot keys in memory, replicate hot data to more nodes, or use time-bucketed keys so one partition doesn't grow forever.
**In the interview:** the follow-up after almost any sharding answer.

### Cross-shard queries — scatter-gather (fan out to all shards), expensive, avoid in hot paths
A query without the shard key (e.g. "find order by order_id" when sharded by user_id) must ask **every** shard and merge the results. Latency equals the slowest shard and load multiplies. Avoid it by choosing the shard key to match the main queries, embedding the shard ID in other IDs, or keeping a **global secondary index** (`order_id → user_id`).
**In the interview:** "every hot-path query includes the shard key."

### Cross-shard transactions — two-phase commit risk, prefer Saga pattern instead
An atomic update across two shards needs 2PC, which is blocking, slow and fragile when the coordinator fails. Prefer co-locating data that changes together on one shard (same shard key), or a **saga** with compensations and an outbox. Distributed SQL databases (Spanner, CockroachDB) do 2PC internally with consensus if you truly need it.
**In the interview:** for money moving between two accounts on different shards, use a saga through a suspense/clearing account.

### Shard key selection — high cardinality, even distribution, matches query pattern
A good shard key has **high cardinality** (many distinct values), spreads both reads and writes **evenly**, appears in most queries (so they hit one shard), keeps related data together (an order with its items), and doesn't increase monotonically (or gets hashed if it does). It's hard to change later, so choose carefully.
**In the interview:** examples: chat by `chat_id`, orders by `user_id`, SaaS by `tenant_id`, ledger by `account_id`.

## NoSQL databases

### MongoDB — documents, collections, BSON, replica sets, sharding (mongos + config servers)
Data is stored as JSON-like **documents** (BSON: binary JSON with richer types) in **collections**, with flexible schemas and nested objects and arrays. **Replica sets** give HA: one primary plus secondaries with automatic election. **Sharding** routes queries through **mongos** routers, using **config servers** that hold the chunk-to-shard metadata.
**In the interview:** good for catalogues, CMS content and user profiles with varied attributes.

### MongoDB shard key selection — cardinality, write distribution, query isolation
The shard key splits a collection into chunks across shards. You want **high cardinality**, **even write distribution** (avoid monotonically increasing `_id` or timestamps, or use a hashed shard key) and **query isolation** (queries include the key, so mongos targets one shard instead of broadcasting). Compound keys such as `{tenantId: 1, _id: 1}` are common. Since 5.0 you can reshard live, but it's still costly.
**In the interview:** the same principles as any shard key, with Mongo terms.

### MongoDB aggregation pipeline — $match, $group, $sort, $lookup, $project, $unwind
Documents flow through stages: `$match` filters (put it early so it can use indexes), `$group` aggregates (`$sum`, `$avg`), `$sort`, `$project` reshapes, `$unwind` flattens arrays into one document per element, and `$lookup` does a left join with another collection. It's MongoDB's answer to SQL GROUP BY and JOIN.
**In the interview:** "Mongo can join with $lookup, but if the design needs many joins, a relational DB fits better."

### MongoDB transactions — multi-document ACID since v4.0 (distributed since v4.2)
Single-document writes were always atomic, and good document modelling (embedding related data) avoids most multi-document needs. Since 4.0, multi-document transactions work in replica sets, and since 4.2 across shards. They have performance costs and time limits (60 s by default), so use them sparingly.
**In the interview:** "Mongo has transactions now, but if most operations need them, choose Postgres."

### Redis data structures — string, list, hash, set, sorted set, stream, HyperLogLog, bitmap, geo
**String**: cache values, counters (`INCR`), locks (`SET NX`). **List**: queues, recent items. **Hash**: object fields. **Set**: unique members, intersections. **Sorted set**: leaderboards, timelines, rate-limit windows. **Stream**: an append-only log with consumer groups. **HyperLogLog**: approximate distinct counts in 12 KB. **Bitmap**: per-user daily flags. **Geo**: radius search.
**In the interview:** naming the right structure for each job ("sorted set for the leaderboard") is the skill being tested.

### Redis persistence — RDB (point-in-time snapshot) vs AOF (append-only log, fsync: always/everysec/no)
**RDB**: periodic forked snapshots to a compact file. Restarts are fast, but you lose everything since the last snapshot. **AOF**: logs every write, with `appendfsync always` (safest, slowest), `everysec` (lose at most ~1 s, the common choice) or `no` (leave it to the OS). AOF files get rewritten to compact them. Production often runs both.
**In the interview:** even with AOF, treat Redis as a cache or derived store unless you've deliberately designed it as the system of record.

### Redis Sentinel — HA: monitors master, auto-failover to replica on failure
Sentinel processes (run at least 3 for quorum) monitor a Redis primary and its replicas. If the primary fails, the sentinels agree, promote a replica, and tell clients the new address. It's for **non-sharded** setups. Because replication is async, a failover can lose the last writes.
**In the interview:** "Sentinel for HA of a single dataset, Cluster when you need to shard."

### Redis Cluster — shards data across 16384 hash slots, each node owns a range
Keys map to one of **16,384 slots** (`CRC16(key) % 16384`), and slots are spread across primaries, each with replicas. Clients are cluster-aware and follow MOVED redirects. Multi-key commands only work within one slot, which you force with **hash tags** (`{user42}:cart`, `{user42}:profile`). Resharding moves slots live.
**In the interview:** know hash tags. Multi-key Lua scripts need them.

### Redis Streams — persistent ordered log with consumer groups (Kafka-lite)
`XADD` appends entries with auto-generated time-based IDs. **Consumer groups** (`XREADGROUP`) spread entries across consumers, track pending (unacknowledged) entries, and support `XACK` and claiming stuck messages. It's lighter than Kafka, but limited by Redis memory and single-node throughput per stream.
**In the interview:** a reasonable choice for small-to-medium event queues when you already run Redis.

### Distributed lock with Redlock — acquire lock on N/2+1 nodes with short TTL, quorum-based safety
Redlock takes the same lock (`SET key token NX PX ttl`) on a majority of N independent Redis nodes within a time limit, and releases it with a token-checked delete. It's debated: GC pauses and clock jumps can still produce two holders (Kleppmann's critique). For correctness, use **fencing tokens**, or rely on DB constraints or etcd/ZooKeeper.
**In the interview:** "a single Redis lock is fine for efficiency, like de-duplicating cron runs. For correctness-critical work, add fencing or use the database."

### Cassandra data model — keyspace, table, partition key (distributes data), clustering key (orders within partition)
**Keyspace** = a database, with its replication settings. The **partition key** decides which nodes hold the data (hashed on the ring), and the **clustering key** sorts rows *within* a partition. `PRIMARY KEY ((chat_id), message_ts)` stores a chat's messages together, sorted by time. Modelling is **query-first**: one table per query, with data duplicated across tables.
**In the interview:** design the table from the exact read query, then keep partitions bounded (add a time bucket).

### Cassandra write path — commit log → memtable → SSTable flush (LSM tree)
A write is appended to the **commit log** (durability) and to the in-memory **memtable**, then acknowledged. That makes writes very fast. Full memtables are flushed to immutable sorted **SSTables** on disk, and background **compaction** merges SSTables. There are no in-place updates: updates and deletes are just newer entries.
**In the interview:** it explains why Cassandra handles huge write volumes (chat, IoT, logs).

### Cassandra read path — bloom filter check → SSTable cache → data files (from multiple SSTables)
A read checks the memtable, then, for each SSTable that might contain the partition (checked with a per-SSTable **bloom filter**), the key cache and partition index to find the offset, then reads the data. Results from several SSTables are merged (newest timestamp wins). More SSTables mean slower reads, which is why compaction strategy matters.
**In the interview:** "reads are costlier than writes in Cassandra; bloom filters and compaction keep them fast."

### Cassandra consistency levels — ONE, QUORUM, ALL, LOCAL_QUORUM, LOCAL_ONE
Set per query: how many replicas must respond. **ONE**: fastest, possibly stale. **QUORUM**: a majority across all datacentres. **ALL**: every replica (fragile). **LOCAL_QUORUM**: a majority within the local datacentre, which avoids cross-region latency (the most common choice in multi-DC setups). **LOCAL_ONE**. Reads and writes at QUORUM (R + W > RF) give read-your-writes.
**In the interview:** "LOCAL_QUORUM for both reads and writes."

### Cassandra gossip protocol — peer-to-peer O(log N) node state propagation
Every second, each node exchanges state (heartbeats, load, schema version, up/down status) with a few random peers. Information spreads epidemically, reaching all nodes in O(log N) rounds with no master. A **phi-accrual failure detector** turns heartbeat timing into a suspicion level for marking nodes down.
**In the interview:** "membership and failure detection without a single point of failure."

### Cassandra hinted handoff — store writes for down nodes, replay when node recovers
If a replica is down during a write, the coordinator keeps a **hint** (the write plus its target) and replays it once the node comes back, within `max_hint_window` (3 h by default). Writes stay available. Hints don't count toward the consistency level, and longer outages need full repair.
**In the interview:** one of the three repair mechanisms (hints, read repair, anti-entropy).

### Cassandra read repair — detect and fix stale replicas on read path
When a read queries several replicas and they disagree, the coordinator returns the newest value and writes it back to the stale replicas. Frequently read data heals itself. Rarely read data relies on anti-entropy repair.
**In the interview:** "repair on read" is a concise definition.

### Cassandra anti-entropy — periodic Merkle tree comparison between replicas
`nodetool repair` builds **Merkle trees** (hash trees) over token ranges on each replica, compares them, and streams only the ranges that differ. It must run regularly, more often than `gc_grace_seconds`, or deleted data can come back from the dead.
**In the interview:** a good example of Merkle trees in practice.

### Cassandra compaction — SizeTiered (write-heavy), Leveled (read-heavy), TWCS (time-series)
Compaction merges SSTables, discarding overwritten and deleted data. **STCS** merges similar-sized files: cheap writes, more read amplification and space spikes. **LCS** keeps small non-overlapping levels: reads touch about one SSTable, at higher write I/O. **TWCS** groups data by time window, so whole windows expire together, which is ideal for TTL'd time-series data.
**In the interview:** match the strategy to the workload: logs/metrics → TWCS, read-heavy → LCS.

### Cassandra tombstones — deleted data marked with timestamp, GC after gc_grace_seconds
Deletes write a **tombstone** marker rather than removing data, because other replicas need to learn about the delete. Tombstones are purged after `gc_grace_seconds` (10 days by default). Too many tombstones in a partition (e.g. using a table as a queue) makes reads scan thousands of them, causing slowdowns and errors.
**In the interview:** "don't use Cassandra as a queue" is a well-known lesson.

### DynamoDB — AWS managed, key-value + document, single-table design pattern
DynamoDB is a serverless, fully managed key-value/document store with single-digit-millisecond latency at any scale, on-demand or provisioned capacity, TTL, streams (CDC), and global tables (multi-region). **Single-table design**: put several entity types in one table with generic keys (`PK = USER#42`, `SK = ORDER#2026-11-09`) so one query fetches related items together.
**In the interview:** great when access patterns are known up front and you want zero operations work.

### DynamoDB partition key + sort key, GSI (Global Secondary Index), LSI (Local)
The **partition key** is hashed to choose the storage partition. The optional **sort key** orders items within it and allows range queries (`begins_with`, `between`). A **GSI** is a different partition/sort key over the same data, asynchronously maintained and eventually consistent, so you can query by other attributes. An **LSI** has the same partition key with a different sort key, must be defined at creation, and supports strong reads.
**In the interview:** list the access patterns, then map each to the table or a GSI.

### DynamoDB hot partition — high-cardinality partition key is essential; write sharding for counters
Each partition has throughput limits (roughly 3,000 reads and 1,000 writes per second). A low-cardinality or skewed key (`status = ACTIVE`, today's date) overloads one partition and causes throttling. Adaptive capacity helps but isn't magic. For hot counters, **write-shard** the key (`likes#0…#9`) and sum on read.
**In the interview:** the main DynamoDB pitfall to mention.

### Graph DB (Neo4j) — nodes, relationships, properties, Cypher query language
Data is stored as **nodes** (entities) and **relationships** (typed edges), both with properties. Traversals follow pointers instead of joins, so "friends of friends who like X" stays fast however deep the query goes. Queries use **Cypher**: `MATCH (a:User)-[:FOLLOWS]->(b)-[:FOLLOWS]->(c) RETURN c`. Good for recommendations, fraud rings, access graphs and knowledge graphs.
**In the interview:** at Facebook/Twitter scale, social graphs often live in sharded KV/SQL stores instead (TAO), because graph databases are harder to shard.

### Time-series DB — InfluxDB, TimescaleDB (Postgres extension), Prometheus TSDB
Optimised for timestamped measurements: append-mostly writes, time-range queries, downsampling, retention policies and heavy compression of similar consecutive values. **TimescaleDB** extends Postgres with automatic time partitioning (hypertables). **InfluxDB** is purpose-built. **Prometheus** stores metrics locally with a pull model.
**In the interview:** use for metrics, IoT and market ticks. Not as a general database.

## NewSQL & cloud databases

### Google Spanner — globally distributed, external consistency, TrueTime (GPS + atomic clocks)
Spanner is a SQL database spread across regions with **ACID transactions** and **external consistency** (strict serializability: commit order matches real time). Data is split into ranges replicated with Paxos. **TrueTime** gives tight clock-uncertainty bounds, so timestamps can be ordered globally. Writes cost cross-region consensus latency.
**In the interview:** the answer for "global strong consistency". Name it, along with its latency cost.

### TrueTime — returns [earliest, latest] time interval, commit wait ensures monotonicity
TrueTime doesn't return a single "now". It returns an interval [earliest, latest], with uncertainty of a few milliseconds thanks to GPS receivers and atomic clocks in each datacentre. On commit, Spanner picks a timestamp and **waits until that timestamp is definitely in the past everywhere** ("commit wait"). Any transaction that starts later is then guaranteed a higher timestamp.
**In the interview:** a fascinating detail, but one sentence is enough.

### CockroachDB — distributed Postgres-compatible, Raft consensus per range
CockroachDB speaks the Postgres wire protocol. Data is split into ~512 MB ranges, each replicated by its own **Raft** group. Transactions are serializable by default and span ranges with a distributed commit protocol. It survives node and zone failures automatically and uses hybrid logical clocks instead of TrueTime.
**In the interview:** "Postgres semantics with horizontal scale and multi-region", at the cost of higher latency than single-node Postgres.

### TiDB — MySQL-compatible, separates compute (TiDB) from storage (TiKV with Raft)
TiDB speaks the MySQL protocol. Stateless SQL nodes (TiDB) sit on top of **TiKV**, a distributed transactional key-value store with Raft-replicated regions, and **TiFlash** provides columnar replicas for analytics (HTAP). It's popular for scaling MySQL workloads without manual sharding.
**In the interview:** an alternative to Vitess for scaling MySQL.

### YugabyteDB — PostgreSQL-compatible distributed SQL, uses DocDB storage engine
YugabyteDB reuses the Postgres query layer on top of **DocDB**, a distributed document store built on RocksDB with Raft replication per tablet. It also offers a Cassandra-compatible API (YCQL). It's similar in spirit to CockroachDB.
**In the interview:** list it alongside CockroachDB and Spanner as distributed SQL options.

### Aurora — MySQL/Postgres-compatible, shared distributed storage (6-way replication across 3 AZs)
Aurora separates compute from a log-structured **storage layer** that keeps **6 copies across 3 AZs**. A write needs 4 of 6, a read 3 of 6. Only redo log records are shipped, not pages. Up to 15 low-lag read replicas share the same storage, and failover takes about 30 seconds. Aurora Serverless scales compute automatically.
**In the interview:** "managed Postgres/MySQL with better HA and read scaling" is a common practical choice.

### Columnar storage — Parquet, ORC, Apache Arrow — for analytics, 10–100× faster than row stores
Values are stored **column by column** instead of row by row. Analytics queries read only the columns they need, and similar values compress extremely well (dictionary, run-length and delta encoding). **Parquet** and **ORC** are on-disk file formats for data lakes. **Arrow** is an in-memory columnar format for zero-copy exchange between tools.
**In the interview:** "events land in S3 as Parquet, queried with Athena, Spark or BigQuery."

### Column-oriented query execution — predicate pushdown, vectorized processing, compression
Columnar engines skip whole file blocks using min/max statistics (**predicate pushdown**), process batches of values with SIMD (**vectorised execution**) instead of one row at a time, and often operate directly on compressed data. That's why ClickHouse, BigQuery and Snowflake aggregate billions of rows in seconds.
**In the interview:** explains OLAP speed. Pairs with OLTP vs OLAP.

### B-tree vs LSM-tree — B-tree: read-optimized (database indexes); LSM: write-optimized (Cassandra, RocksDB)
**B-tree**: updates pages in place. Reads are predictable (a few page reads), but random writes are slower. Used by Postgres, MySQL and Oracle. **LSM**: buffers writes in memory and flushes sorted immutable files, then compacts them. Writes are very fast and sequential, while reads may check several files (helped by bloom filters). Used by Cassandra, RocksDB, HBase and ScyllaDB.
**In the interview:** "write-heavy and append-mostly → LSM, read-heavy and transactional → B-tree."

### Write amplification in LSM trees — compaction rewrites data multiple times
In an LSM tree, a byte written once may be rewritten many times as compaction merges it into larger levels: 10–30× write amplification is common with leveled compaction. That costs disk bandwidth and SSD lifetime, and compaction bursts compete with live traffic. Tuning (size-tiered compaction, larger memtables) trades write amplification against read and space amplification.
**In the interview:** "LSM writes are cheap up front, but compaction costs come later."

### Read amplification mitigated — bloom filter per SSTable level avoids unnecessary disk seeks
A point read in an LSM tree might have to check many SSTables. Each SSTable has a **bloom filter** that answers "definitely not here" for most of them, so the engine only touches files that might hold the key, usually one or two disk reads. Fence-pointer indexes and block caches cut the cost further.
**In the interview:** links the bloom filter (probabilistic data structures) to real database internals.
