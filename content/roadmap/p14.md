## OOP & principles

### Four pillars — encapsulation, abstraction, inheritance, polymorphism
**Encapsulation**: hide state behind methods (private, final fields, invariants enforced inside the class). **Abstraction**: expose *what* through interfaces and hide *how*. **Inheritance**: is-a reuse (use sparingly). **Polymorphism**: callers work with an interface while the concrete class decides behaviour (`PaymentMethod.pay()` for card, UPI or wallet).
**In the interview:** use these words when explaining your class design. [Lesson →](#/item/oop-solid)

### SOLID principles — SRP, OCP, LSP, ISP, DIP
**S**ingle responsibility: one reason to change. **O**pen/closed: extend with new classes, don't edit growing if/else chains. **L**iskov substitution: subtypes must behave like their parent (Square/Rectangle is the classic violation). **I**nterface segregation: small focused interfaces. **D**ependency inversion: depend on interfaces and inject implementations (Spring DI), which also makes code testable.
**In the interview:** give one concrete example per letter, ideally from your design.

### Composition over inheritance — has-a beats deep hierarchies
Build behaviour by **combining objects** (a Vehicle *has* an Engine, a Service *has* a PricingStrategy) instead of deep subclass trees, which are rigid, fragile and prone to LSP violations. Composition lets behaviour be swapped at runtime and tested in isolation. Reserve inheritance for true is-a relationships with shared behaviour (often abstract base classes).
**In the interview:** "I'll compose a pricing strategy rather than subclassing per vehicle type."

## Design patterns

### Creational — Singleton, Factory, Builder
**Singleton**: exactly one instance (config, registry). Prefer DI-managed singletons for testability. **Factory**: centralise creation based on input (`NotificationSenderFactory.create(channel)`), keeping `new` out of business code. **Builder**: construct complex objects with many optional fields readably and immutably (`Order.builder()…build()`, Lombok `@Builder`).
**In the interview:** use them where creation logic varies or is complex. [Patterns lesson →](#/item/design-patterns)

### Strategy pattern — swap algorithms at runtime
Define a family of interchangeable algorithms behind one interface and inject the one you need: pricing (hourly, weekend), spot allocation (nearest, EV-first), split types (equal, exact, percent), rate-limit algorithms (token bucket, sliding window). New behaviour means a new class (Open/Closed).
**In the interview:** the most frequently useful pattern in LLD rounds.

### Observer pattern — notify subscribers of changes
Subjects keep a list of listeners and notify them on events: parking display boards on spot changes, price alerts on ticks, notification channels on order updates. Decouples producers from consumers. In Java, use thread-safe listener lists (CopyOnWriteArrayList) and consider async dispatch so slow observers don't block.
**In the interview:** "display boards observe spot availability."

### State pattern — behaviour changes with lifecycle state
Each lifecycle state is a class implementing only the actions legal in that state, and transitions swap the current state object. It replaces giant switch statements in every method. Classic uses: ATM (Idle → CardInserted → Authenticated → Dispensing), vending machine, order and payment lifecycles, elevator.
**In the interview:** the go-to pattern for the ATM and vending-machine problems. [ATM →](#/item/lld-atm)

### Decorator & Adapter — wrap to add behaviour or translate interfaces
**Decorator**: wrap an object implementing the same interface to add behaviour (logging, retries, caching, metrics around a `PaymentGateway`), stackable at runtime. **Adapter**: make a third-party or legacy interface fit yours (`RazorpayAdapter implements PaymentGateway`), isolating vendor SDKs from business code.
**In the interview:** "adapters per PSP, decorated with retry and logging."

### Chain of Responsibility — pass requests along handlers
A request travels through a chain of handlers, each processing it or passing it on: ATM cash dispensing (₹2000 → ₹500 → ₹200 → ₹100), request validation pipelines, approval workflows (team lead → manager → director by amount), servlet filters and middleware.
**In the interview:** the clean answer for denomination dispensing.

## Machine coding & concurrency

### Machine-coding approach — requirements, entities, classes, code, tests in 90 minutes
Spend 5–10 minutes clarifying and listing requirements (and what's out of scope), identify entities from nouns, sketch the class diagram and interfaces, then **code the core flow first** so you have a runnable demo early. Add extensibility (patterns) and edge cases next, then concurrency, then a few tests. Use clean packages, good names and custom exceptions.
**In the interview:** working, readable, extensible code beats clever, unfinished code. [Method →](#/item/lld-approach-concurrency)

### Java concurrency toolkit — locks, atomics, ConcurrentHashMap, executors
`synchronized` and `ReentrantLock` (tryLock, fairness) for mutual exclusion. `ReadWriteLock` for read-mostly data. `AtomicInteger` and `LongAdder` for counters. `ConcurrentHashMap` with atomic `computeIfAbsent`/`merge`. `BlockingQueue` for producer-consumer. `ExecutorService` and `CompletableFuture` for async work. `Semaphore` to limit concurrency. Java 21 virtual threads for I/O-bound tasks.
**In the interview:** pick the narrowest tool that makes the operation atomic.

### Thread-safe singleton — holder idiom, enum, double-checked locking
**Initialisation-on-demand holder**: a private static nested class holds the instance, created lazily and thread-safely by class loading. **Enum singleton**: simplest, and safe against serialisation and reflection. **Double-checked locking** needs a `volatile` field to be correct. In Spring apps, a singleton-scoped bean is usually the right answer.
**In the interview:** write the holder idiom from memory.

### Per-resource locking — CAS on the resource instead of one global lock
Instead of one lock around the whole parking lot or seat map, make the claim atomic **per resource**: `AtomicBoolean.compareAndSet(false, true)` on a spot, per-seat locks, `ConcurrentHashMap.putIfAbsent` for holds. Only threads contending for the *same* resource interact, so throughput scales. In a distributed setup the equivalent is a conditional DB update or Redis `SET NX`.
**In the interview:** the expected answer for "two cars at two gates taking the same spot".
