## Messaging fundamentals

### Point-to-point queue — one message consumed by exactly one consumer (work queue pattern)
Producers put messages on a queue, and each message goes to **one** of the consumers. Adding consumers spreads the work (competing consumers). It's typical for background jobs: send email, resize image, generate invoice. Examples: SQS, a RabbitMQ queue, Celery/Sidekiq, or Kafka within one consumer group.
**In the interview:** "a work queue with N workers, autoscaled on queue depth."

### Publish-subscribe topic — one message delivered to all subscribed consumers
A message published to a topic is delivered to **every** subscriber (or every subscriber group). One `OrderPlaced` event feeds Payments, Inventory, Email and Analytics independently, and the publisher doesn't know who listens. Examples: Kafka topics (one copy per consumer group), SNS, Google Pub/Sub, RabbitMQ fanout exchanges.
**In the interview:** the backbone of event-driven microservices.

### Pull consumer model — consumer polls for messages (Kafka, SQS); consumer controls pace
Consumers request messages when they're ready. They control their own pace, so there's natural backpressure, and they can batch for efficiency and replay by moving their offset. They need to poll efficiently (long polling) to avoid wasted calls and latency.
**In the interview:** "Kafka consumers pull, so a slow consumer just lags instead of being overwhelmed."

### Push consumer model — broker pushes to consumer (RabbitMQ); simpler but broker must manage rate
The broker delivers messages to consumers as they arrive, giving low latency and simple consumers. The broker must avoid overwhelming them: RabbitMQ uses a **prefetch count** (max unacknowledged messages per consumer). Webhooks and SNS-to-HTTP are push models too.
**In the interview:** mention prefetch or flow control if you choose push.

### Message durability — persisted to disk (Kafka, SQS) vs in-memory (RabbitMQ default)
A durable broker writes messages to disk (and replicates them) before acknowledging the producer, so they survive crashes. Kafka always persists and replicates. In RabbitMQ you need durable queues *and* persistent messages (quorum queues for replication). In-memory or transient messaging (Redis pub/sub, NATS core) is faster but loses messages on failure.
**In the interview:** for orders and payments, say "durable, replicated, acks=all".

### Message ordering — FIFO within partition (Kafka), not across partitions; SQS FIFO queues for order
Global ordering doesn't scale, so systems order **per key**. Kafka keeps order within a partition (same key → same partition). SQS FIFO keeps order within a **message group ID**. Retries and multiple consumers can break ordering, so process one key sequentially and handle out-of-order events (sequence numbers, version checks).
**In the interview:** "partition by account_id, so events per account stay ordered."

### Dead letter queue (DLQ) — messages that fail after N retries go here for inspection
After a message fails processing N times (with backoff), move it to a separate DLQ instead of retrying forever or dropping it. Alert on DLQ depth, inspect the failures, fix the bug, then **redrive** (replay) the messages. SQS and RabbitMQ support DLQs natively, and with Kafka you publish to a retry or DLQ topic yourself.
**In the interview:** always include a DLQ in async designs.

### Poison pill message — causes consumer to crash; detect with retry count, send to DLQ
A malformed or unexpected message makes the consumer throw or crash every time. With ordered processing, it blocks everything behind it in that partition. Track the delivery or retry count, catch deserialisation errors, and after N attempts move it to the DLQ and continue. Schema validation at the producer helps prevent it.
**In the interview:** "one bad message must never stop the pipeline."

### Message deduplication — use idempotency key; consumer maintains processed-IDs set (inbox table)
With at-least-once delivery, duplicates will arrive. Give every message a unique ID. The consumer records processed IDs (an inbox table with a unique constraint, or a Redis set with a TTL) **atomically with its side effect**, and skips IDs it has seen. Or make the operation naturally idempotent (set status to PAID only if currently PENDING).
**In the interview:** pair it with at-least-once delivery every time.

### Backpressure — slow consumer signals producer to slow down; Kafka: consumer controls offset commit rate
When downstream can't keep up, something must give: buffer (a queue grows), slow the producer (blocking or bounded queues, TCP flow control), or drop or shed load. Pull-based systems like Kafka handle it naturally: consumers fall behind (lag grows) without crashing. Monitor lag, autoscale consumers, and reject at the edge (429) if the backlog becomes unacceptable.
**In the interview:** "bounded queues and lag-based autoscaling", never unbounded in-memory buffers.

### Fan-out pattern — one event triggers multiple independent consumers (order placed → payment + inventory + email)
Publish one event and let any number of services react independently, each with its own subscription or consumer group, at its own pace and with its own retries. Adding a new consumer (e.g. fraud analytics) needs no change to the producer. Watch for consistency between consumers (each is eventually consistent) and for tracing across them.
**In the interview:** "OrderPlaced fans out to inventory, notifications, analytics and loyalty."

### Competing consumers — multiple workers on same queue share load, each message processed once
Run N identical consumers on one queue, and the broker hands each message to one of them. Throughput scales horizontally, and a crashed worker's unacknowledged messages get redelivered to others. In Kafka, parallelism is capped by the partition count. Ordering across messages is lost unless you partition by key.
**In the interview:** scale workers on queue depth or lag.

### Message schema evolution — Avro/Protobuf compatibility modes: backward (reader handles old schema), forward (reader handles new schema), full
Producers and consumers deploy independently, so message formats must evolve safely. **Backward compatible**: new consumers can read old messages (add optional fields with defaults). **Forward compatible**: old consumers can read new messages (they ignore unknown fields). **Full** means both. A Schema Registry enforces these rules. Never rename or reuse field numbers in Protobuf.
**In the interview:** "Avro/Protobuf with a Schema Registry set to backward compatibility."

## Apache Kafka deep dive

### Topic — named logical stream of records
A topic is a category of events (`orders`, `payments.authorized`), stored as an append-only log split into partitions. Records are key-value pairs with timestamps and headers. Many producers can write to a topic and many consumer groups can read it independently. Retention is time- or size-based, not consumption-based.
**In the interview:** name topics after business events.

### Partition — unit of parallelism; messages ordered within partition, not across
Each topic is split into partitions: ordered, immutable logs stored on different brokers. The producer picks one by `hash(key) % partitions`. Ordering is guaranteed **only within a partition**. Partitions set the max consumer parallelism per group, so choose the count with headroom, because increasing it later changes key mapping.
**In the interview:** "12 partitions keyed by account_id: per-account order, 12-way parallelism."

### Offset — position of message within partition; unique and monotonically increasing
Each record in a partition has an offset (0, 1, 2…). Consumers track the next offset to read and **commit** it (stored in the internal `__consumer_offsets` topic). Rewinding the offset lets you **replay** history, for reprocessing after a bug or bootstrapping a new service.
**In the interview:** commit after processing for at-least-once delivery.

### Consumer group — each partition consumed by exactly one consumer in group; parallelism = partition count
Consumers sharing a `group.id` split the partitions between them, so each partition goes to one consumer in the group. Different groups each get the full stream (pub/sub). Group membership changes trigger a **rebalance**. Extra consumers beyond the partition count sit idle.
**In the interview:** the "queue within a group, pub/sub across groups" duality.

### Producer acks — acks=0 (fire and forget), acks=1 (leader only), acks=all (all ISR must ack)
**acks=0**: don't wait at all, so data can be lost silently. **acks=1**: the leader wrote it, but data is lost if the leader dies before followers copy it. **acks=all**: every in-sync replica has it, the safest option. Combine it with `min.insync.replicas=2` and RF=3 for durability against one broker failure.
**In the interview:** "acks=all with idempotence enabled" for any business-critical topic.

### ISR (In-Sync Replicas) — set of replicas fully caught up to leader; min.insync.replicas threshold
The ISR is the set of replicas (leader included) caught up within `replica.lag.time.max.ms`. With acks=all, a write succeeds when every ISR member has it. If the ISR shrinks below `min.insync.replicas`, producers get errors instead of silently losing durability. Only ISR members are eligible for leader election (unless unclean election is enabled, which risks data loss).
**In the interview:** explain how RF=3 plus min ISR 2 tolerates one broker failure.

### Exactly-once semantics — enable.idempotence=true + transactional.id + consumer isolation=read_committed
**Idempotent producer**: the broker dedupes retried sends using the producer ID and sequence numbers. **Transactions** (`transactional.id`): atomically write to several partitions *and* commit consumer offsets, all or nothing. Consumers with `read_committed` don't see aborted or uncommitted records. Together they give exactly-once for consume → process → produce loops (Kafka Streams with `processing.guarantee=exactly_once_v2`).
**In the interview:** add that external side effects still need idempotency.

### Consumer lag — latest_offset - committed_offset per partition; monitor to detect slow consumers
Lag is how far behind a consumer group is, measured in messages or time. Rising lag means consumers can't keep up (too few consumers, slow downstream, a poison message, rebalancing storms). Alert on lag and autoscale on it (KEDA). Tools: Burrow, Kafka exporter for Prometheus, Confluent Control Center.
**In the interview:** "the #1 Kafka health metric."

### Compacted topics — retain only latest value per key; used for changelogs, Kafka as database
With `cleanup.policy=compact`, Kafka eventually keeps only the **latest record per key** (older ones are removed by compaction, and a null value is a tombstone that deletes the key). The topic becomes a durable "current state" table: user settings, account status, Kafka Streams changelogs, CDC snapshots. New consumers can rebuild full state by reading it.
**In the interview:** "a compacted topic as the source for rebuilding caches."

### Kafka Streams — stream processing library: stateful transformations with RocksDB local state stores
A Java library (not a cluster) for building stream apps inside your service: filter, map, join, windowed aggregations. State lives in local **RocksDB** stores, backed by compacted changelog topics for fault tolerance. It scales by running more app instances, which split the partitions, and supports exactly-once.
**In the interview:** good for real-time aggregation such as per-merchant transaction counts for fraud checks.

### Kafka Connect — source connectors (DB → Kafka) and sink connectors (Kafka → DB/S3)
A framework for moving data in and out of Kafka without writing code. **Source** connectors include Debezium CDC, JDBC and files. **Sink** connectors include S3, Elasticsearch, Snowflake and JDBC. It runs as a distributed worker cluster, tracks offsets, retries, and supports single-message transforms.
**In the interview:** "Debezium source → Kafka → Elasticsearch sink" keeps search in sync.

### Schema Registry — Avro/Protobuf schema storage, compatibility enforcement on produce/consume
A service (Confluent, Apicurio, AWS Glue) storing versioned schemas per topic. Producers register schemas and messages carry a small schema ID instead of the full schema. The registry **rejects incompatible changes** according to the compatibility mode, so a producer deploy can't break consumers.
**In the interview:** part of a mature event-driven platform answer.

### Kafka transactions — atomic multi-partition produce + offset commit
A producer with a `transactional.id` begins a transaction, sends to several partitions and topics, adds the consumer offsets to it, and then commits or aborts atomically. A transaction coordinator writes markers into the logs. "Zombie" producer instances are fenced by epoch. It's what makes exactly-once stream processing possible.
**In the interview:** detail-level. Use it to back up an exactly-once claim.

### Retention — by time (retention.ms) or size (retention.bytes), not by consumer acknowledgement
Kafka deletes old log **segments** after a time (7 days by default) or size limit, **regardless** of whether anyone consumed them. Slow consumers can lose data if they fall behind retention. Infinite retention plus **tiered storage** (old segments offloaded to S3) makes Kafka a long-term event store.
**In the interview:** contrast it with traditional queues, which delete on acknowledgement. Kafka enables replay.

### Log compaction — background thread merges segments, keeps latest value per key
The log cleaner rewrites older segments, dropping records superseded by a newer record with the same key, and removes tombstones after `delete.retention.ms`. The latest value per key is always kept. Compaction preserves order and offsets of surviving records, and runs on compacted topics only.
**In the interview:** explain it alongside compacted topics. They're the same feature.

## Other messaging systems

### RabbitMQ — exchanges (direct, fanout, topic, headers), bindings, routing keys, queues
Producers publish to an **exchange** with a routing key, and **bindings** route messages into queues. **Direct**: exact key match. **Fanout**: every bound queue. **Topic**: wildcard patterns (`order.*.created`). **Headers**: match on headers. Messages are deleted once acknowledged. It supports priorities, TTLs, DLX (dead-letter exchanges), and quorum queues for replication.
**In the interview:** "RabbitMQ for task queues needing flexible routing and per-message acknowledgements."

### RabbitMQ vs Kafka — traditional message broker vs distributed log; RabbitMQ: complex routing; Kafka: replay, high throughput
**RabbitMQ**: a smart broker that pushes to consumers, rich routing, per-message acks, deletes after consumption, and works well up to tens of thousands of messages per second. **Kafka**: a dumb broker with smart consumers, a retained partitioned log, replay, very high throughput, ordering per partition, and many independent consumer groups. Use RabbitMQ for job queues and complex routing, Kafka for event streaming, CDC, analytics and event sourcing.
**In the interview:** pick one and explain why. Both are respectable answers.

### AWS SQS Standard — at-least-once, best-effort ordering, up to 1 MiB, infinite scale
A fully managed queue with practically unlimited throughput, at-least-once delivery (duplicates possible) and best-effort ordering. Messages up to 1 MiB (use S3 for bigger payloads), retention up to 14 days, a **visibility timeout** (a received message is hidden until deleted or the timeout expires), long polling, and DLQ redrive.
**In the interview:** the default "simple queue" answer on AWS.

### AWS SQS FIFO — exactly-once processing, ordered within message group, 300 TPS (3000 with batching)
FIFO queues guarantee ordering within a **message group ID** and deduplicate within a 5-minute window (by deduplication ID or content hash). Base throughput is limited (300 messages per second, 3,000 with batching; high-throughput mode raises this significantly). Messages in different groups are processed in parallel.
**In the interview:** "a FIFO queue with group ID = account_id for ordered per-account processing."

### AWS SNS — pub/sub fan-out to SQS, Lambda, HTTP, email, SMS; no replay
A managed pub/sub service: publish once and SNS pushes to every subscription (SQS queues, Lambda, HTTP endpoints, email, SMS, mobile push). Messages aren't stored for replay. The common pattern is **SNS → multiple SQS queues** (fan-out with durable per-consumer buffering). Supports message filtering policies.
**In the interview:** "SNS fan-out to per-service SQS queues" is a classic AWS design.

### AWS Kinesis Data Streams — real-time, 1MB/s per shard, 7-day retention, replay capable
AWS's managed Kafka-like stream. Data is split into **shards** (each ~1 MB/s or 1,000 records/s in, 2 MB/s out), ordered per partition key within a shard, with 24 h to 365 days retention and replay. It integrates with Lambda, Firehose (to S3 or Redshift) and Flink. It's simpler to operate than Kafka, but has lower per-shard limits.
**In the interview:** an alternative to MSK (managed Kafka) on AWS.

### Google Cloud Pub/Sub — managed pub/sub, at-least-once, ordering per ordering-key, push or pull
Google's global, serverless messaging service. Topics and subscriptions, at-least-once delivery (with an exactly-once option), optional ordering by **ordering key**, push or pull delivery, dead-letter topics, replay by seeking to a timestamp. It scales automatically with no partitions to manage.
**In the interview:** the GCP equivalent of SNS + SQS + Kinesis.

### Apache Pulsar — tiered storage (offload to S3), geo-replication, multi-tenancy, unified queue+stream
A distributed messaging system that separates compute (stateless brokers) from storage (Apache BookKeeper). It has built-in **tiered storage** to S3, native **geo-replication**, **multi-tenancy** (tenants and namespaces), and supports both queue semantics (shared subscriptions) and stream semantics. It's used at Yahoo, Tencent and Splunk.
**In the interview:** mention it as a Kafka alternative where multi-tenancy and geo-replication matter.

### NATS — ultra-lightweight, sub-millisecond latency, JetStream for persistence
A simple, very fast messaging system (a single small binary). **Core NATS** is fire-and-forget pub/sub and request-reply (at-most-once). **JetStream** adds persistence, at-least-once and exactly-once delivery, replay and key-value and object stores. It's popular for IoT, edge and microservice request-reply.
**In the interview:** niche. Mention it for ultra-low-latency internal messaging.

## Event-driven patterns

### Event sourcing — append-only log of domain events is source of truth; current state = replay of events
Store every change as an immutable event (`AccountOpened`, `MoneyDeposited`, `MoneyWithdrawn`) instead of overwriting state. Current state is derived by replaying events, using **snapshots** to speed this up. You get a perfect audit trail, time travel and the ability to build new read models later. The costs: complexity, schema evolution, and eventually consistent queries.
**In the interview:** natural for ledgers, trading and order lifecycles. Overkill for simple CRUD.

### Event store — immutable, ordered, replayable; projections rebuild read models
The database of events: append-only streams per aggregate (e.g. per account) with optimistic concurrency (append only if the stream version is still N). **Projections** subscribe to events to build query-friendly views, and you can rebuild them from scratch at any time. Options: EventStoreDB, Kafka (with care), Postgres tables, Axon.
**In the interview:** "optimistic concurrency on the stream version prevents conflicting appends."

### CQRS — Command Query Responsibility Segregation: separate write model (commands) from read model (queries)
Use one model to **change** state (commands: validated, normalised, transactional) and different models to **read** it (queries: denormalised, shaped per screen). It lets each side scale and be optimised independently, e.g. writes to Postgres and reads from Elasticsearch or Redis. The read side is eventually consistent.
**In the interview:** use it when read and write patterns differ greatly. It doesn't require event sourcing.

### CQRS read models — optimized for query patterns, updated asynchronously via events
Precomputed views tailored to specific queries: an order-search index, a user dashboard, a timeline cache. Projectors consume events or CDC and update them idempotently, and you can add new read models without touching the write side. Expect lag, and design the UI for it (show "processing…").
**In the interview:** "the admin search page reads from an Elasticsearch read model fed by CDC."

### Outbox pattern — write event to outbox table in same DB transaction as domain change; relay process publishes to MQ
This solves the dual-write problem. In **one local transaction**, update the business tables and insert the event into an `outbox` table. A relay (a polling publisher, or CDC with Debezium) reads the outbox and publishes to Kafka, then marks the rows sent. The event is published if and only if the transaction committed, though possibly more than once, so consumers dedupe.
**In the interview:** essential in any microservices design that publishes events after DB writes.

### Inbox pattern — idempotent consumer with inbox table to deduplicate duplicate deliveries
The consumer side of the outbox. Upon receiving a message, insert its ID into an `inbox` (processed messages) table with a unique constraint **in the same transaction** as the side effect. A duplicate fails the insert and is skipped. Clean up old IDs after the redelivery window.
**In the interview:** "outbox on the producer side, inbox on the consumer side gives effectively-once processing."

### Change Data Capture (CDC) — Debezium reads DB write-ahead log → publishes to Kafka; zero-impact on DB
CDC streams every committed insert, update and delete by tailing the DB's replication log (Postgres WAL through logical decoding, the MySQL binlog), with no triggers and no application changes. Events are ordered per row key. Uses: cache invalidation, search indexing, data warehouse sync, outbox relay, migrating to new services.
**In the interview:** the most reliable way to keep derived systems in sync.

### Saga choreography vs orchestration — choreography: loose coupling, hard to trace; orchestration: central control, easier to monitor
**Choreography**: each service listens and reacts to events. It's decoupled and simple for small flows, but the flow is implicit (event spaghetti) and hard to debug or change. **Orchestration**: a coordinator drives the steps explicitly. The flow is visible, easier to monitor and to handle timeouts and compensations in, with a central component to maintain (Temporal, Camunda).
**In the interview:** choose orchestration for complex or money-related flows.

### Event versioning and upcasting — handle schema changes by transforming old events to new schema on read
Stored events are immutable, but schemas evolve. Options: add only optional fields (compatible changes); version event types (`OrderPlacedV2`); or **upcasters** that transform old event versions into the current shape when reading, so business logic only knows the latest version. Avoid rewriting history in the store.
**In the interview:** shows you've thought about event sourcing past the happy path.

### Temporal coupling problem — synchronous chains; fix with async events to decouple services
With synchronous calls (A → B → C), every service must be **up at the same time** for a request to succeed. Availability multiplies (0.99³ ≈ 0.97), latency adds up, and one slow service cascades. Publishing events and letting downstream services react asynchronously removes the coupling: A succeeds even if C is down, and C catches up later.
**In the interview:** "only the steps the user must wait for are synchronous; the rest are events."
