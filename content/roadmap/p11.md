## Search engine internals

### Web crawler — BFS URL frontier with priority queue; politeness: per-domain rate limit, robots.txt, crawl-delay
Start from seed URLs, fetch pages, extract links, and add new ones to a **frontier**. The frontier is roughly BFS but prioritised by importance and freshness. **Politeness**: one queue per host, so each host is fetched at most every few seconds; obey `robots.txt` and `Crawl-delay`. Distributed fetchers are partitioned by hostname, with DNS caching and timeouts.
**In the interview:** see the Web Crawler case study for the full design.

### URL deduplication — canonical URL normalization + Bloom filter to avoid recrawling
Normalise URLs before checking them: lowercase the scheme and host, remove default ports and fragments, sort query parameters, strip tracking parameters, resolve relative paths, and respect `rel=canonical`. Then check a **bloom filter** (backed by a KV store of URL hashes) to skip ones already seen. Detect duplicate *content* separately with checksums or SimHash.
**In the interview:** "normalise, then a bloom filter, then content fingerprinting."

### Inverted index construction — tokenize → normalize → build term→postings list mapping
For each document: tokenise the text, normalise (lowercase, strip accents, stem, drop stop words), then for each term append `(docID, frequency, positions)` to that term's postings. At scale it's built in batches as sorted segments (map-reduce style) and merged. Lucene writes immutable segments and merges them in the background.
**In the interview:** describe the analyser pipeline briefly.

### Postings list — docID + term frequency + position offsets; sorted by docID for merge operations
Each term's list holds the documents containing it, with term frequency (for scoring) and positions (for phrase and proximity queries). It's sorted by doc ID and compressed (delta encoding plus variable-byte or PForDelta), and AND queries intersect lists with skip pointers. Long lists for common terms are why stop words and early termination matter.
**In the interview:** "a query intersects the sorted postings lists."

### TF-IDF — term frequency (how often term appears in doc) × inverse document frequency (log(N/df))
The score for term t in document d is **TF** (how often t appears in d) × **IDF** = log(N / number of docs containing t). Rare terms ("biryani") get high weight and common ones ("the") almost none. A document's score is summed across query terms. It's simple and intuitive, but long documents are favoured and TF grows unbounded.
**In the interview:** explain the intuition, then say BM25 improves on it.

### BM25 — improved TF-IDF: saturates term frequency, normalizes by document length; default in Elasticsearch
BM25 adds **TF saturation** (the 10th occurrence of a term adds little; parameter k1 ≈ 1.2) and **length normalisation** (a match in a short title counts more than one in a long article; parameter b ≈ 0.75). It's been the default similarity in Lucene and Elasticsearch since 5.0 and is a strong baseline that's still used alongside neural rankers.
**In the interview:** "BM25 for lexical relevance, plus business signals."

### Tokenization — split text on whitespace and punctuation; language-specific tokenizers (ICU, MeCab for Japanese)
Breaking text into terms: on whitespace and punctuation for English, handling emails, URLs and hyphenation. Languages without spaces (Chinese, Japanese, Thai) need dictionary-based tokenisers (MeCab, Kuromoji, ICU). N-gram tokenisers produce substrings, useful for partial and autocomplete matching. The tokeniser choice directly affects recall.
**In the interview:** a quick mention when describing analysers. Hindi and Indic text needs proper tokenisers too.

### Stemming — reduce words to root form (running → run); Porter, Snowball stemmers
Rule-based suffix stripping so "running", "runs" and "runner" become the same term "run", which increases recall. Porter and Snowball are classic algorithms, and aggressive stemmers can conflate unrelated words ("universal" vs "university"). Apply the same analyser at index and query time.
**In the interview:** part of the analyser chain, one line.

### Lemmatization — context-aware stemming (better → good); computationally heavier than stemming
Maps words to their dictionary form using vocabulary and grammar ("better" → "good", "was" → "be"), so it's more accurate than stemming but slower and language-specific. It's common in NLP pipelines, and less common in search engines, which usually stem.
**In the interview:** contrast it with stemming in one line.

### Stop words — filter high-frequency words (the, a, is) to reduce index size
Very common words carry little meaning and create huge postings lists. Removing them shrinks the index and speeds up queries. The risk is breaking phrase queries ("to be or not to be", "The Who"), so modern engines often keep them and rely on BM25's low IDF weight instead.
**In the interview:** mention the trade-off, not just the definition.

### Elasticsearch cluster — master node (cluster state), data nodes (store/query shards), coordinating nodes
**Master-eligible** nodes elect a master that manages cluster state (indices, mappings, shard allocation). Run 3 dedicated masters for quorum. **Data** nodes hold shards and do indexing and search work (often tiered hot/warm/cold). **Coordinating** nodes route requests, scatter queries to shards and merge results. **Ingest** nodes run preprocessing pipelines.
**In the interview:** "3 dedicated masters, data nodes scaled by shard count."

### Elasticsearch shard — Lucene index; primary + replica; max ~50GB per shard for performance
An index is split into **primary shards** (fixed at index creation; changing the count needs split, shrink or reindex), each with **replicas** for HA and read throughput. Each shard is a full Lucene index of segments. Guidance: aim for roughly 10–50 GB per shard and avoid thousands of tiny ones, because each shard costs heap and file handles.
**In the interview:** "size shards to ~30 GB; use rollover for time-based data."

### Elasticsearch queries — match (full-text), term (exact), bool (must/should/must_not/filter), range, fuzzy, phrase, nested
**match**: analysed full-text search. **term**: exact value on keyword fields. **bool**: combines clauses, where `must` and `should` affect scoring, while `filter` and `must_not` don't score and are cacheable. **range**: numbers and dates. **fuzzy**: typo tolerance by edit distance. **match_phrase**: word order matters. **nested**: queries inside arrays of objects.
**In the interview:** "filters in a bool filter context so they're cached and unscored."

### Elasticsearch aggregations — terms (counts), date_histogram, stats, percentiles, nested agg
Analytics over the matching documents. **terms**: top values with counts (facets). **date_histogram**: counts per time bucket. **stats / avg / sum**. **percentiles**: latency p95/p99, using approximate TDigest. **cardinality**: approximate distinct counts, using HyperLogLog. Aggregations can be nested (per category → average price).
**In the interview:** powers facets and dashboards (Kibana).

### Autocomplete — edge n-gram analyzer (index), completion suggester (FST-based, very fast)
**Edge n-grams** index the prefixes of each word ("iph", "ipho", "iphon") so prefix queries are normal term lookups. That's flexible, but the index gets large. The **completion suggester** builds an in-memory FST per shard for extremely fast prefix suggestions with weights, but it's less flexible (prefix only, harder to filter). `search_as_you_type` fields are a middle ground.
**In the interview:** see the typeahead case study for the trie-based alternative.

### Spell correction — edit distance (Levenshtein), phonetic matching (Soundex, Metaphone)
"Did you mean…?" Find dictionary terms within a small **edit distance** (insertions, deletions, substitutions; Elasticsearch fuzzy queries allow up to 2), ranked by term frequency. **Phonetic** algorithms (Soundex, Metaphone) match words that sound alike, which helps with names. Query logs supply common misspelling-to-correction pairs.
**In the interview:** "fuzzy matching with edit distance ≤ 2 plus query-log-based suggestions."

### Faceted search — aggregations + post_filter; show category/price/brand counts alongside results
Show filter options with counts ("Brand: Nike (120), Puma (80)") next to results. Implemented with terms and range aggregations. With multi-select facets, use **post_filter** so selecting "Nike" filters the hits but the brand facet still shows counts for other brands. Facet fields should be `keyword` type with doc values.
**In the interview:** expected in e-commerce search designs.

### Search relevance tuning — field boosting (title^3), function_score (recency), learning to rank
Start with BM25 and boost important fields (`title^3`, `brand^2`). Use **function_score** to blend business signals: recency decay, popularity, rating, stock availability, personalisation. Advanced: **learning to rank**, an ML model trained on click and purchase data, re-ranking the top N results. Evaluate offline (NDCG) and online (A/B tests, CTR).
**In the interview:** "BM25 plus boosts, then an LTR re-ranker trained on clicks."

### Index lifecycle management (ILM) — hot → warm → cold → delete phases for time-series indices
For logs and metrics, write to time-based indices via a **rollover** alias (a new index per day or per 50 GB). ILM policies then move indices through **hot** (fast SSD, indexing), **warm** (read-only, cheaper nodes, force-merged), **cold/frozen** (searchable snapshots on S3), and **delete** after the retention period. It controls cost automatically.
**In the interview:** part of any log-platform design.

## Vector & semantic search

### Dense vector embeddings — neural encoder maps text/image to fixed-dim float vector in semantic space
A model (BERT-style text encoder, CLIP for images) converts content into a fixed-length float vector (e.g. 384–3,072 dimensions) where **semantically similar items are close together** (by cosine or dot product). Embed documents offline, embed the query at search time, and find the nearest vectors.
**In the interview:** the foundation of semantic search, recommendations and RAG.

### Semantic search — find similar meaning, not exact keyword match; handles synonyms, paraphrases
It matches by meaning: "cheap phone with good camera" finds "budget smartphone, excellent photos" even without shared words. It handles synonyms, paraphrases and cross-language queries. Weaknesses: exact identifiers (SKUs, error codes, names) and rare jargon, where keyword search is better. Hence hybrid search.
**In the interview:** know when keyword search beats semantic search.

### Approximate Nearest Neighbor (ANN) — find K most similar vectors without exhaustive search
Exact k-NN compares the query with every vector, O(N·d), which is too slow for millions of vectors. ANN indexes (HNSW graphs, IVF clustering, product quantisation, LSH) return *almost* the best matches (95–99% recall) in milliseconds. Tune the recall vs latency vs memory trade-off.
**In the interview:** "ANN with HNSW, tuned for ~95% recall at under 20 ms."

### HNSW — Hierarchical Navigable Small World: graph-based ANN, O(log N) query, best recall/speed tradeoff
Vectors are nodes in a multi-layer proximity graph. The top layers are sparse long-range "highways" and the bottom layer is dense. A search greedily walks from the top down, getting closer each step: roughly logarithmic time and excellent recall. Parameters: M (links per node), efConstruction and efSearch. It's memory-hungry (vectors plus graph in RAM). Used by Elasticsearch, OpenSearch, pgvector, Qdrant, Weaviate and Milvus.
**In the interview:** the default ANN index to name.

### FAISS — Meta's ANN library: IVF (inverted file index) + PQ (product quantization for compression)
A C++/Python library for vector search at scale, with GPU support. **IVF**: cluster vectors with k-means and only search the nearest clusters (`nprobe`). **PQ**: compress vectors by splitting them into sub-vectors quantised to codebooks, cutting memory 10–50× at some accuracy cost. It also includes HNSW and flat indexes. It's a library, not a database: no replication or CRUD API.
**In the interview:** "IVF-PQ when billions of vectors don't fit in RAM."

### Vector databases — Pinecone, Weaviate, Milvus, Qdrant, pgvector (Postgres extension)
Systems that store vectors with metadata, build ANN indexes, filter by metadata, and handle CRUD, replication and sharding. **Pinecone**: managed. **Weaviate, Milvus, Qdrant**: open source, scalable. **pgvector**: vectors inside Postgres (HNSW/IVF), great when the data is modest and you want joins and transactions. Elasticsearch and OpenSearch also support kNN.
**In the interview:** "pgvector to start, a dedicated vector DB at hundreds of millions of vectors."

### Hybrid search — BM25 keyword + dense vector; combine with Reciprocal Rank Fusion (RRF)
Run lexical (BM25) and semantic (vector) retrieval in parallel, then merge. **RRF** scores each document as Σ 1/(k + rank) across the result lists, which is robust and needs no score calibration. This combines exact-match precision with semantic recall. Supported natively by Elasticsearch, OpenSearch, Weaviate and others.
**In the interview:** the modern best practice for search and RAG retrieval.

### Embedding models — text-embedding-3-small (OpenAI), BERT, BGE, E5, Cohere Embed
Options: API models (OpenAI text-embedding-3-small/large, Cohere Embed, Voyage, Google) or open-source models (BGE, E5, GTE, sentence-transformers), which can be self-hosted. Choose by quality on benchmarks (MTEB), language support (Indic languages), dimension (storage cost), latency and cost, and data-privacy requirements. Re-embed everything if you switch models.
**In the interview:** mention re-embedding cost and versioning embeddings by model.

### RAG (Retrieval-Augmented Generation) — vector search retrieves context, LLM generates answer
Instead of relying on the LLM's memory, **retrieve** relevant chunks from your documents (hybrid search over embedded chunks), put them in the prompt, and have the LLM **generate** a grounded answer with citations. The pipeline: chunking → embedding → indexing → retrieval → (re-ranking) → prompt → generation, plus evaluation and access control on the documents.
**In the interview:** increasingly asked: "design a support chatbot over our docs."

### Re-ranking — cross-encoder (slower, higher quality) re-ranks top-K ANN results for final list
Fast first-stage retrieval (BM25 or ANN) gets the top 100–200 candidates. A **cross-encoder** model then scores each (query, document) pair jointly, which is much more accurate but too slow to run over the whole corpus, and the top results are reordered. Examples: Cohere Rerank, bge-reranker. It significantly improves search and RAG quality.
**In the interview:** "two-stage retrieval: cheap recall, then expensive precision."

## Analytics & data pipelines

### OLTP vs OLAP — row-oriented (many small writes) vs columnar (analytical aggregations)
**OLTP** (Postgres, MySQL, Oracle): many short transactions touching a few rows by key, row-oriented, normalised, millisecond latency. **OLAP** (BigQuery, Snowflake, ClickHouse, Redshift): few huge queries scanning millions or billions of rows over a few columns, columnar, denormalised, seconds of latency. Keep them separate, and feed OLAP from OLTP via CDC or ETL.
**In the interview:** "never run analytics on the production OLTP database."

### Star schema — fact table (events) + dimension tables (who, what, when, where); Kimball model
A central **fact** table holds measurable events (orders, payments) with foreign keys and numeric measures (amount, qty), surrounded by denormalised **dimension** tables (customer, product, merchant, date). It gives simple joins, is BI-friendly and fast for aggregations. Kimball's dimensional modelling is the standard warehouse design.
**In the interview:** "fact_payments with dim_merchant, dim_date, dim_payment_method."

### Snowflake schema — normalized dimensions; reduces redundancy but more JOINs
Dimensions are further normalised into sub-dimensions (product → category → department). It saves storage and keeps dimension updates consistent, at the cost of more joins and more complex queries. Modern columnar warehouses make storage cheap, so star schemas usually win. (Not to be confused with Snowflake the company.)
**In the interview:** contrast it with star in one line.

### Columnar storage — Parquet, ORC: compress and encode columns together; 10–100× faster for analytics
Storing each column contiguously means a query reads only the columns it needs, compresses far better (similar values, dictionary and run-length encoding), and can skip row groups using min/max statistics. **Parquet** is the de facto standard for data lakes, and **ORC** is common in the Hive ecosystem. Result: much less I/O and dramatically faster scans than row formats like CSV or JSON.
**In the interview:** "events stored as partitioned Parquet in S3."

### Data warehouse — Snowflake (cloud-native), BigQuery (serverless), Redshift (columnar, AWS)
Managed analytical databases that separate storage and compute. **Snowflake**: virtual warehouses (independent compute clusters), multi-cloud, data sharing. **BigQuery**: serverless, pay per bytes scanned or reserved slots. **Redshift**: an AWS columnar cluster, with Serverless and Spectrum for S3 data. All use SQL, columnar storage and MPP execution.
**In the interview:** "CDC → warehouse for BI and reporting."

### Data lake — raw files in S3/GCS, queried via Athena/Presto on-demand; flexible but no ACID
Dump raw and semi-structured data cheaply in object storage (JSON, CSV, Parquet, logs, images) with schema-on-read, and query it with Athena, Presto/Trino or Spark. It's flexible and cheap, and good for ML and exploration. Without governance it becomes a "data swamp", and with no ACID guarantees, concurrent writes and updates are painful.
**In the interview:** "a lake for raw data, a warehouse or lakehouse for curated tables."

### Lakehouse — ACID transactions on data lake; Delta Lake, Apache Iceberg, Apache Hudi
Open **table formats** add a transaction log and metadata on top of Parquet files in object storage: ACID commits, schema evolution, time travel, upserts and deletes (useful for GDPR), and efficient pruning. **Delta Lake** (Databricks), **Iceberg** (Netflix, widely adopted across engines) and **Hudi** (Uber, upsert-heavy workloads). You get warehouse reliability at lake cost.
**In the interview:** "Iceberg tables on S3 queried by Spark and Trino."

### Batch processing — Apache Spark: RDD, DataFrame, Spark SQL, lazy evaluation, Catalyst optimizer
Spark processes large datasets in parallel across a cluster, in memory where possible. **RDDs** are the low-level distributed collections. **DataFrames/Spark SQL** are the structured API, optimised by the **Catalyst** query planner and the Tungsten execution engine. Transformations are **lazy**: they build a plan that runs only when an action triggers it. Shuffles (joins, groupBy) are the expensive part.
**In the interview:** "nightly Spark job for reconciliation and reporting."

### Stream processing — Apache Flink: event time vs processing time, watermarks, stateful operators, exactly-once
Flink processes unbounded streams record by record with low latency. It distinguishes **event time** (when it happened) from **processing time** (when it was seen). **Watermarks** track event-time progress so windows can close despite late or out-of-order data. State is fault-tolerant through distributed **checkpoints**, which together with transactional sinks give exactly-once results.
**In the interview:** "Flink for real-time fraud features and windowed aggregates."

### Kafka Streams — lightweight stream processing: stateful with embedded RocksDB, runs inside application
A Java library (no separate cluster) for Kafka-to-Kafka processing: KStream and KTable abstractions, joins, windowed aggregations. State lives in local RocksDB, backed up to compacted changelog topics, so it scales and recovers by running more instances, with exactly-once support. It's simpler to operate than Flink, but tied to Kafka and the JVM.
**In the interview:** good for per-account aggregates inside a microservice.

### Lambda architecture — batch layer (Spark, correctness) + speed layer (Flink, low latency) + serving layer
Run two pipelines over the same data: a **batch layer** that periodically recomputes accurate views over all history, and a **speed layer** for low-latency approximate views of recent data. A **serving layer** merges them. It's robust, but you maintain the same logic twice, which is complex and error-prone.
**In the interview:** know it, and say Kappa is often preferred now.

### Kappa architecture — stream-only using Kafka as event log; reprocess historical data by replaying from offset 0
A single streaming pipeline handles everything. To fix a bug or change logic, deploy a new version of the job that **replays the retained log** from the beginning (or from tiered storage) into a new output table, then switch readers over. There's one codebase, but it needs long Kafka retention and a stream processor with good state management.
**In the interview:** "Kappa with Flink, replaying Kafka for backfills."

### ELT vs ETL — load raw first then transform (ELT with dbt) vs transform before loading (ETL with SSIS/Informatica)
**ETL**: transform in a separate engine before loading curated data into the warehouse (traditional tools: Informatica, SSIS, still common in banks). **ELT**: load raw data first, then transform *inside* the warehouse with SQL (dbt), using its elastic compute. ELT keeps the raw data for reprocessing and is the modern default. ETL is still useful for masking PII before it lands.
**In the interview:** "ELT with dbt models on Snowflake or BigQuery."

### Apache Airflow — workflow orchestration: DAGs, schedulers, workers, metadata DB; define pipelines as code
You define pipelines as Python **DAGs** of tasks with dependencies, schedules, retries and SLAs. The scheduler queues runnable tasks, workers execute them (Celery or Kubernetes executors), and a metadata DB tracks state. There's a UI for monitoring and backfills. Alternatives: Dagster, Prefect, and managed options such as MWAA and Cloud Composer.
**In the interview:** "Airflow orchestrates the nightly extract → transform → reconcile jobs."

### CDC with Debezium — reads DB WAL (binary log) → publishes change events to Kafka; zero impact on source DB
Debezium connectors (on Kafka Connect) tail the Postgres WAL (logical decoding), MySQL binlog, Oracle LogMiner or MongoDB oplog, and emit insert, update and delete events with before/after images, ordered per key. It starts with a consistent snapshot, then streams changes. Load on the source is minimal: it reads the log rather than querying tables.
**In the interview:** "CDC feeds the warehouse, search index and caches without dual writes."

### ClickHouse — columnar OLAP engine, 100–1000× faster than MySQL for aggregations, real-time ingestion
An open-source columnar DBMS optimised for analytical queries: vectorised execution, heavy compression, MergeTree tables with sorting keys and data skipping, materialised views for pre-aggregation, and fast ingestion (including straight from Kafka). It's great for real-time dashboards, product analytics, logs and ad-click aggregation.
**In the interview:** "ClickHouse for sub-second analytics on billions of events."

### Apache Druid — real-time OLAP: ingest from Kafka, sub-second queries, time-series optimized
A distributed analytics database designed for event and time-series data: streaming ingestion from Kafka (queryable immediately), roll-up at ingest time, columnar segments with bitmap indexes, and sub-second slice-and-dice queries at high concurrency. Used for user-facing analytics dashboards. **Apache Pinot** (LinkedIn) is similar.
**In the interview:** an alternative to ClickHouse for high-concurrency, user-facing analytics.

### Presto / Trino — federated SQL query engine: query S3, Hive, Cassandra, MySQL with single SQL
A distributed MPP SQL engine with no storage of its own: connectors query data where it lives (S3 Parquet/Iceberg via Hive or Glue catalogs, MySQL, Postgres, Kafka, Elasticsearch, Cassandra) and can **join across sources** in one query. Trino is the community fork of Presto, and AWS Athena is Presto/Trino as a service.
**In the interview:** "Trino over the Iceberg lake for ad-hoc analysis."

## Real-time systems

### WebSocket upgrade — HTTP Upgrade header (101 Switching Protocols), then full-duplex ws:// protocol
The client sends a GET with `Upgrade: websocket`, `Connection: Upgrade` and a `Sec-WebSocket-Key`. The server answers **101 Switching Protocols** with `Sec-WebSocket-Accept`. From then on the TCP connection carries framed messages in both directions (text or binary, plus ping/pong and close frames). `wss://` runs over TLS, and load balancers must support upgrades and long-lived connections.
**In the interview:** quick protocol detail when designing chat.

### WebSocket scalability — fan-out via Redis Pub/Sub across multiple WebSocket server instances
Each gateway server holds a subset of connections. To deliver a message to user X, look up which gateway holds X (a Redis registry), then publish to that gateway's channel through Redis pub/sub, NATS or Kafka. For rooms or groups, gateways subscribe to the room channels of their connected users. Scale gateways horizontally, use heartbeats, and drain connections on deploy.
**In the interview:** "a connection registry plus pub/sub between gateways."

### Server-Sent Events — HTTP streaming, server pushes events, client auto-reconnects; simpler than WebSocket
A one-way stream over a normal HTTP response (`text/event-stream`). The browser's EventSource reconnects automatically and resumes from `Last-Event-ID`. It works through proxies and HTTP/2 (multiplexed, so no 6-connection limit), and suits notifications, live scores, dashboards and streaming LLM output.
**In the interview:** choose it over WebSockets when only the server pushes.

### Long polling — client holds connection (30s timeout) until event; reconnects immediately after response
The client asks, and the server holds the request open until data arrives or about 30 seconds pass, then the client immediately asks again. It's near-real-time over plain HTTP, but has overhead per message (a new request each time), and each waiting client ties up a connection. It's a fallback when WebSockets or SSE aren't available.
**In the interview:** "long polling as the fallback transport."

### Real-time presence system — heartbeat every 30s with TTL=60s in Redis; expire = offline; publish change via Pub/Sub
Clients send a heartbeat every ~30 s that sets `presence:{user}` with a ~60 s TTL. If the key expires, the user is offline, and keyspace notifications or a sweeper publish "went offline". Publish changes only to interested viewers (open chats or contacts on screen), not to everyone, to avoid huge fan-out. "Last seen" is the timestamp of the last heartbeat.
**In the interview:** the presence component of the WhatsApp design.

### Live leaderboard — Redis sorted set: ZADD adds score, ZRANGE gets rank, ZRANK gets position; push via WebSocket
`ZINCRBY lb:game1 50 user42` updates a score. `ZREVRANGE lb:game1 0 9 WITHSCORES` gives the top 10, and `ZREVRANK lb:game1 user42` gives a user's rank, all O(log N). Push top-N changes to clients over WebSockets or SSE, throttled (e.g. once a second). For huge leaderboards, shard by region and merge, or approximate ranks for low scorers.
**In the interview:** the canonical sorted-set use case.

### Real-time collaborative editing — OT (Operational Transformation, Google Docs) vs CRDT (conflict-free, Figma, Notion)
Several users edit the same document at once. **OT**: a central server transforms concurrent operations against each other (insert at position 5 is shifted by a concurrent insert at 3), which works well with a server, as in Google Docs. **CRDTs** (Yjs, Automerge): every character or element has a unique ID, so replicas merge in any order without a central authority, which suits offline and peer-to-peer editing. Both use WebSockets to distribute operations, plus presence cursors.
**In the interview:** a "design Google Docs" follow-up. Name both approaches.

### Online gaming — authoritative server model, UDP for state updates, client-side prediction + reconciliation
The **server is authoritative**: clients send inputs, not results, which prevents cheating. State updates go over **UDP** (or QUIC) at a fixed tick rate, because late packets are useless. **Client-side prediction** applies inputs immediately for responsiveness, and **server reconciliation** corrects the client when the authoritative state differs. Interpolation smooths other players' movement, and lag compensation handles hit detection. Matchmaking places players on regional servers.
**In the interview:** niche, but a good real-time design topic.

### Real-time location tracking — GPS → WebSocket → geospatial index (Redis GEO or Quadtree) → nearby query
Devices send GPS every few seconds over a persistent connection. The latest position updates an in-memory geo index (Redis GEOADD or H3 cells) with a TTL, and history is streamed to Kafka. Viewers subscribe to specific entities (a rider watching their driver) and receive throttled updates. Nearby queries search the cell and its neighbours.
**In the interview:** see the Uber case study.

### Live streaming — RTMP ingest → transcode (FFmpeg) → HLS segmentation → CDN origin → edge → viewer
The broadcaster pushes over RTMP or SRT (or WebRTC) to an ingest server. A transcoder produces multiple bitrates in real time, a packager cuts them into short HLS/DASH segments plus manifests, and the CDN distributes them to viewers. Latency: standard HLS is 10–30 s, Low-Latency HLS/DASH is 2–5 s, and WebRTC is under 1 s for interactive use. Chat and reactions run on a separate real-time channel.
**In the interview:** "design Twitch / Hotstar live": ingest, transcode, package, CDN.

### Adaptive bitrate streaming — HLS/DASH: multiple quality levels; client switches based on bandwidth
Video is encoded at several bitrates (a ladder, 240p–4K) and split into 2–10 s segments listed in manifests. The player measures throughput and buffer level and requests the next segment at the best sustainable quality, switching down instead of stalling. Segments are static files, so they're perfectly CDN-cacheable.
**In the interview:** see the YouTube/Netflix case study.

### Real-time counters at scale — Redis INCR + async batch flush to DB every N seconds; eventual consistency
Updating a DB row per view or like at 100K/s creates a hot-row bottleneck. Instead, `INCR` in Redis (sharded keys for viral items), and a job flushes aggregated deltas to the DB every few seconds. Alternatively, aggregate events from Kafka in a stream processor. Display counts may lag slightly, and exact or billed counts get reconciled offline.
**In the interview:** "Redis counters with periodic flush; approximate display, exact billing."
