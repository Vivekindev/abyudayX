## ACID & transactions

### Atomicity — all operations in a transaction succeed or all roll back
A transaction is all-or-nothing. In a transfer that debits A and credits B, a crash after the debit rolls the debit back, so money never disappears halfway. The DB uses its undo/redo logs to reverse partial work.
**In the interview:** this is why money movement belongs in one DB transaction, and why spreading it across services needs a saga with compensations.

### Consistency — DB moves from one valid state to another, constraints always satisfied
Every committed transaction leaves the data satisfying all rules: primary/foreign keys, `UNIQUE`, `CHECK (balance >= 0)`, NOT NULL. A transaction that would break a rule is rejected. (The "C" in ACID is different from the "C" in CAP, which is about replicas agreeing.)
**In the interview:** push critical rules into DB constraints, like a unique idempotency key or a unique seat booking. They're your last line of defence against races.

### Isolation — concurrent transactions don't see each other's intermediate state
Concurrent transactions should behave as if they ran one at a time. How fully that holds depends on the **isolation level**. Weaker levels allow anomalies (dirty, non-repeatable and phantom reads, lost updates, write skew) in exchange for more concurrency.
**In the interview:** know which anomaly each level allows, and which one your design is exposed to.

### Durability — committed data survives crashes (WAL-based)
Once COMMIT returns, the change survives power loss. The DB first appends it to the **write-ahead log** and fsyncs it to disk, applying it to data pages later. After a crash it replays the WAL. Replication to other nodes adds protection against losing the disk itself.
**In the interview:** `fsync` costs latency. Group commit and async replication trade a little durability for speed.

### BEGIN, COMMIT, ROLLBACK, SAVEPOINT — transaction control
`BEGIN` starts a transaction, `COMMIT` makes its changes permanent and visible, and `ROLLBACK` discards them. `SAVEPOINT sp1` marks a point you can `ROLLBACK TO sp1` without abandoning the whole transaction. In Spring, `@Transactional` wraps these for you; watch propagation settings and self-invocation pitfalls.
**In the interview:** keep transactions **short**. Never make a network call (to a PSP or another service) while holding locks.

### Read Uncommitted — dirty reads allowed, fastest but rarely useful
The weakest level: you can see other transactions' uncommitted changes, which might be rolled back. Postgres doesn't even implement it (it behaves as Read Committed). It's almost never the right choice.
**In the interview:** mention it only to complete the list.

### Read Committed — no dirty reads, default in PostgreSQL and Oracle
Each **statement** sees only data committed before that statement began. You never see uncommitted data, but two reads in the same transaction can return different values, and lost updates are possible with read-modify-write in application code.
**In the interview:** it's the default in Postgres and Oracle. Protect read-modify-write with `SELECT … FOR UPDATE`, version columns, or atomic `SET x = x + 1`.

### Repeatable Read — same row read twice gives same result within transaction (MySQL default)
The whole transaction reads from **one snapshot** taken at its start, so rows you've read don't change under you. In Postgres it's true snapshot isolation (it also detects concurrent updates to the same row and aborts one). MySQL InnoDB uses gap/next-key locks for locking reads to block most phantoms. Write skew is still possible.
**In the interview:** the MySQL default. Good for consistent reports within a transaction.

### Serializable — strictest, prevents all anomalies including phantoms (SSI in PostgreSQL)
The result is guaranteed equivalent to running transactions one after another. Postgres implements it with **Serializable Snapshot Isolation**: it tracks read/write dependencies and **aborts** a transaction that would break serializability, so your code **must retry** on serialization failures. MySQL uses locking instead.
**In the interview:** use it for complex invariants (write skew) with retry logic, or prefer explicit locks on the specific rows involved.

### Dirty read — reading uncommitted data from a concurrent transaction
T1 updates a balance to ₹0 but hasn't committed, T2 reads ₹0 and declines a payment, then T1 rolls back. T2 acted on data that never existed. Every level from Read Committed up prevents this.
**In the interview:** a quick definition is enough.

### Non-repeatable read — same row returns different value on second read in same transaction
T1 reads a product's price (₹100), T2 updates it to ₹120 and commits, and T1 reads it again and gets ₹120. Inside one transaction the "same" data changed. This happens under Read Committed, and Repeatable Read prevents it.
**In the interview:** relevant for multi-step logic like "check the price, then compute the invoice" inside one transaction.

### Phantom read — same range query returns different set of rows in same transaction
T1 runs `SELECT COUNT(*) FROM bookings WHERE slot='7pm'` and gets 9. T2 inserts a booking and commits. T1 counts again and gets 10: a **new row** appeared. It's about rows matching a condition, not changes to existing rows. Serializable (or predicate/gap locks) prevents it.
**In the interview:** "max 10 bookings per slot" rules are vulnerable. Lock a parent row (the slot) or use Serializable.

### Lost update — two transactions read-modify-write the same row, one overwrites the other
Both read `stock = 5`, both compute 4 in app code, both write 4. Two items sold, stock dropped by 1. The fixes: an atomic update (`SET stock = stock - 1 WHERE stock > 0`), `SELECT … FOR UPDATE`, or **optimistic locking** with a version column.
**In the interview:** the most common real-world concurrency bug. Name it and the three fixes.

### Write skew — two transactions read overlapping data and make conflicting writes (e.g., on-call scheduling)
Rule: at least 1 doctor on call. Alice and Bob are both on call. Each, concurrently, checks "2 on call, OK for me to leave" and updates **their own** row. Both leave and the rule is broken. There's no row-level conflict, so snapshot isolation misses it. Fixes: Serializable, or `SELECT … FOR UPDATE` on all the rows the decision depends on, or materialise the constraint into one lockable row.
**In the interview:** naming write skew separates strong candidates from the rest.

## Locking & concurrency control

### Shared lock (S) — multiple readers can hold simultaneously
A read lock. Many transactions can hold S locks on the same row at once, but nobody can take an exclusive lock while they do. In SQL: `SELECT … FOR SHARE`. MVCC databases rarely need S locks for plain reads.
**In the interview:** used when you must make sure a row doesn't change while you depend on it (e.g. a parent row that mustn't be deleted).

### Exclusive lock (X) — single writer holds, blocks all readers and writers
A write lock: one holder at a time. It's taken automatically by UPDATE/DELETE, or explicitly with `SELECT … FOR UPDATE`. Other writers (and locking readers) wait until commit. Under MVCC, plain non-locking reads still see the old version without waiting.
**In the interview:** the basis of pessimistic locking for bookings and balances.

### Intention locks (IS, IX, SIX) — hierarchical locking for efficiency
Before locking a row, a transaction places an **intention** lock on the table: IS ("I'll take S locks on some rows"), IX ("I'll take X locks on some rows"), SIX (S on the whole table plus X on some rows). Then someone wanting a full-table lock can check one table-level lock instead of scanning every row lock. InnoDB uses these internally.
**In the interview:** rarely asked at SDE-2. Knowing the purpose (cheap conflict checks at the table level) is enough.

### Two-Phase Locking (2PL) — growing phase (acquire only), shrinking phase (release only)
The classic way to guarantee serializability with locks: a transaction **acquires** locks (growing phase) and, once it releases any lock, **never acquires another** (shrinking phase). It's correct but limits concurrency and can deadlock. (Don't confuse it with two-phase **commit** across databases.)
**In the interview:** say "2PL is locking for serializability; 2PC is atomic commit across nodes." Mixing them up is a common slip.

### Strict 2PL — hold all exclusive locks until commit/abort (prevents cascading aborts)
A variant that holds all write locks until the transaction ends. Nobody can read your uncommitted writes, so one abort never forces others to abort (no cascading aborts). Most lock-based databases behave this way: row locks taken by UPDATE are held until COMMIT.
**In the interview:** it explains why long transactions block others. Locks live until commit.

### Deadlock — circular wait: T1 holds A waits B, T2 holds B waits A
Two (or more) transactions each hold a lock the other needs, so neither can proceed. The classic case: two transfers A→B and B→A, each locking its source account first. Databases detect this and kill one transaction, which the app must retry.
**In the interview:** expect "how do you avoid deadlocks in a money-transfer service?" Lock ordering is the answer.

### Deadlock detection — wait-for graph cycle detection
The DB keeps a graph of who's waiting for whom. A **cycle** means deadlock, so it aborts a victim (Postgres checks after `deadlock_timeout`, about 1 s by default; InnoDB detects immediately). The victim gets an error such as "deadlock detected" or SQLSTATE 40P01.
**In the interview:** "the DB breaks it, and our code catches the error and retries with backoff."

### Deadlock prevention — lock ordering (always acquire in same order), timeout + retry
Prevent the cycle in the first place. Always lock resources in a **consistent global order** (e.g. sort account IDs ascending and lock the lower one first). Keep transactions short and touch rows in the same order. Add `lock_timeout` so waits don't hang forever, and retry.
**In the interview:** for transfers, `SELECT … WHERE id IN (a, b) ORDER BY id FOR UPDATE`.

### Deadlock resolution — abort the youngest transaction (wound-wait scheme)
When a deadlock happens, pick a **victim**, usually the transaction that has done the least work or is youngest. **Wound-wait**: an older transaction "wounds" (aborts) a younger one holding a lock it needs, while a younger one waits for an older one. **Wait-die** is the mirror image. Both use timestamps, so the system always makes progress and nobody starves.
**In the interview:** knowing that "the DB aborts one transaction and the app retries" is sufficient.

### MVCC — Multi-Version Concurrency Control: readers don't block writers, writers don't block readers
Updates create a **new version** of a row instead of overwriting it. Each transaction reads the versions visible to its snapshot. Readers never wait for writers (they read the older version), and writers never wait for readers. Old versions are cleaned up later. Used by Postgres, MySQL InnoDB, Oracle and CockroachDB.
**In the interview:** it's why plain SELECTs don't block in modern databases, and why long-running transactions cause bloat.

### MVCC in PostgreSQL — each row has xmin/xmax visibility markers
Each row version (tuple) stores **xmin** (the transaction that created it) and **xmax** (the transaction that deleted or replaced it). A snapshot decides visibility: a version is visible if xmin committed before the snapshot and xmax didn't. An UPDATE writes a new tuple and sets xmax on the old one, so dead tuples pile up until **VACUUM** reclaims them.
**In the interview:** heavily updated tables need autovacuum tuning, or they bloat and slow down.

### Optimistic locking — read with version, update with WHERE version=N, check affected rows
No locks are held while the user thinks. Read the row with `version = 7`, then `UPDATE … SET …, version = 8 WHERE id = ? AND version = 7`. If **0 rows** were updated, someone else changed it, so retry or report a conflict (HTTP 409). JPA's `@Version` does this automatically.
**In the interview:** best when conflicts are rare (profile edits, admin forms). Under heavy contention it causes retry storms.

### Pessimistic locking — SELECT FOR UPDATE (acquires row-level lock)
Lock first, then work: `SELECT * FROM seats WHERE id = 7 FOR UPDATE` takes an exclusive row lock until commit, and concurrent transactions wait. It's simple and correct under **high contention** (the last seat, flash-sale stock, wallet balance). Keep the transaction short, add `NOWAIT` or `lock_timeout` to fail fast instead of queueing.
**In the interview:** the standard answer for "prevent double booking".

### SELECT FOR UPDATE SKIP LOCKED — queue-like pattern for job workers
`SELECT * FROM jobs WHERE status = 'PENDING' ORDER BY created_at LIMIT 10 FOR UPDATE SKIP LOCKED` lets each worker grab rows **no other worker has locked**, without waiting. Many workers can pull from one table like a queue, with no duplicates and no blocking. Mark rows processing or done in the same transaction.
**In the interview:** a great answer for "job scheduler on Postgres" or "outbox relay with several workers".

### Predicate locks — Serializable Snapshot Isolation (SSI) in PostgreSQL 9.1+
Under SERIALIZABLE, Postgres records which **ranges** (predicates) each transaction read, using SIRead locks that block nobody. If another transaction writes into a range you read, and that creates a dangerous dependency cycle, one transaction is aborted at commit. That's how SSI catches phantoms and write skew without blocking.
**In the interview:** "Serializable in Postgres is optimistic: expect serialization failures and retry."

## Indexing & query optimization

### B+ tree index — leaf nodes contain data/row pointers linked in sorted order, O(log N) seek + range
The default index in almost every relational DB. It's a balanced tree of pages with hundreds of keys per node, so a billion rows need only 3–4 levels. Leaves hold the keys (plus row pointers or the row itself) and are **linked in order**, so range scans and ORDER BY walk the leaves sequentially.
**In the interview:** it supports equality, range, prefix and sort. The default answer to "how do you make this query fast?"

### Hash index — O(1) exact match, no range queries, used in Hash join, pg_trgm GIN
A hash index maps `hash(key)` to row locations: O(1) for **equality only**, with no ranges, no sorting and no prefix search. Postgres supports them, but B-trees are usually close enough in speed. Hashing shows up more in **hash joins** (the planner builds an in-memory hash table of one side) and in key-value stores. Text search uses other structures (GIN, trigrams).
**In the interview:** "a hash index only helps equality lookups, so a B-tree is the safe default."

### Composite index — column order matters: WHERE a=1 AND b=2 uses (a,b) but not (b,a) for a-only query
An index on `(a, b, c)` is sorted by a, then b, then c. It serves filters on the **leftmost prefix**: `a`, `a,b`, `a,b,c`, plus `ORDER BY` in that order. It can't efficiently serve a query on `b` alone. Put equality columns first and range/sort columns last: `(user_id, created_at)` for "latest orders of a user".
**In the interview:** one well-designed composite index often replaces several single-column ones.

### Covering index — index includes all queried columns, avoids table heap lookup (index-only scan)
If the index contains every column the query needs, the DB answers from the index alone with no trip to the table rows (an **index-only scan**). Postgres: `CREATE INDEX … (user_id, created_at) INCLUDE (amount, status)`. In InnoDB, secondary indexes implicitly contain the primary key.
**In the interview:** a big win for hot read queries, at the cost of a bigger index and slower writes.

### Partial index — index on subset of rows with WHERE clause (e.g. WHERE status='active')
`CREATE INDEX ON orders (created_at) WHERE status = 'PENDING'` indexes only the rows you query often. It's tiny and fast, and cheap to maintain. It can also enforce conditional uniqueness: `UNIQUE (user_id) WHERE active`.
**In the interview:** perfect for "find pending jobs" or "active subscriptions" when those are a small fraction of the table.

### Expression / functional index — index on LOWER(email), EXTRACT(year FROM created_at)
Index the **result of an expression**, so queries that use the same expression can use it: `CREATE INDEX ON users (LOWER(email))` serves `WHERE LOWER(email) = ?`. Without it, wrapping a column in a function prevents a normal index from being used.
**In the interview:** case-insensitive login lookups are the classic example.

### Index selectivity — high cardinality = high selectivity = more useful index
Selectivity is the fraction of rows a condition returns. An index on `email` (unique) is extremely selective. An index on `is_active` (two values, 90% true) is nearly useless, because the planner prefers a full scan when a condition matches a large share of the table. Low-cardinality columns help only inside composite or partial indexes.
**In the interview:** say why you'd **not** index something. It shows judgement.

### Clustered index (InnoDB) vs heap storage (PostgreSQL) — physical row ordering differs
**InnoDB** stores rows *inside* the primary-key B+ tree (a clustered index), so PK range scans are fast and secondary indexes point to the PK, which means a second lookup. Random PKs (UUIDv4) cause page splits. **Postgres** stores rows in an unordered **heap**, and every index, including the PK, points to a tuple location.
**In the interview:** prefer sequential or time-ordered PKs (BIGINT identity, Snowflake, UUIDv7), especially on MySQL.

### EXPLAIN / EXPLAIN ANALYZE — read execution plans: seq scan vs index scan vs bitmap
`EXPLAIN` shows the planner's plan, and `EXPLAIN ANALYZE` actually runs the query and shows real row counts and timings. Look for: a **Seq Scan** on a big table with a selective filter (a missing index), Index Scan / **Index Only Scan** (good), **Bitmap** Heap Scan (many matching rows gathered efficiently), expensive Sorts and Nested Loops over large inputs, and big gaps between estimated and actual rows (stale statistics).
**In the interview:** "I'd check the plan with EXPLAIN ANALYZE before adding indexes."

### Query planner statistics — ANALYZE command, pg_statistic, histograms
The planner estimates row counts from **statistics**: the number of distinct values, most-common values and **histograms** per column, collected by `ANALYZE` (autovacuum runs it too) and stored in `pg_statistic`. Bad statistics lead to bad plans, such as a nested loop over millions of rows. After a bulk load, run ANALYZE. For correlated columns, use extended statistics.
**In the interview:** a sudden slow query after a data change is often a statistics problem.

### N+1 query problem — fetch N parents then 1 query per parent; fix with JOIN or DataLoader batching
Load 100 orders (1 query), then each order's customer separately (100 queries). It's common with ORMs and lazy loading. Fixes: a **JOIN**, **eager fetching** (`JOIN FETCH` / `@EntityGraph` in JPA), batch fetching (`WHERE id IN (...)`), or DataLoader in GraphQL. Detect it with SQL logging or APM traces showing many repeated queries.
**In the interview:** a classic Java/Hibernate question at banks.

### JOIN types — INNER, LEFT OUTER, RIGHT OUTER, FULL OUTER, CROSS, SELF JOIN
**INNER**: only rows matching on both sides. **LEFT**: every left row, with NULLs where there's no match ("customers and their orders, including customers with none"). **RIGHT**: the mirror of LEFT. **FULL**: all rows from both sides. **CROSS**: every combination (a Cartesian product). **SELF**: a table joined to itself (employee → manager). Joins run as nested loops, hash joins or merge joins.
**In the interview:** be ready to write a LEFT JOIN with a GROUP BY in SQL rounds.

### Window functions — ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, SUM/AVG OVER PARTITION
These compute across related rows **without collapsing them**: `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC)` gives "latest order per user". RANK leaves gaps after ties and DENSE_RANK doesn't. LAG/LEAD reach the previous or next row (day-over-day change). `SUM(amount) OVER (ORDER BY day)` gives a running total.
**In the interview:** they come up often in SQL rounds ("top 3 salaries per department", "second-highest").

### CTEs (Common Table Expressions) — WITH clause, readability, recursive CTEs for tree traversal
`WITH recent AS (SELECT …) SELECT … FROM recent` names subqueries so complex SQL becomes readable. **Recursive CTEs** walk hierarchies: org charts, category trees, graph paths (`WITH RECURSIVE … UNION ALL …`). In Postgres 12+, CTEs are inlined unless you mark them MATERIALIZED.
**In the interview:** "fetch a category and all its subcategories" means a recursive CTE.

### Lateral joins — correlated subquery in FROM clause, row-by-row evaluation
`LATERAL` lets a subquery in FROM refer to columns of tables listed before it, so it runs per row. It's ideal for "**top N per group**": `FROM users u, LATERAL (SELECT * FROM orders o WHERE o.user_id = u.id ORDER BY created_at DESC LIMIT 3) x`. With an index on `(user_id, created_at)` it's very efficient.
**In the interview:** niche. A window function also solves top-N per group.

## Schema design & operations

### 1NF — atomic values, no repeating groups
Each column holds one value per row, with no comma-separated lists and no `phone1, phone2, phone3` columns. Repeating data moves to its own table (`user_phones`). (Modern Postgres arrays and JSONB knowingly bend this rule when that's useful.)
**In the interview:** "a comma-separated list in a column" is the canonical bad design.

### 2NF — full functional dependency on entire primary key (no partial dependency)
With a composite key, every non-key column must depend on the **whole** key. In `order_items (order_id, product_id, product_name, qty)`, `product_name` depends only on product_id, so it belongs in `products`. Otherwise updating a product name means touching many rows (an update anomaly).
**In the interview:** rarely asked directly. Know that normalisation removes update anomalies.

### 3NF — no transitive dependency (non-key → non-key)
Non-key columns depend only on the key, not on other non-key columns. In `employees (id, dept_id, dept_name)`, `dept_name` depends on dept_id, so move it to `departments`. 3NF is the usual target for transactional (OLTP) schemas.
**In the interview:** "normalised to 3NF for writes, denormalised read models where needed."

### BCNF — every determinant is a candidate key
A stricter 3NF: for every functional dependency X → Y, X must be a candidate key. It matters only in unusual schemas with overlapping candidate keys. Most 3NF schemas are already in BCNF.
**In the interview:** niche. A one-line definition is plenty.

### Denormalization — intentional redundancy to speed up reads, accept write overhead
Store data redundantly to avoid expensive joins: keep `author_name` on posts, store a `comment_count` on the post, precompute feeds. Reads get faster and simpler, but writes must update every copy (sync, triggers, events) and copies can drift. NoSQL modelling is denormalised by design.
**In the interview:** justify it by read:write ratio, and say how the copies stay consistent (transaction, CDC, async job).

### Online schema changes — gh-ost (GitHub), pt-online-schema-change (Percona), pg_repack
`ALTER TABLE` on a huge MySQL table can lock it for hours. **gh-ost** and **pt-osc** create a shadow table with the new schema, copy rows in chunks while capturing ongoing changes (gh-ost reads the binlog, pt-osc uses triggers), then atomically swap tables. Postgres can do many changes instantly (adding a nullable column, `CREATE INDEX CONCURRENTLY`), and **pg_repack** rebuilds bloated tables online.
**In the interview:** "migrations must not lock hot tables. Use online tools plus expand-contract."

### Expand-contract pattern — add new column nullable → backfill → add constraint → drop old
A zero-downtime way to change schemas while old and new code run side by side. **Expand**: add the new column or table (nullable) and deploy code that writes both. **Backfill** old rows in batches. Switch reads to the new column. Add constraints. **Contract**: stop writing the old column, then drop it in a later release.
**In the interview:** every step stays compatible with the version of the code currently running.

### Connection pooling — PgBouncer (transaction mode), HikariCP (JVM), Sequelize pool (Node)
Opening a DB connection is expensive (TCP + TLS + auth + a backend process: in Postgres, one OS process per connection, roughly 10 MB each). A pool keeps connections open and lends them out. **HikariCP** is the standard in Spring Boot. **PgBouncer** in *transaction mode* lets thousands of app connections share a few hundred DB connections (session-level features like prepared statements need care).
**In the interview:** with 100 pods × 20 connections = 2,000 connections, a Postgres server would choke, so put PgBouncer or RDS Proxy in front.

### PostgreSQL-specific — VACUUM, autovacuum, TOAST (for large values), pg_stat_activity
**VACUUM** reclaims dead MVCC tuples and prevents transaction-ID wraparound. **Autovacuum** does it automatically, and busy tables need tuning. **TOAST** stores large values (big text or JSONB over ~2 KB) out of line, compressed. **pg_stat_activity** shows running queries, waits and locks, which is your first stop in an incident. Long-open transactions block vacuum and cause bloat.
**In the interview:** shows you've actually operated Postgres.

### JSONB in PostgreSQL — binary JSON, GIN indexable, operators @>, ?, #>>
JSONB stores parsed binary JSON. You can query inside it: `data @> '{"brand":"Nike"}'` (contains), `data ? 'size'` (key exists), `data #>> '{address,city}'` (extract as text). A **GIN index** makes containment queries fast, and expression indexes target specific keys. It gives you a document store inside a relational database.
**In the interview:** "flexible product attributes in JSONB" is a good alternative to adding MongoDB.

### Full-text search in PostgreSQL — tsvector, tsquery, GIN index, ts_rank
`to_tsvector('english', body)` tokenises and stems text into lexemes, and `to_tsquery('running & shoes')` builds a query. Matching uses `@@`, a **GIN** index on the tsvector makes it fast, and `ts_rank` orders results by relevance. It handles moderate search needs without running Elasticsearch, but has weaker relevance tuning, facets and scale.
**In the interview:** "Postgres FTS to start, Elasticsearch when search becomes a core feature."

### Write-Ahead Log (WAL) — every change written to log before applied, enables crash recovery and replication
Every change is appended to a sequential log and flushed **before** the data pages are modified. After a crash the DB replays the WAL from the last checkpoint. The same log stream feeds **replication** (replicas replay it) and **CDC** (Debezium reads it via logical decoding). MySQL's equivalents are the redo log and the binlog.
**In the interview:** WAL comes up in durability, replication, CDC and outbox discussions.

### Checkpointing — periodically flush dirty pages to disk, bound WAL replay on restart
Modified pages live in memory (the buffer pool) and are written to disk lazily. A **checkpoint** forces dirty pages to disk and records a position in the WAL, so recovery only needs to replay WAL written after it, which bounds restart time. Checkpoints that are too frequent cause I/O spikes; too rare means slow recovery.
**In the interview:** niche. Pairs with the WAL explanation.
