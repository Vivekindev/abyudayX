## Service architecture & DDD

### Monolith — single deployable unit; simple to start, becomes bottleneck as team grows
All features live in one codebase, built and deployed as one unit, usually with one database. In-process calls are fast, transactions are easy, and debugging and deploying are simple. Pain arrives with scale: large teams stepping on each other, slow builds, risky deploys, and having to scale the whole app for one hot feature.
**In the interview:** a monolith is a valid start. Don't apologise for it, justify it.

### Modular monolith — well-structured monolith with clear module boundaries; intermediate step
One deployable, but internally split into modules with explicit interfaces and no reaching into each other's tables (enforced with packages, ArchUnit or Spring Modulith). You keep monolith simplicity and get clean boundaries, so extracting a module into a service later is easy.
**In the interview:** often the best recommendation for teams under ~30 engineers.

### Microservices — small, independently deployable services; each owns its data and API
The system is split by business capability into services, each with its own codebase, database and deploy pipeline, owned by one team, communicating over APIs or events. You get independent deployment and scaling, team autonomy, technology freedom and fault isolation.
**In the interview:** define them by **independence** (deploy, data, team), not by size.

### Microservices trade-offs — independent scaling, independent deploy, team autonomy vs network latency, distributed transactions, operational complexity
**Gains**: scale hot services alone, deploy without coordinating, smaller codebases, isolated failures. **Costs**: network latency and partial failures, distributed transactions (sagas), eventual consistency, much more infrastructure (service discovery, tracing, CI/CD per service), harder local testing, and data duplication.
**In the interview:** name both columns, then choose based on team size and scale.

### Domain-Driven Design (DDD) — model software around business domain
An approach where software structure mirrors the business domain, built in close collaboration with domain experts. **Strategic DDD** covers bounded contexts and context maps (where the boundaries go). **Tactical DDD** covers entities, value objects, aggregates, domain events, repositories and services (how to model inside a boundary).
**In the interview:** use DDD vocabulary to justify how you split services.

### Bounded context — explicit boundary within which a domain model applies (defines service boundary)
Inside a bounded context, each term has one precise meaning. "Account" in Payments (balance, limits) is different from "Account" in Identity (login, MFA), so each context keeps its own model. Bounded contexts are the natural candidates for microservice and team boundaries.
**In the interview:** "I'd split by bounded context: Payments, Ledger, Identity, Notifications."

### Aggregate root — consistency boundary: all changes go through root entity
An aggregate is a cluster of objects that must stay consistent together (an Order with its OrderLines). Outsiders reference and modify it **only through the root** (`order.addLine()`), which enforces invariants. **One transaction modifies one aggregate.** Across aggregates you rely on eventual consistency via domain events. Keep aggregates small.
**In the interview:** "transaction boundaries = aggregate boundaries" sounds senior.

### Domain events — things that happened in the domain; trigger side effects in other bounded contexts
Past-tense facts about the business: `PaymentAuthorized`, `OrderShipped`, `AccountFrozen`. They're raised by aggregates and published (via an outbox) so other contexts can react without the publisher knowing them. Events carry the needed data, an ID and a timestamp, and are immutable.
**In the interview:** the integration mechanism between bounded contexts.

### Ubiquitous language — shared vocabulary between engineers and domain experts within bounded context
Code, conversations and docs use the **same** business terms ("authorization", "capture", "settlement", "chargeback"), with no translation layer between what the business says and what the code says. This reduces misunderstandings, and class and method names reflect the domain.
**In the interview:** in fintech designs, using correct payment terms is itself a signal.

### Strangler fig pattern — incrementally migrate monolith: route traffic to new service, deprecate old endpoint
Replace a legacy system piece by piece: put a proxy or gateway in front, build one capability as a new service, route that traffic to it, and repeat until the old system can be retired. It's lower risk than a big-bang rewrite, and every step ships value. It needs data synchronisation (CDC) during the transition.
**In the interview:** the standard answer for "how would you migrate our monolith?"

### Anti-corruption layer — translation layer between old and new domain models
A boundary component that translates between your clean model and a legacy or external system's model (an old core-banking API, a partner's format), so their concepts don't leak into your code. It's implemented with adapters, facades and translators.
**In the interview:** essential when integrating with legacy bank systems or third-party PSPs.

### Shared kernel — small, carefully managed shared domain model between two contexts
Two teams deliberately share a small piece of model or code (e.g. a `Money` value type, common identifiers) and agree to change it only jointly. It reduces duplication but couples the teams, so keep it tiny.
**In the interview:** niche. A one-line definition is enough.

### Database per service — each service owns its DB; prevents tight coupling through shared schema
Only the owning service reads or writes its tables, and others go through its API or events. Each service can then change its schema and pick its own technology (polyglot persistence) safely. Cross-service queries become API composition or CQRS read models, and cross-service consistency uses sagas.
**In the interview:** state it explicitly when you draw microservices.

### Shared database antipattern — multiple services sharing one DB creates deployment and schema coupling
When several services read and write the same tables, a schema change requires coordinated deploys, one service's heavy queries hurt the others, ownership is unclear, and invariants get bypassed. You end up with a distributed monolith. Acceptable only as a temporary migration step.
**In the interview:** name it if your design starts drifting toward it.

## Service communication & resilience

### Synchronous (REST, gRPC) — immediate response; temporal coupling: caller blocks, dependency failures cascade
The caller waits for the answer. It's simple and the result arrives immediately, which suits reads and decisions the user is waiting for ("is this card valid?"). The cost is temporal coupling: if the callee is slow or down, the caller suffers, so you need timeouts, retries and circuit breakers. Avoid long synchronous chains.
**In the interview:** use sync only on the critical path.

### Asynchronous (events, queues) — decoupled in time; harder to trace, but more resilient
The caller emits a message and moves on, and consumers process it whenever they can. Downstream outages don't fail the caller, spikes are buffered, and fan-out is easy. The costs: eventual consistency, duplicates and ordering to handle, harder debugging (needs tracing and correlation IDs), and no immediate result.
**In the interview:** "anything the user doesn't need to wait for becomes an event."

### Service discovery — how services find each other's network location dynamically
Instances come and go (autoscaling, deploys), so IP addresses can't be hardcoded. Services register in a registry or get tracked by the platform, and callers resolve a logical name (`payment-service`) to healthy instances. It's done client-side or server-side.
**In the interview:** on Kubernetes the answer is simply "Kubernetes Service DNS".

### Client-side discovery — service queries registry (Eureka), load balances itself
The client asks the registry (Eureka, Consul) for the list of healthy instances and picks one using its own load-balancing logic (Spring Cloud LoadBalancer, Ribbon). There's no extra hop and it allows smart routing, but every client needs the library, and it's language-specific.
**In the interview:** common in older Spring Cloud / Netflix OSS stacks at banks.

### Server-side discovery — load balancer queries registry (AWS ALB + ECS, Kubernetes Service)
The client calls a stable address (a load balancer or virtual IP), and the platform routes to a healthy instance. Clients stay simple and language-agnostic, at the cost of an extra hop, with the LB as infrastructure to manage. Examples: a Kubernetes Service with kube-proxy, AWS ALB target groups, a service mesh.
**In the interview:** the default in modern container platforms.

### Service registry — Consul (with health checks), Eureka, Kubernetes DNS (CoreDNS)
The database of service instances and their health. **Consul**: CP (Raft-based), health checks, KV store, DNS interface, multi-datacentre. **Eureka**: AP, self-preservation mode, Netflix and Spring. **Kubernetes**: the API server plus etcd track endpoints, and CoreDNS resolves Service names.
**In the interview:** name the one that matches the platform you're proposing.

### Circuit breaker pattern — closed (normal) → open (fail fast after threshold) → half-open (test recovery)
Wraps calls to a dependency. **Closed**: calls pass through and failures are counted. When the failure rate crosses a threshold, it goes **open**: calls fail immediately or use a fallback, which protects your threads and gives the dependency time to recover. After a cool-down it goes **half-open**: a few trial calls go through, and success closes it while failure re-opens it.
**In the interview:** know the three states and why fail-fast prevents cascading failures.

### Hystrix (deprecated) / Resilience4j (Java) / Polly (.NET) — circuit breaker implementations
**Hystrix** (Netflix) popularised circuit breakers and bulkheads, but has been in maintenance mode since 2018. **Resilience4j** is the modern Java choice: a lightweight, functional library with CircuitBreaker, Retry, RateLimiter, Bulkhead and TimeLimiter modules, integrated with Spring Boot and Micrometer. **Polly** is the .NET equivalent. Service meshes can provide similar policies without libraries.
**In the interview:** "Resilience4j" is the right name to say in Java and Spring interviews.

### Retry with exponential backoff + jitter — avoid thundering herd on retry storms
Retry only **transient** failures (timeouts, 503, connection resets) on **idempotent** operations, with increasing randomised delays and a maximum number of attempts. Retry at one layer only (not at the client, the gateway *and* the service), and set a retry budget so retries never multiply load during an outage.
**In the interview:** combine it with circuit breakers. Retries alone can make outages worse.

### Timeout — always set explicit timeouts; cascading timeouts cause full-stack slowdowns
Every network call needs connect and read timeouts based on the dependency's p99 latency, not library defaults (which are often infinite or 30 s+). Propagate **deadlines**: if the user request has 2 s left, downstream calls get less. Callers' timeouts should exceed callees', and the combination with retries must fit within the overall budget.
**In the interview:** "no call without a timeout" is the first resilience rule.

### Bulkhead pattern — separate thread pools/connection pools per dependency; one slow dep can't exhaust all threads
Isolate resources per dependency or per feature, like a ship's watertight compartments: separate thread pools, connection pools or semaphores. If the recommendation service hangs, only its 20 threads block, and checkout keeps working. It can also isolate tenants or priority classes.
**In the interview:** pair it with the circuit breaker in any "one slow service took everything down" story.

### Fallback — return cached/default response when dependency fails (graceful degradation)
When a call fails or the circuit is open, return something useful: cached or stale data, a default (empty recommendations), a simplified response, or queue the request for later ("we'll email your invoice"). Fallbacks must be cheap and never call the same failing dependency. Some operations (payments) have no safe fallback, so fail clearly instead.
**In the interview:** say which features degrade and which must fail closed.

### Idempotent APIs — safe to retry; critical for distributed systems where retries are unavoidable
Retries happen everywhere: clients, gateways, SDKs, message redelivery. Make every mutating operation safe to repeat through idempotency keys, natural keys and unique constraints, conditional state transitions, or PUT-style "set" semantics instead of "increment".
**In the interview:** a theme in every distributed design. Mention it early.

### Sidecar pattern — inject cross-cutting concerns (proxy, logging, mTLS) as sidecar container
A helper container runs alongside the main app in the same pod and shares its network and storage. It provides proxying (Envoy), mTLS, log shipping, config reloading or secrets fetching, without changing app code and regardless of language. The cost is extra resources and latency per pod.
**In the interview:** "service mesh sidecars give us mTLS and retries uniformly."

### Ambassador pattern — outbound proxy that adds retry/timeout/circuit-breaker to legacy services
A specialised sidecar or proxy that handles a service's **outbound** calls: retries, timeouts, circuit breaking, routing and monitoring for remote services. It's useful for legacy apps you can't modify, or to centralise client-side connectivity logic.
**In the interview:** niche. Treat it as a sidecar focused on outbound calls.

### Health endpoints — /health (is process running?), /ready (can accept traffic?), /live (Kubernetes liveness)
**Liveness** (`/live`): is the process healthy, or should it be restarted? Keep it simple, with no dependency checks, or a DB outage triggers restart loops. **Readiness** (`/ready`): can it serve traffic now (warmed up, connected to its dependencies)? If not, it's removed from load balancing without a restart. A **startup** probe covers slow boots. In Spring, Actuator provides `/actuator/health/liveness` and `/readiness`.
**In the interview:** the liveness vs readiness distinction is a common question.

## API design & gateway patterns

### API gateway — single entry point: routing, auth enforcement, rate limiting, SSL termination, request aggregation
One front door for every client: TLS termination, authentication (JWT validation), rate limiting and quotas, routing to services, request/response transformation, aggregation, CORS, logging and metrics. Examples: Kong, Apigee, AWS API Gateway, Spring Cloud Gateway, Envoy-based gateways. Keep it highly available and free of business logic.
**In the interview:** draw it as the first box after the load balancer in microservice designs.

### Backend for Frontend (BFF) — separate API layer per client type (iOS, Android, web, third-party)
A thin backend per client experience that aggregates, shapes and trims data for that UI (mobile needs smaller payloads, web needs richer pages), owned by the frontend team. It avoids one bloated general-purpose API and lets clients evolve independently. Watch for duplicated logic across BFFs.
**In the interview:** good for apps with very different mobile and web needs.

### API composition — gateway aggregates multiple downstream service calls into one response
To answer "order details with customer and shipping status", a composer (gateway, BFF or dedicated service) calls the Order, Customer and Shipping services, **in parallel** where possible, and merges the results. It's simple, but latency is that of the slowest call, it has partial-failure handling to do, and it can't do efficient joins over large data. CQRS read models are the alternative.
**In the interview:** use it for simple cross-service reads. Use a read model for heavy queries.

### Pagination — offset-based (simple, inconsistent with concurrent mutations) vs cursor-based (consistent, scales)
**Offset/limit**: easy and supports page numbers, but slow for deep pages (the DB scans the skipped rows) and unstable when rows are inserted or deleted (duplicates or gaps). **Cursor/keyset**: return an opaque cursor encoding the last seen sort key, and the next query is `WHERE (created_at, id) < (?, ?) LIMIT 20`. It uses an index, stays fast at any depth and is stable. It can't jump to page N.
**In the interview:** cursor pagination for feeds and large lists.

### Filtering, sorting, field selection (sparse fieldsets) in REST API design
Use query parameters: `?status=PAID&minAmount=1000`, `?sort=-createdAt,amount`, `?fields=id,amount,status`. Whitelist filterable and sortable fields (backed by indexes), cap page sizes, and validate input. Sparse fieldsets cut payload size for mobile clients. JSON:API and OData standardise these conventions.
**In the interview:** quick polish points in the API design step.

### GraphQL federation — compose multiple subgraph schemas into unified API (Apollo Federation)
Each team owns a GraphQL **subgraph** for its domain (users, orders, products), and a **router or gateway** composes them into one supergraph. Entities can be extended across subgraphs (`Order.customer` resolved by the users subgraph). Clients see a single schema while teams deploy independently.
**In the interview:** for organisations that chose GraphQL across many services.

### Rate limiting at gateway — token bucket per API key/user, per endpoint; return 429 with Retry-After header
Enforce limits at the edge before requests reach services: per API key, user, IP or tenant, and per endpoint (stricter on login and payments). A token bucket in Redis (atomic via Lua) keeps limits consistent across gateway instances. Return `429 Too Many Requests` with `Retry-After` and remaining-quota headers. Decide fail-open vs fail-closed for when Redis is down.
**In the interview:** see the Rate Limiter case study for the full design.

### OAuth 2.0 authorization code + PKCE — for SPA and mobile (prevents authorization code interception)
The user is redirected to the authorisation server, logs in and consents, and the app receives a short-lived **code** that it exchanges for tokens. **PKCE**: the app first sends `code_challenge = SHA256(code_verifier)` and later proves possession with the `code_verifier`, so an intercepted code is useless to an attacker. It's now recommended for all clients, including server-side web apps.
**In the interview:** the correct flow for any user-facing login.

### OAuth 2.0 client credentials — for server-to-server, no user involved
A service authenticates with its own client ID and secret (or a private-key JWT, or mTLS) and gets an access token with scopes for calling other APIs. There's no user context. Used for batch jobs, backend integrations and partner APIs. Cache tokens until expiry, and rotate secrets.
**In the interview:** "service A gets a client-credentials token scoped to `ledger:write`."

### OpenID Connect (OIDC) — authentication layer on top of OAuth 2.0: ID token (JWT) carries user identity
OAuth answers "can this app access the API?". OIDC adds "**who is the user?**": an **ID token** (a JWT with `sub`, `email`, `name`, `iss`, `aud`, `exp`), a userinfo endpoint and standard discovery. It's the basis of "Login with Google" and enterprise SSO (Okta, Azure AD, Keycloak).
**In the interview:** "OIDC for login, OAuth access tokens for APIs."

### JWT structure — header (alg, typ) + payload (sub, iss, aud, exp, iat) + signature (HMAC-SHA256 or RS256)
Three base64url parts joined by dots. **Header**: the algorithm and key ID (`kid`). **Payload (claims)**: subject, issuer, audience, expiry, issued-at, plus custom claims like roles. **Signature**: HMAC (shared secret) or RSA/ECDSA (private key signs, public key verifies; better for many verifying services). It's signed, not encrypted, so anyone can read the payload.
**In the interview:** prefer asymmetric (RS256/ES256) with keys published via JWKS.

### JWT validation — verify signature, check exp, iss, aud claims; short expiry + refresh token rotation
On every request: verify the signature with the issuer's public key (fetched from JWKS and cached, matched by `kid`), reject `alg: none` and unexpected algorithms, and check `exp`/`nbf` (allowing small clock skew), `iss` (the expected issuer) and `aud` (meant for this API). Keep access tokens short-lived and rotate refresh tokens.
**In the interview:** "validated at the gateway and again in sensitive services" is defence in depth.

### API contract testing — Pact (consumer-driven contracts): consumer defines expectations, provider verifies
Consumers write tests describing the requests they send and the responses they expect, producing a **contract**. The provider's CI verifies it still satisfies every consumer's contract before deploying. That catches breaking API changes without slow end-to-end environments. Pact and Spring Cloud Contract are the common tools.
**In the interview:** an answer to "how do you stop one team's change breaking another service?"

### OpenAPI / Swagger specification — machine-readable API contract, enables code generation
A YAML/JSON description of endpoints, parameters, schemas, auth and errors. It generates documentation (Swagger UI), client SDKs and server stubs, enables request validation and mock servers, and supports design-first API reviews. Springdoc generates it from Spring controllers.
**In the interview:** "design-first with OpenAPI, reviewed before implementation."

## Deployment & release patterns

### Blue-green deployment — two identical environments; instant cutover by switching load balancer target
**Blue** runs the current version. Deploy the new one to **green**, test it, then flip the load balancer or DNS so all traffic goes to green. Rollback is an instant flip back. The costs are double the infrastructure during the switch, a big-bang exposure at cutover, and databases that must work with both versions.
**In the interview:** good for critical services that need instant rollback.

### Canary release — route 1–5% of traffic to new version, monitor error rate, gradually increase
Send a small slice of traffic to the new version, compare its metrics (error rate, latency, business KPIs) against the baseline, then expand step by step (5% → 25% → 50% → 100%) or roll back automatically. Tools: Argo Rollouts, Flagger, a service mesh, weighted load-balancer targets. It limits the blast radius of bad releases.
**In the interview:** "canary with automated metric analysis" is the modern standard.

### Feature flags — decouple code deploy from feature release; enable per user/segment
Ship code turned off behind a flag, then enable it at runtime for internal users, a percentage, a region or specific merchants. Flags also act as **kill switches** during incidents. Tools: LaunchDarkly, Unleash, Flagsmith, or homegrown. Clean up stale flags to avoid technical debt.
**In the interview:** "deploy dark, release with a flag, kill switch ready."

### A/B testing — route users to variants statistically, measure conversion/engagement
Randomly assign users (consistently, by hashing the user ID) to variants, measure the target metric, and use statistical significance tests to decide. Needs enough sample size, a predefined success metric, and guardrail metrics. It's built on feature-flag infrastructure plus an analytics pipeline.
**In the interview:** different from canary: A/B tests a product hypothesis, canary tests release safety.

### Rolling deployment — incrementally replace pods/instances with new version (Kubernetes default)
Replace instances a few at a time, waiting for health and readiness checks between batches. There's no extra environment needed, but old and new versions run **simultaneously**, so APIs, events and schemas must be backward compatible, and rollback is another rolling update.
**In the interview:** the default on Kubernetes. Mention version compatibility.

### Immutable infrastructure — never patch running instances; replace with new image from scratch
Instead of SSH-ing in to update servers, build a new image (AMI or container) for every change and replace the old instances. Environments become reproducible, there's no configuration drift, rollback means redeploying the old image, and security patching is consistent. Containers and IaC make this natural.
**In the interview:** part of a modern ops answer.

### GitOps — Git as source of truth for desired state; ArgoCD/Flux reconciles cluster to match
Desired cluster state (manifests, Helm values) lives in Git. Changes go through pull requests, and a controller in the cluster (Argo CD, Flux) continuously **pulls** and applies them, correcting drift. You get an audit trail, easy rollback (git revert), and no cluster credentials in CI.
**In the interview:** "deployments via GitOps with Argo CD."

### CI/CD pipeline — source → build → unit test → integration test → security scan → artifact → staging → production
Automate every change from commit to production: compile, unit tests, static analysis, dependency and container vulnerability scans (Snyk, Trivy), integration and contract tests, build an immutable artifact, deploy to staging, run smoke and e2e tests, then a progressive production rollout with automatic rollback. Banks add approval gates and change records.
**In the interview:** enough to show you understand the delivery lifecycle.

### Expand-contract (parallel change) — add new field, backfill, then remove old field across two deploys
Break incompatible changes into compatible steps. Expand: add the new field, column or endpoint, and write both. Migrate: backfill and move readers. Contract: remove the old one in a later deploy. It applies to DB schemas, APIs and event formats, so old and new code can coexist during rolling deploys.
**In the interview:** the key technique for zero-downtime changes.

### Database migration strategy in zero-downtime deploy — never use ALTER that locks table on production
Use versioned migrations (Flyway, Liquibase) run by CI. Prefer operations that don't lock or rewrite large tables: add nullable columns, `CREATE INDEX CONCURRENTLY`, batched backfills, and online schema tools (gh-ost) for MySQL. Set lock timeouts so a migration fails rather than blocking traffic. Every migration must be compatible with the code currently running.
**In the interview:** "Flyway + expand-contract + online DDL tooling."
