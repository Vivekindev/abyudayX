## Cloud services (AWS-focused)

### EC2 — VMs, instance types (compute/memory/storage-optimized), placement groups, AMI
Virtual machines on demand. Instance families: general purpose (m), compute-optimised (c), memory-optimised (r, x), storage-optimised (i), GPU (p, g). **AMIs** are machine images used to launch identical instances. **Placement groups**: cluster (low latency, same rack), spread (separate hardware) or partition. Pricing: on-demand, reserved/savings plans, or spot.
**In the interview:** "app servers on EC2 or containers in an Auto Scaling Group across 3 AZs."

### Lambda — serverless functions, event-driven, 15-min max, 10GB max memory, pay per GB-second
Upload code and AWS runs it in response to events (API Gateway, S3, SQS, EventBridge, DynamoDB Streams). It scales automatically per request, you pay per millisecond × memory, with up to 15 minutes per invocation and 10 GB of memory (CPU scales with memory). Watch for cold starts, connection limits to databases and concurrency limits.
**In the interview:** great for glue code, async event processing and spiky workloads.

### ECS — Docker container orchestration, Fargate (serverless) vs EC2 launch type
AWS's own container orchestrator, simpler than Kubernetes. **Fargate**: no servers to manage, you pay per task's vCPU and memory. **EC2 launch type**: you manage the cluster instances, which is cheaper at scale and allows GPUs and custom setups. It integrates with ALB, IAM roles per task, CloudWatch and Service Connect.
**In the interview:** "ECS on Fargate" is a low-ops choice for containerised services on AWS.

### EKS — managed Kubernetes, control plane managed by AWS
AWS runs the Kubernetes control plane (API server, etcd) across AZs, and you run worker nodes (managed node groups, Karpenter, or Fargate). You get the full Kubernetes ecosystem (Helm, operators, service meshes) with AWS integrations (IAM roles for service accounts, ALB controller, EBS/EFS drivers).
**In the interview:** choose it when you want Kubernetes portability and ecosystem.

### S3 — object storage: bucket + key model, 5TB max object, strong consistency since 2021
Store objects (files) by bucket and key over HTTP APIs. 11 nines of durability (replicated across AZs), virtually unlimited capacity, objects up to 5 TB. **Strong read-after-write consistency** for all operations since December 2020. Storage classes trade cost for access speed. It's the default home for media, backups, logs and data lakes.
**In the interview:** "blobs in S3, metadata in the DB, served via CloudFront."

### S3 features — versioning, lifecycle policies, presigned URLs (time-limited access), multipart upload, replication, S3 Select
**Versioning**: keep every version (recovers from overwrites and deletes). **Lifecycle**: move objects to cheaper tiers or expire them automatically. **Presigned URLs**: time-limited upload or download links without exposing credentials. **Multipart upload**: parallel, resumable uploads for large files. **Replication**: cross-region or same-region copies. **S3 Select/Athena**: query data in place. Also event notifications and Object Lock (WORM, for compliance).
**In the interview:** presigned URLs plus multipart upload appear in every upload design.

### EBS — block storage attached to EC2, like a hard drive; one AZ, snapshot to S3
Network block volumes attached to a single instance (multi-attach only for special cases), living in **one AZ**. Types: gp3 (general SSD with tunable IOPS), io2 (high IOPS for databases), st1/sc1 (HDD throughput). Point-in-time **snapshots** go to S3 and can be copied across regions.
**In the interview:** "self-managed databases on EBS io2; managed RDS handles this for you."

### EFS — managed NFS, shared file system across multiple EC2 instances in same region
A managed, elastic NFS file system that many instances (and containers or Lambdas) can mount at once, across AZs within a region. It's useful for shared content, legacy apps expecting a file system, and ML datasets. It costs more per GB than S3 and has higher latency than EBS.
**In the interview:** choose it only when you genuinely need a shared POSIX file system.

### RDS — managed relational DB: PostgreSQL, MySQL, Oracle, SQL Server; Multi-AZ for HA
AWS handles provisioning, patching, backups (point-in-time recovery), monitoring and failover. **Multi-AZ** keeps a synchronous standby in another AZ with automatic failover (~60–120 s). **Read replicas** scale reads (asynchronous, can be cross-region). You choose the instance size and storage.
**In the interview:** "Postgres on RDS Multi-AZ with 2 read replicas" is a solid concrete answer.

### Aurora — MySQL/Postgres-compatible, 6-way storage replication across 3 AZs, auto-scaling storage
Aurora separates compute from a distributed storage layer: 6 copies across 3 AZs, a 4-of-6 write quorum, self-healing, storage that grows automatically up to 128 TB. It supports up to 15 low-lag replicas sharing the storage, faster failover (~30 s), Global Database (cross-region replication with ~1 s lag), and Serverless v2.
**In the interview:** the step up from RDS when you need better HA and read scaling.

### DynamoDB — fully managed NoSQL, single-digit ms latency, automatic sharding
A key-value/document store with automatic partitioning, on-demand or provisioned capacity, TTL, Streams (CDC), transactions, Global Tables (multi-region active-active) and DAX caching. There's no server management. Design around access patterns (partition and sort keys, GSIs) and avoid hot partitions.
**In the interview:** "DynamoDB for the high-scale key-value access pattern, keyed by user_id."

### ElastiCache — managed Redis or Memcached in VPC
Managed in-memory caching: Redis (now including Valkey) with replication, cluster mode (sharding), Multi-AZ automatic failover and backups, or Memcached. It runs inside your VPC with low latency. **MemoryDB** is the durable Redis-compatible variant when Redis needs to be the primary store.
**In the interview:** "ElastiCache Redis in cluster mode as the shared cache."

### SQS / SNS / Kinesis / MSK — managed messaging; MSK = managed Kafka
**SQS**: managed queues (standard or FIFO). **SNS**: pub/sub fan-out. **Kinesis Data Streams**: ordered, replayable streams by shard. **MSK**: managed Apache Kafka (brokers, ZooKeeper/KRaft, patching). There's also **EventBridge** for event routing. Choose based on semantics: queue vs pub/sub vs stream.
**In the interview:** "SNS → SQS for fan-out; MSK where we need Kafka features like replay and high throughput."

### VPC — isolated virtual network; public subnets (internet-facing), private subnets (internal)
Your own private network in AWS, with a chosen CIDR range, split into subnets per AZ. **Public subnets** route to an Internet Gateway (load balancers, bastions). **Private subnets** hold app servers and databases with no inbound internet access, reaching out via a **NAT Gateway**. Route tables, VPC endpoints (private access to S3 and DynamoDB), peering and Transit Gateway connect networks.
**In the interview:** "DBs in private subnets, only reachable from the app tier's security group."

### Security Groups — stateful firewall at instance level; NACLs — stateless at subnet level
**Security groups** attach to instances or ENIs, have allow-rules only, and are **stateful** (return traffic is automatically allowed). They can reference other security groups ("allow 5432 from app-sg"). **NACLs** apply to whole subnets, support allow and deny rules, are **stateless** (return traffic needs explicit rules), and are evaluated in order. Most control lives in security groups.
**In the interview:** "least-privilege security groups chained tier to tier."

### Route53 — DNS with health checks, routing policies: simple, weighted, latency, failover, geolocation
Managed DNS plus domain registration. Routing policies: **simple**, **weighted** (canary or blue-green by percentage), **latency-based** (nearest region), **failover** (primary/secondary with health checks), **geolocation/geoproximity** (by user location or data-residency rules), and multivalue answers. Health checks drive automatic failover.
**In the interview:** the GSLB layer in multi-region AWS designs.

### CloudFront — CDN, Lambda@Edge for edge compute, TLS termination, WAF integration
AWS's CDN with 400+ edge locations: caches S3 or custom origins, terminates TLS, compresses, supports signed URLs and cookies for private content and Origin Shield to cut origin load. Runs code at the edge (CloudFront Functions for lightweight logic, Lambda@Edge for heavier logic), integrates with AWS WAF and Shield for DDoS protection.
**In the interview:** "S3 + CloudFront with signed URLs for private media."

### IAM — identity and access management: users, groups, roles, policies, least privilege
Controls who can do what in AWS. **Users/groups** are for humans (prefer SSO), **roles** are assumed by services and workloads, giving temporary credentials with no long-lived keys. **Policies** are JSON allow/deny statements on actions and resources, with conditions. Apply **least privilege**, use separate accounts per environment (AWS Organizations, SCPs), and audit with CloudTrail.
**In the interview:** "each service runs with its own IAM role scoped to its own resources."

### KMS — key management service: envelope encryption, key rotation, CloudTrail audit
Managed encryption keys backed by HSMs. Master keys (KMS keys) never leave KMS. Services use **envelope encryption**: KMS generates data keys that encrypt the data, and those data keys are themselves encrypted by the KMS key. Automatic yearly rotation, fine-grained key policies, and every use is logged in CloudTrail. It integrates with S3, EBS, RDS and Secrets Manager. CloudHSM gives dedicated HSMs for strict compliance.
**In the interview:** "encryption at rest with KMS customer-managed keys" for regulated data.

### CloudWatch — metrics, logs, alarms, dashboards; X-Ray for distributed tracing
CloudWatch collects AWS and custom metrics, logs (Logs Insights for querying), alarms (which trigger SNS notifications or autoscaling), dashboards and synthetic canaries. **X-Ray** provides distributed tracing across Lambda, ECS and API Gateway (OpenTelemetry-compatible via ADOT). Many teams also use Prometheus/Grafana or Datadog.
**In the interview:** name it as the observability stack if your design is AWS-native.

## Serverless & infrastructure as code

### Lambda cold starts — JVM/Python faster than Java; reduce with provisioned concurrency, SnapStart
The first invocation on a new execution environment must download the code, start the runtime and run initialisation: about 100 ms for Node/Python/Go, seconds for an unoptimised JVM. Mitigations: **provisioned concurrency** (pre-warmed environments, paid), **SnapStart** for Java (restore from a snapshot), smaller packages, lazy initialisation, lighter frameworks (Quarkus/Micronaut, GraalVM native).
**In the interview:** relevant whenever you put Lambda on a user-facing, latency-sensitive path.

### Lambda concurrency — reserved concurrency (cap), provisioned concurrency (pre-warmed)
**Concurrency** is the number of simultaneous executions (account default about 1,000 per region, raisable). **Reserved concurrency** guarantees a function a slice of that and also **caps** it, which protects downstream databases from being overwhelmed. **Provisioned concurrency** keeps N environments initialised to remove cold starts.
**In the interview:** "reserved concurrency caps DB connections from Lambda."

### Lambda + SQS — reserved concurrency = backpressure; SQS retains messages, Lambda scales
The SQS event source polls the queue and invokes Lambda in batches, scaling consumers with queue depth. Capping concurrency (or the event source's maximum concurrency) limits throughput to what downstream can handle, while SQS buffers the rest durably. Failed batches retry until `maxReceiveCount`, then go to the DLQ. Use partial batch responses to avoid reprocessing successful messages.
**In the interview:** a clean serverless pattern for smoothing load spikes.

### Step Functions — stateful serverless workflows: sequential, parallel, wait, retry, catch
Managed state machines defined in JSON/YAML (Amazon States Language) with task, choice, parallel, map, wait, retry (with backoff) and catch states. **Standard** workflows run up to a year with exactly-once step execution and full history. **Express** workflows are high-volume and short. Good for orchestrated sagas, order processing and ETL steps.
**In the interview:** "a Step Functions saga orchestrator with compensation in the catch blocks."

### EventBridge — serverless event bus: route events from AWS services and SaaS to Lambda/SQS
Publish events to a bus, and **rules** with content-based patterns route them to targets (Lambda, SQS, Step Functions, API destinations). It has a schema registry, archive and replay, cross-account buses, SaaS partner sources, and a **Scheduler** for cron and one-off scheduled events.
**In the interview:** good for loosely coupled AWS-native event routing. Use Kafka for high-throughput streams.

### Terraform — declarative IaC: resources, providers, state file (lock with S3 + DynamoDB)
Describe infrastructure in HCL (resources, variables, modules), and **providers** talk to AWS, GCP, Azure, Kubernetes, Cloudflare and more. Terraform keeps a **state file** mapping code to real resources. Store it remotely (an S3 backend with DynamoDB locking, or Terraform Cloud) so teams don't corrupt it. OpenTofu is the open-source fork.
**In the interview:** "all infrastructure in Terraform modules, reviewed via PRs."

### Terraform plan/apply workflow — preview changes before applying; destroy with care
`terraform plan` diffs the desired state against actual state and shows exactly what will be created, changed or **destroyed**. Review it (often as a PR comment via Atlantis or CI), then `terraform apply`. Watch for force-replacement of stateful resources (databases). Use `prevent_destroy` lifecycle rules and separate state per environment.
**In the interview:** shows safe operational practice.

### CloudFormation — AWS-native IaC: stacks, change sets, drift detection
AWS's own IaC in YAML/JSON templates. Resources are grouped into **stacks**, **change sets** preview updates, failures roll back automatically, **drift detection** finds manual changes, and StackSets deploy across accounts and regions. **AWS CDK** lets you write it in TypeScript, Java or Python.
**In the interview:** an alternative to Terraform for AWS-only shops.

### Ansible — configuration management: agentless, idempotent YAML playbooks
Ansible configures servers over SSH with no agents. **Playbooks** (YAML) describe the desired state (install packages, write config files, restart services), and modules are idempotent, so rerunning is safe. Common in on-prem and bank environments for VM fleets. With containers and immutable images, it's used more for image building and legacy hosts.
**In the interview:** "Terraform provisions, Ansible configures" for VM-based setups.

### Container registry — ECR (AWS), Docker Hub, GCR, Harbor (self-hosted)
Registries store and version container images: **ECR** (AWS, IAM-integrated, image scanning), Docker Hub, GCR/Artifact Registry, GitHub Container Registry, **Harbor** (self-hosted, with vulnerability scanning and replication, popular on-prem and in banks). Tag images immutably (commit SHA), scan them, and sign them (cosign).
**In the interview:** a small but expected piece of a CI/CD answer.

### GitOps with ArgoCD — desired state in Git, ArgoCD reconciles cluster continuously
Argo CD watches Git repositories of manifests or Helm charts and syncs them into Kubernetes, shows drift, and can auto-heal. Promotion between environments happens through PRs. Combine it with Argo Rollouts for canary and blue-green deployments, and image updater tools for automatic version bumps.
**In the interview:** "CI builds and pushes the image; Argo CD deploys from Git."

### CI/CD stages — build → unit test → integration test → security scan → artifact publish → deploy to staging → smoke test → promote to production
A typical pipeline (Jenkins, GitHub Actions, GitLab CI): compile, run unit tests with coverage, static analysis (SonarQube), dependency, secret and container scans, integration and contract tests, publish a versioned artifact or image, deploy to staging, run smoke and e2e tests, then a progressive production rollout (canary) with automatic rollback and, in regulated firms, change-approval gates.
**In the interview:** name the stages and the quality gates in order.

## Security fundamentals

### Authentication vs authorization — who are you (authn) vs what can you do (authz)
**AuthN** verifies identity (password + MFA, OIDC login, client certificates, API keys). **AuthZ** decides permissions for that identity (RBAC roles, ABAC attribute rules, ReBAC relationships, resource ownership checks). HTTP mapping: a failed authn → 401, a failed authz → 403. Enforce authz in each service, not only at the gateway.
**In the interview:** a classic warm-up question. Answer with an example.

### OAuth 2.0 authorization code flow + PKCE — for SPA/mobile: code_verifier + code_challenge prevent interception
The client creates a random `code_verifier` and sends `code_challenge = BASE64URL(SHA256(verifier))` with the authorisation request. After login, it receives a code and exchanges it, plus the verifier, for tokens. The server checks that the hash matches, so a stolen code can't be redeemed. It replaces the deprecated implicit flow, and OAuth 2.1 makes it mandatory.
**In the interview:** know why PKCE exists: public clients can't keep secrets.

### OAuth 2.0 client credentials flow — service-to-service, no user context
A machine client authenticates directly to the token endpoint with its credentials and receives an access token for specific scopes. Use it for backend jobs and service integrations. Keep secrets in a vault, prefer private-key JWT or mTLS client authentication, and use short token lifetimes.
**In the interview:** the answer for "how does the batch job call the API securely?"

### JWT validation — verify signature (RS256 public key), check exp, iss, aud; never skip validation
Always verify the signature with the expected key (from JWKS, by `kid`) and an algorithm allow-list (reject `none` and confused HS/RS algorithms). Check `exp` and `nbf` with small clock skew, `iss` and `aud`. Treat claims as untrusted until verified, and use maintained libraries rather than hand-rolled parsing.
**In the interview:** common vulnerabilities include skipping `aud` checks and accepting `alg=none`.

### Refresh token rotation — issue new refresh token on every use; revoke old one (prevents token theft)
Each time a refresh token is used, issue a **new** one and invalidate the old. If an old (stolen) refresh token is ever reused, detect it and **revoke the whole token family**, forcing re-login. Combine with short-lived access tokens, and bind refresh tokens to the client or device where possible.
**In the interview:** the mitigation for JWT revocation problems.

### Token storage — httpOnly+Secure cookies (XSS-resistant) vs localStorage (XSS risk)
**localStorage/sessionStorage**: any injected script can read the tokens, so an XSS bug means stolen tokens. **HttpOnly + Secure + SameSite cookies**: JavaScript can't read them. You then need CSRF protection (SameSite=Lax or Strict, CSRF tokens). Mobile apps should use the OS keychain or keystore. The BFF pattern keeps tokens server-side entirely.
**In the interview:** "tokens in HttpOnly cookies, or a BFF holding the tokens server-side."

### API keys — rotate regularly, hash before storage (like passwords), scope by service
API keys are long random secrets identifying a client (partners, server-to-server). Show the key once, then store only a **hash** (plus a prefix for lookup). Scope keys to permissions and environments, support multiple active keys for zero-downtime rotation, rate-limit per key, and revoke quickly. Never put them in URLs (they end up in logs).
**In the interview:** "partner API keys hashed with a prefix lookup, scoped and rotatable."

### mTLS — both client and server present X.509 certificates; used for service-to-service auth in production
Both sides authenticate with certificates during the TLS handshake. It establishes strong workload identity (SPIFFE IDs) without passwords, and encrypts the traffic. Certificate issuance and rotation are automated by a service mesh (Istio, Linkerd) or an internal CA (Vault PKI, cert-manager). It's common in banking and partner integrations (card networks, payment switches).
**In the interview:** "zero-trust between services via mesh-managed mTLS."

### Encryption at rest — AES-256, transparent encryption (TDE), or field-level encryption
Protect stored data if disks, snapshots or backups leak. Options: **volume/disk encryption** (EBS, S3 SSE), **TDE** (the DB encrypts data files transparently), and **field-level / application-level encryption** for sensitive fields (PAN, Aadhaar, PII), so even DB admins and SQL-injection attacks only see ciphertext. Keys live in a KMS or HSM with envelope encryption and rotation.
**In the interview:** "field-level encryption for PII on top of storage encryption" for fintech.

### Encryption in transit — TLS 1.2/1.3 everywhere; enforce in security groups / policies
Encrypt every hop: client → CDN/LB (TLS 1.2+, HSTS), LB → services (re-encrypt), service → service (mTLS), service → DB/cache/Kafka (TLS). Disable old protocols and weak ciphers, enforce it with policies (S3 `aws:SecureTransport`, DB `require_ssl`), and automate certificates.
**In the interview:** "TLS everywhere, including internal traffic" is the expected baseline.

### Secret management — HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager; never hardcode secrets
Store credentials, API keys and certificates in a dedicated secrets manager, with access control, audit logs, rotation and versioning. Apps fetch secrets at runtime (or via sidecars or CSI drivers) using their workload identity. **Vault** also issues **dynamic secrets** (short-lived DB credentials per service). Never commit secrets to Git, and scan for leaks (gitleaks).
**In the interview:** "DB credentials rotated automatically via Secrets Manager or Vault."

### OWASP Top 10 — SQL injection, XSS, SSRF, broken access control, insecure deserialization — know each
The most critical web risks: **broken access control** (e.g. IDOR: `/accounts/124` showing someone else's data), cryptographic failures, **injection** (SQL, command), insecure design, security misconfiguration, vulnerable components, authentication failures, software and data integrity failures (including insecure deserialisation), logging and monitoring failures, and **SSRF**. Each has standard mitigations.
**In the interview:** give each risk with its fix in one breath.

### SSRF — Server-Side Request Forgery: prevent by validating/blocking internal IP ranges in outbound requests
An attacker makes your server fetch a URL they choose, such as `http://169.254.169.254/` (cloud metadata credentials) or internal admin services. It's common in "fetch image from URL", webhook and PDF-render features. Mitigations: allow-list destinations, resolve DNS and block private, link-local and loopback ranges (re-checking after redirects), use IMDSv2 on AWS, and route outbound fetches through an egress proxy.
**In the interview:** relevant when your design fetches user-supplied URLs (crawlers, webhooks).

### SQL injection — always parameterized queries, never string concatenation for SQL
Concatenating user input into SQL (`"WHERE name = '" + input + "'"`) lets attackers change the query (`' OR 1=1 --`). The fix is **parameterised queries / prepared statements** (JDBC `?`, JPA parameters) and ORMs used correctly. Also validate input, use least-privilege DB users, and never build dynamic ORDER BY clauses from raw input without allow-lists.
**In the interview:** basic, but expected at banks.

### DDoS mitigation — rate limiting (WAF), CDN absorption, IP reputation lists, Anycast
Absorb and filter attack traffic before it reaches you: **CDN/anycast networks** (Cloudflare, CloudFront + Shield) spread volumetric floods; a **WAF** blocks malicious patterns and enforces rate limits; IP reputation lists, geo-blocking and bot management handle the rest. Autoscaling and load shedding are the internal last resort.
**In the interview:** "Cloudflare/Shield at the edge, WAF rate rules, and app-level rate limiting."

### Zero-trust architecture — never trust, always verify; microsegmentation, device health checks
Don't trust anything based on network location ("inside the VPN"). Authenticate and authorise **every** request, between users and services, using strong identity (mTLS, OIDC), device posture, least privilege and continuous verification. **Microsegmentation** limits lateral movement after a breach. Examples: Google BeyondCorp, service-mesh mTLS with authorisation policies.
**In the interview:** a modern banking-security answer.

### Principle of least privilege — every service/user gets minimum permissions needed
Grant only the permissions required, for only as long as needed: scoped IAM roles per service, read-only DB users for read paths, just-in-time access for engineers (with approval and expiry), and separate production access. It limits the blast radius when credentials leak.
**In the interview:** say it when describing service identities and DB access.

### Audit logging — immutable log: who accessed what, when, from where; ship to SIEM
Record security-relevant actions (logins, permission changes, data access, money movements, admin operations) with actor, action, resource, time, source IP and result. Make the logs **tamper-evident** (append-only, WORM storage, hash chaining), retain them per regulation, and stream them to a **SIEM** (Splunk, Sentinel) for alerting and investigations.
**In the interview:** mandatory in financial systems. Mention it in payment and ledger designs.

### GDPR / PII handling — data minimization, right to erasure, encryption, data subject rights
Collect only the personal data you need (minimisation), state the purpose, encrypt it, restrict access, and honour data subject rights: access, correction, **erasure** ("right to be forgotten", hard with backups and event logs, so use crypto-shredding with per-user keys) and portability. Respect data residency (India's DPDP Act, RBI rules for payment data).
**In the interview:** "PII isolated in its own service, encrypted, with erasure via crypto-shredding."

### Data masking and tokenization — protect PII in non-production environments
**Masking** replaces real values with realistic fakes or partial values (`XXXX-XXXX-1234`) for test environments, analytics and display. **Tokenization** swaps sensitive data for random tokens, with the real values held in a secure vault (card PANs), so most systems never see real data, which also shrinks PCI-DSS scope. Never copy raw production PII into dev or test.
**In the interview:** "card numbers tokenised; downstream services only see tokens."
