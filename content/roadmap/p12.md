## Reliability & availability

### SLA — Service Level Agreement: contractual uptime commitment (e.g., 99.9% uptime per month)
A **contract** with customers: "99.9% monthly availability, or you get service credits." It has legal and financial consequences, so it's set looser than internal targets. It defines precisely what counts as downtime, how it's measured and what's excluded (planned maintenance).
**In the interview:** "the SLA is 99.9%, so our internal SLO is 99.95% for headroom."

### SLO — Service Level Objective: internal target (e.g., p99 latency < 200ms, error rate < 0.1%)
The **target** your team commits to internally for an SLI over a window: "99.95% of payment requests succeed in under 500 ms over 30 days." It drives engineering priorities and alerting. Choose SLOs based on what users actually notice, not on what's easy to measure.
**In the interview:** set explicit SLOs during the non-functional requirements step.

### SLI — Service Level Indicator: the actual measured metric (e.g., % of requests completing < 200ms)
The **measurement**: a ratio of good events to valid events, such as the fraction of HTTP requests that are non-5xx and faster than 300 ms, measured at the load balancer or client. Good SLIs reflect user experience (availability, latency, correctness, freshness).
**In the interview:** define SLI → SLO → SLA in that order. It's a common question.

### Error budget — 1 − SLO: how much downtime/error is acceptable in a period (99.9% → 43 min/month)
The allowed unreliability: a 99.9% SLO leaves 0.1% of requests (or ~43 minutes a month) to "spend" on deploys, experiments and incidents. With budget left, ship faster. When it's exhausted, freeze risky launches and prioritise reliability work. It aligns product and SRE incentives.
**In the interview:** "error-budget policies decide release velocity."

### Error budget burn rate — rate at which budget is consumed; fast burn = imminent SLO violation
The burn rate is how fast you're consuming the budget relative to plan (burn rate 1 = exactly on budget for the window). **Multi-window burn-rate alerts** (Google SRE): page if a 1-hour window burns at 14× (2% of the monthly budget gone in an hour), and file a ticket for a slow burn over 6–24 hours. It catches real problems quickly with few false alarms.
**In the interview:** the modern alternative to static threshold alerts.

### 99% = 87.6 hr/yr, 99.9% = 8.7 hr/yr, 99.99% = 52 min/yr, 99.999% = 5.2 min/yr
Each extra nine cuts allowed downtime by 10×: 99% ≈ 3.65 days/year (7.3 h/month), 99.9% ≈ 8.8 h/year (43 min/month), 99.99% ≈ 53 min/year (4.4 min/month), 99.999% ≈ 5 min/year (26 s/month). Every nine costs much more: redundancy, automation, multi-region. Serial dependencies multiply (three 99.9% services ≈ 99.7%).
**In the interview:** memorise this table and the multiplication rule.

### MTTR — Mean Time to Recovery: key reliability metric; minimize with runbooks + automation
The average time from failure to restored service: detect (good alerting), diagnose (observability, runbooks), mitigate (rollbacks, feature flags, failover automation), recover. Availability ≈ MTBF / (MTBF + MTTR), so cutting MTTR is often cheaper than preventing every failure.
**In the interview:** "fast rollback and kill switches minimise MTTR."

### MTBF — Mean Time Between Failures; maximize with fault isolation and redundancy
The average operating time between failures. Increase it through redundancy (no single points of failure), fault isolation (bulkheads, cells), testing, gradual rollouts and capacity headroom. At scale, individual component failures are constant, so design for graceful handling rather than assuming high MTBF.
**In the interview:** pair it with MTTR in availability discussions.

### RTO — Recovery Time Objective: max acceptable downtime (DR planning)
How long the business can tolerate a system being down after a disaster. Core payments: minutes. An internal reporting tool: hours or a day. RTO determines the DR strategy: backup & restore (hours), pilot light, warm standby (minutes), or active-active (near zero).
**In the interview:** state RTO and RPO when discussing multi-region.

### RPO — Recovery Point Objective: max acceptable data loss (backup frequency)
How much data, measured in time, you can afford to lose: RPO 24 h means daily backups are fine, and RPO ≈ 0 requires synchronous replication. Financial ledgers need RPO ≈ 0 (synchronous or quorum replication to another AZ or region). Analytics can tolerate hours.
**In the interview:** "ledger: RPO 0, RTO 5 minutes; analytics: RPO 24 h."

### Multi-AZ deployment — replicate across availability zones for HA within a region
Availability zones are separate datacentres (independent power, cooling and network) within a region, with low latency between them (~1–2 ms). Run instances across ≥2–3 AZs behind a load balancer, with databases using a synchronous standby in another AZ (RDS Multi-AZ, Aurora), and replicated caches and Kafka across AZs. It survives a datacentre failure with little complexity.
**In the interview:** the baseline for any production system.

### Multi-region deployment — replicate across regions for DR; active-active vs active-passive
Deploy in two or more geographic regions to survive regional outages and serve global users with low latency. The hard part is data: cross-region latency (~50–250 ms) forces trade-offs between async replication (possible data loss on failover) and synchronous replication (slow writes). Data residency laws may restrict which regions you can use (RBI: payment data stays in India).
**In the interview:** justify the added complexity with RTO/RPO or latency requirements.

### Active-active failover — both regions serve traffic; complex consistency, zero downtime
All regions handle live traffic (users routed to the nearest), and if one fails the others absorb its load. Near-zero RTO and better latency, but you need multi-region writes (conflict resolution, CRDTs, or partitioning users by home region) and enough spare capacity in each region to take over. It's the most expensive and complex option.
**In the interview:** often done with "each user is homed to one region" to avoid write conflicts.

### Active-passive failover — primary serves all traffic; secondary on standby; DNS failover
One region serves everything while a standby region receives replicated data (async). On disaster, promote the standby database and switch DNS or the global load balancer. It's simpler, but RTO is minutes (promotion + DNS TTL + warm-up), and async replication means RPO > 0. Variants: pilot light (minimal infra) vs warm standby (scaled-down copy running).
**In the interview:** the common, pragmatic DR choice. Rehearse it with drills.

### Chaos engineering — intentionally inject failures: kill random pods (Chaos Monkey), Gremlin
Proactively test resilience by injecting controlled failures in production or staging: kill instances (Chaos Monkey), add latency or packet loss, fail a dependency, exhaust CPU or disk, black-hole an AZ. Start with a hypothesis ("checkout survives losing one Redis node"), limit the blast radius, observe, and fix weaknesses. Tools: Gremlin, Chaos Mesh, AWS FIS, Litmus.
**In the interview:** "we verify failover with regular chaos experiments."

### Game days — scheduled chaos: simulate region outage, practice incident response with real team
Planned exercises where teams simulate a major failure (region down, database failover, Kafka cluster loss) and practise detection, communication, runbooks and recovery, measuring actual RTO. They reveal gaps in tooling, documentation and on-call readiness. Banks run regulator-mandated DR drills that are similar in spirit.
**In the interview:** shows operational maturity.

### Graceful degradation — serve reduced functionality when dependency fails (disable recommendations, show cached data)
When parts of the system fail or are overloaded, keep the **core** working: show cached prices, hide recommendations, queue non-urgent writes, disable heavy features via flags, serve a static fallback page. Decide in advance which features are critical (pay, login) and which are optional (personalisation, reviews).
**In the interview:** "during the sale we shed recommendations to protect checkout."

### Bulkhead isolation — separate thread pools and connection pools per downstream dependency
Partition resources so one failure can't sink everything: separate pools per dependency, separate clusters per tenant tier, **cell-based architecture** (independent stacks, each serving a slice of users). A slow recommendation API exhausts only its own pool, and a bad tenant affects only its own cell.
**In the interview:** combine it with circuit breakers and timeouts.

## Observability — logs, metrics, traces

### Three pillars of observability — logs (what happened), metrics (how much), traces (how long and where)
**Metrics**: cheap numeric time series for dashboards and alerts ("error rate 2%"). **Logs**: detailed event records for investigation ("payment abc failed: issuer timeout"). **Traces**: a request's path across services with timing per hop ("the ledger call took 400 ms"). Correlate them with shared IDs (trace ID in logs, exemplars on metrics).
**In the interview:** "metrics to detect, traces to localise, logs to explain."

### Four golden signals (Google SRE) — latency, traffic (RPS), errors (rate), saturation (utilization)
Monitor these for every user-facing service. **Latency**: percentiles, with successful and failed requests separated. **Traffic**: requests per second. **Errors**: rate of failed requests, explicit and implicit (wrong content, too slow). **Saturation**: how full the service is (CPU, memory, pool usage, queue depth), which is the leading indicator of trouble.
**In the interview:** list them when asked "what would you monitor?"

### RED method — Rate (requests/sec), Errors (rate), Duration (latency distribution)
A service-centric subset of the golden signals for request-driven microservices: **R**ate, **E**rrors, **D**uration. Build one standard RED dashboard per service, so every team's dashboard looks the same and is easy to read during incidents.
**In the interview:** "RED dashboards per service, USE dashboards per resource."

### USE method — Utilization, Saturation, Errors per resource (CPU, memory, disk, network)
For each **resource** (CPU, memory, disk, network, connection pools, threads): **U**tilisation (% busy), **S**aturation (queued work: run-queue length, swap, pool wait time), **E**rrors (device or connection errors). It systematically finds bottlenecks in infrastructure (Brendan Gregg).
**In the interview:** use it when diagnosing "the service is slow but CPU looks fine".

### Structured logging — JSON format: include trace_id, span_id, request_id, user_id, service_name
Log machine-parseable JSON with consistent fields: timestamp, level, service, environment, version, trace_id/span_id, request ID, user or tenant ID (careful with PII), event name and error details. You can then filter and aggregate across services ("all logs for trace X"). Never log secrets, card numbers or passwords, and mask PII.
**In the interview:** "JSON logs with trace IDs, shipped centrally, with PII masked."

### Log levels — TRACE (verbose), DEBUG, INFO (business events), WARN (recoverable), ERROR (needs action), FATAL
**TRACE/DEBUG**: developer detail, usually off in production or dynamically enabled. **INFO**: significant business and lifecycle events. **WARN**: unexpected but handled (a retry that succeeded). **ERROR**: a failed operation that needs attention. **FATAL**: the process can't continue. Excessive logging costs money and hurts performance, so sample high-volume logs.
**In the interview:** minor, but logging discipline signals experience.

### Log aggregation — Fluentd/Logstash collect → Elasticsearch store → Kibana visualize (ELK/EFK)
Agents (Fluent Bit, Fluentd, Filebeat, Vector) collect container and host logs, parse and enrich them, and ship them to a central store: **Elasticsearch/OpenSearch** (searchable, Kibana UI), **Loki** (cheaper, label-indexed, Grafana), **Splunk** (common in banks) or cloud services. Apply retention tiers and ILM to control cost.
**In the interview:** "Fluent Bit → OpenSearch (or Loki) → dashboards and alerts."

### Prometheus data model — time series labeled by key-value pairs; pull-based scraping
Each series is a metric name plus **labels** (`http_requests_total{service="pay", status="500", route="/charge"}`) with timestamped values. Prometheus **pulls** (scrapes) `/metrics` endpoints on an interval, finding targets via service discovery (Kubernetes). Beware **high cardinality**: labels such as user ID or full URL explode the series count. Use Thanos, Mimir or Cortex for long-term, global storage.
**In the interview:** "avoid unbounded label values" is a key operational point.

### Prometheus metric types — Counter (monotone: total_requests), Gauge (current: active_connections), Histogram (latency buckets), Summary
**Counter**: only goes up (resets on restart); use `rate()` over it (requests, errors). **Gauge**: goes up and down (queue depth, memory, active connections). **Histogram**: counts observations into buckets, so you can compute percentiles server-side and aggregate across instances (latency). **Summary**: client-side quantiles that can't be aggregated across instances. Prefer histograms.
**In the interview:** "latency as a histogram so we can aggregate p99 across pods."

### PromQL queries — rate(http_requests_total[5m]), histogram_quantile(0.99, ...), topk(5, ...)
`rate(http_requests_total[5m])` gives per-second request rate over 5 minutes. `sum by (service)(rate(errors_total[5m])) / sum by (service)(rate(http_requests_total[5m]))` gives error ratio. `histogram_quantile(0.99, sum by (le)(rate(http_request_duration_seconds_bucket[5m])))` gives p99 latency. `topk(5, …)` gives the top offenders. Recording rules precompute expensive queries.
**In the interview:** knowing `rate` plus `histogram_quantile` is enough.

### Grafana — connect to Prometheus/CloudWatch/InfluxDB; build dashboards, set alert thresholds
A visualisation layer over many data sources (Prometheus, Loki, Tempo, Elasticsearch, CloudWatch, SQL). Build dashboards per service (RED) and per platform component, use templated variables, link metrics → logs → traces, and define alert rules that route to Slack or PagerDuty. Dashboards-as-code via Grafonnet or Terraform.
**In the interview:** the standard dashboard answer.

### Distributed tracing — trace = end-to-end request; span = single operation with start/end/metadata
A **trace** follows one request through every service, and each **span** is one operation (HTTP call, DB query) with start and end times, attributes and a parent span. A trace ID propagates via headers. It reveals where time goes, which dependency fails, and fan-out patterns. Sample it (head- or tail-based) to control cost, keeping all error and slow traces.
**In the interview:** "tracing found that 80% of checkout latency was the fraud-check call."

### OpenTelemetry — vendor-neutral SDK for traces, metrics, logs; single integration for all backends
A CNCF standard: APIs, SDKs and auto-instrumentation (a Java agent, Spring and others) produce traces, metrics and logs in a common format (OTLP). An **OTel Collector** receives, processes (sampling, PII scrubbing) and exports the data to any backend (Jaeger, Tempo, Prometheus, Datadog, New Relic), so there's no vendor lock-in in your code.
**In the interview:** "instrumented with OpenTelemetry, exported via the Collector."

### W3C TraceContext — traceparent and tracestate headers for cross-service trace propagation
The standard HTTP headers for propagating trace context: `traceparent: 00-<trace-id>-<parent-span-id>-<flags>` (the flags include the sampling decision) and `tracestate` for vendor-specific data. Every service (and message headers in Kafka) must forward them so traces stay connected across languages and vendors.
**In the interview:** detail. "Trace context propagates via traceparent, including through Kafka headers."

### Jaeger / Zipkin — open-source distributed tracing backends; Tempo (Grafana), X-Ray (AWS)
Backends that store, index and visualise traces. **Jaeger** (CNCF, from Uber) and **Zipkin** (from Twitter) are the classic open-source options. **Grafana Tempo** stores traces cheaply in object storage and links them with Loki and Prometheus. **AWS X-Ray**, Google Cloud Trace and Azure App Insights are the managed options.
**In the interview:** name one. All accept OpenTelemetry data.

### APM tools — Datadog, New Relic, Dynatrace: trace + metrics + logs in one platform
Commercial all-in-one observability: agents auto-instrument applications and give you traces, metrics, logs, profiling, real-user monitoring, synthetic checks and AI-assisted alerting in a single UI. They're fast to adopt and powerful, but cost grows with data volume (and with high cardinality). Many banks use Dynatrace or AppDynamics.
**In the interview:** "Datadog/Dynatrace, or an OSS stack (Prometheus, Loki, Tempo, Grafana) for cost control."

### Alerting best practices — alert on SLO burn rate, not raw metrics; PagerDuty + runbooks for every alert
Page humans only for **user-impacting, actionable** conditions (SLO burn rate, error spikes, full queues), and send everything else to tickets or dashboards. Every alert links a **runbook**. Route by severity (PagerDuty, Opsgenie), deduplicate and group, and regularly prune noisy alerts. Alert fatigue makes people ignore real incidents.
**In the interview:** "symptom-based, SLO-driven alerts with runbooks."

### P50/P99/P99.9 latency — mean misleads; tail latency (P99.9) matters at scale (1 in 1000 requests)
The mean hides outliers. p50 is the typical user, and p99 and p99.9 are the worst 1% and 0.1%. At scale the tail matters: if a page calls 50 services, the chance of hitting at least one p99-slow call is about 40%. Heavy users often hit the tail most. Set SLOs on high percentiles, and compute them from histograms (you can't average percentiles).
**In the interview:** "we track p99, not the average."

### Tail latency mitigation — hedged requests: send duplicate to second server if first exceeds threshold, use first response
**Hedged requests**: if a request hasn't returned by the p95 time, send a duplicate to another replica and use whichever answers first (only for idempotent reads, at the cost of a few percent extra load). Other techniques: tied requests, timeouts with fast retries, avoiding GC pauses, separating slow and fast workloads, request coalescing, and keeping queues short (Little's Law). See Google's "The Tail at Scale".
**In the interview:** an impressive advanced point for read-heavy fan-out systems.

### On-call best practices — runbooks, escalation policy, post-mortems, blameless culture, rotation fairness
Sustainable on-call: fair rotations with handoffs, a clear escalation policy, runbooks for every alert, an incident commander role for major incidents, status-page communication, and **blameless post-mortems** that focus on systemic fixes (with action items tracked to completion). Measure alert volume and pages outside working hours.
**In the interview:** shows maturity in behavioural and system design discussions.

## Performance optimization

### Profiling — CPU flame graphs (async-profiler, py-spy), heap dumps, I/O tracing (strace, perf)
Measure, don't guess. **CPU profilers** (async-profiler or JFR for Java, py-spy, pprof for Go) sample stacks to find hot code. **Heap dumps** and allocation profiling (Eclipse MAT) find leaks and GC pressure. **Off-CPU / I/O analysis** (perf, strace, eBPF tools) shows waiting on locks, disk or network. Continuous profiling (Pyroscope, Datadog) catches production-only issues.
**In the interview:** "profile in production with async-profiler/JFR before optimising."

### Flame graph — visualize hot code paths; identify unexpected CPU consumers in production
Each box is a stack frame. Width shows how much of the sampled time includes that frame, and stacks grow upward. Wide plateaus are where CPU goes, such as unexpected JSON serialisation, regex, logging or lock contention. Differential flame graphs compare before and after a change.
**In the interview:** "a flame graph showed 30% of CPU in JSON mapping, so we switched to protobuf."

### Load testing — k6, Locust, Apache JMeter, wrk; always test in staging environment first
Simulate expected traffic patterns (realistic request mix, think times, data volumes) to verify the system meets SLOs at target load and to find capacity limits. Tools: **k6** (JS scripts, CI-friendly), **Gatling** (JVM), **Locust** (Python), **JMeter**, **wrk** (raw HTTP). Use a production-like environment and data, and watch the whole stack (DB, cache, queues), not just the app.
**In the interview:** "load-test at 2–3× expected peak before the sale."

### Stress testing — find breaking point (max RPS before error rate spikes)
Increase load beyond normal levels until the system degrades or fails. Find the maximum sustainable throughput, which component breaks first (DB connections, CPU, a downstream rate limit), and **how** it fails: gracefully with 429/503 and load shedding, or catastrophically with cascading timeouts. Verify that it recovers once load drops.
**In the interview:** "we know our breaking point and the first bottleneck."

### Soak testing — sustained load for hours; catch memory leaks, connection pool exhaustion
Run moderate, realistic load for many hours or days. It reveals slow problems: memory leaks, file descriptor or connection leaks, growing caches, log-disk exhaustion, GC degradation, database bloat, and token or certificate expiry. Things that pass a 10-minute test often fail overnight.
**In the interview:** mention it alongside load and stress tests.

### Spike testing — sudden 10× traffic increase; test auto-scaling and DB connection pool behavior
Hit the system with an abrupt surge (sale start, push-notification blast, a match result) to check how it absorbs bursts: does autoscaling react fast enough, do queues buffer, do rate limiters and waiting rooms engage, does the DB connection pool or cache stampede protection hold? Often reveals the need for pre-scaling.
**In the interview:** essential for flash-sale and Tatkal-style designs.

### Little's Law in practice — L = λW: if p99 latency increases, L (queue depth) grows; fix by reducing W or λ
Concurrency = throughput × latency. If a dependency slows from 50 ms to 500 ms at 2,000 req/s, in-flight requests jump from 100 to 1,000, which exhausts thread pools, connection pools and memory and causes cascading failure. Fixes: reduce W (cache, optimise, use timeouts) or reduce λ (shed load, rate limit), and size pools for expected L with headroom.
**In the interview:** use it to explain why timeouts and bulkheads are essential.

### Connection pool sizing — formula: pool = (cores × 2) + effective_spindle_count; too large → context switch overhead
More DB connections isn't faster. A database has limited CPU cores and disk parallelism, and hundreds of concurrent queries just cause contention and context switching. HikariCP's guidance is roughly `cores × 2 + effective spindles` for the **database's** cores, e.g. 10–20 per DB, shared across all app instances (use PgBouncer to multiplex). Measure pool wait times and adjust.
**In the interview:** "a small pool per instance, PgBouncer in front, total within DB limits."

### Thread pool sizing — I/O-bound: threads = (1 + wait_time/service_time) × cores; CPU-bound: threads ≈ cores
**CPU-bound** work: about one thread per core (more just adds context switching). **I/O-bound** work: threads ≈ cores × (1 + wait time / compute time). If requests wait 90 ms on I/O for 10 ms of CPU, that's about 10× the cores. Better still: Java 21 **virtual threads** or async I/O make blocking cheap. Always bound pools and queues.
**In the interview:** "virtual threads for I/O-heavy Spring services."

### Async I/O and non-blocking — event loop (Node.js, Netty, asyncio): single thread handles thousands of I/O connections
Instead of one blocked thread per connection, an **event loop** multiplexes thousands of sockets (epoll/kqueue) and runs callbacks when I/O is ready. That gives high concurrency with low memory (Node.js, Netty, Spring WebFlux, Vert.x, Python asyncio). CPU-heavy work must be offloaded, or it blocks the loop. Java virtual threads offer similar scalability with simpler blocking-style code.
**In the interview:** WebSocket gateways and API gateways are usually built on Netty-style event loops.

### N+1 query — detect via slow query log or ORM verbose mode; fix with JOIN, eager loading, or DataLoader
Symptom: a page issues hundreds of small, nearly identical queries (one per item). Detect it via SQL logging (`spring.jpa.show-sql`, Hibernate statistics), APM traces showing repeated queries, or tests that assert query counts. Fix it with JOINs or `JOIN FETCH`, entity graphs, batch fetching (`@BatchSize`), `IN (...)` queries, or DataLoader in GraphQL.
**In the interview:** a classic Java/Hibernate performance question.

### Batch APIs — reduce round trips: fetch 100 items in one request vs 100 individual requests (10× improvement)
Every request pays network RTT and per-request overhead. Batch endpoints (`GET /users?ids=1,2,3`, `POST /events:batchCreate`), multi-get in caches (Redis MGET or pipelining), batched DB writes (JDBC batch inserts) and batched Kafka production give large gains. Limit batch sizes and handle partial failures.
**In the interview:** "multi-get from the cache instead of N round trips."

### Compression — Snappy (fastest, moderate ratio), LZ4 (balanced), gzip (best ratio, slower), Zstandard (best of both)
Trade CPU for fewer bytes. **Snappy and LZ4**: very fast with moderate ratios, the defaults for Kafka, Cassandra and RocksDB blocks. **gzip/deflate**: good ratios, slower, universal on HTTP. **Brotli**: the best ratio for static web assets. **Zstandard**: an excellent ratio with fast speed and tunable levels, the modern favourite for Kafka, data lakes and backups.
**In the interview:** "zstd on Kafka topics cut network and storage by about 4×."

### Efficient serialization — Protocol Buffers 3–10× smaller than JSON; Avro for Kafka schemas; MessagePack for binary JSON
Text JSON is verbose and slow to parse. **Protobuf**: compact binary, typed schemas, fast, the gRPC default. **Avro**: schema-based binary, great with a Schema Registry for Kafka, and schema evolution is built in. **MessagePack/CBOR**: binary JSON-like with no schema. Low-latency trading uses SBE or FlatBuffers (zero-copy).
**In the interview:** "protobuf between services, Avro on Kafka, JSON only at the public edge."

### GC tuning (JVM) — G1GC for balanced latency; ZGC for sub-ms GC pauses; tune heap: not too small (frequent GC), not too large (long GC)
**G1** (the default) balances throughput and pause times (target ~200 ms). **ZGC** and **Shenandoah** do concurrent compaction with pauses under a millisecond, even on large heaps, which suits latency-sensitive services. A heap that's too small means frequent GC, and too large can mean long full GCs (less of a problem with ZGC). Reduce allocation rates (object reuse, fewer temporary objects), monitor GC logs, and set container memory limits correctly.
**In the interview:** "ZGC for the latency-critical service, plus reducing allocation."

### Database connection exhaustion — symptom: timeout waiting for connection; fix: pool size + circuit breaker upstream
Symptoms: "Connection is not available, request timed out after 30000ms" (HikariCP), or "too many connections" at the DB. Causes: slow queries holding connections, leaked connections, too many app instances × pool size, long transactions, or a traffic spike. Fixes: tune queries, set timeouts (pool, statement), use PgBouncer or RDS Proxy, limit concurrency upstream (bulkheads, circuit breakers), and add leak detection.
**In the interview:** a frequent real incident type, good for behavioural stories too.

## Cost optimization & efficiency

### Right-sizing compute — use CloudWatch metrics to identify over-provisioned instances
Most fleets are over-provisioned. Analyse CPU and memory utilisation over weeks (CloudWatch, Compute Optimizer, Kubernetes VPA recommendations) and downsize or change instance families (Graviton/ARM is often 20–40% cheaper for the performance). Set Kubernetes requests from real usage so nodes pack efficiently.
**In the interview:** a quick cost-awareness point.

### Spot / preemptible instances — 70–90% savings; design stateless workers that handle 2-min shutdown notice
Use spare capacity at a deep discount for interruptible work: batch jobs, CI, stateless workers, part of a web fleet (mixed with on-demand). Handle the termination notice (drain, checkpoint, requeue), diversify instance types and AZs, and never put stateful primaries on spot.
**In the interview:** "Spark jobs and queue workers on spot."

### Reserved instances vs savings plans — 1–3 year commitment for 30–60% discount on baseline capacity
Commit to steady baseline usage for 1–3 years in exchange for large discounts. **Reserved instances** are tied to instance attributes (or convertible). **Savings plans** commit to a dollar-per-hour spend and are flexible across instance types, regions and Fargate/Lambda (compute plans). Cover the predictable baseline with commitments, the variable part with on-demand, and interruptible work with spot.
**In the interview:** "a commitment for the baseline, autoscaling on-demand for peaks."

### S3 storage tiering — Standard → Standard-IA → Glacier Instant → Glacier Flexible → Deep Archive
Storage classes trade price against retrieval cost and latency. **Standard**: hot. **Standard-IA / One Zone-IA**: infrequent access, with a retrieval fee. **Glacier Instant Retrieval**: archival with millisecond access. **Glacier Flexible**: minutes to hours. **Deep Archive**: about 12 hours, cheapest (regulatory archives). **Intelligent-Tiering** moves objects automatically based on access.
**In the interview:** "old statements and audit logs move to Glacier after 1 year (7–10 year retention)."

### Lifecycle policies — auto-transition objects to cheaper tier after 30/90/365 days
Rules on buckets or prefixes automatically transition objects (e.g. to IA after 30 days, to Glacier after 180) and expire them (delete temporary uploads after 7 days, old log versions after 90). Also clean up incomplete multipart uploads. It's set-and-forget cost control, and the same idea exists for Elasticsearch (ILM) and Kafka (tiered storage).
**In the interview:** one line in any design with large blob storage.

### Data transfer costs — same-AZ is free; cross-AZ costs $0.01/GB; cross-region higher; CDN reduces egress
Network transfer is a hidden cost. Internet egress is the most expensive (CDNs and compression reduce it), cross-region replication costs per GB, and cross-AZ traffic (chatty microservices, Kafka replication, multi-AZ databases) adds up surprisingly fast. Mitigations: AZ-aware routing, compression, VPC endpoints instead of NAT gateways for S3, and caching.
**In the interview:** an advanced cost point that impresses senior interviewers.

### Caching ROI — every cache hit saves a DB query; measure cache hit rate, aim for >95% for hot paths
Caches pay off when hit rates are high and the alternative is expensive (DB load, latency, third-party API fees). Measure the hit rate, latency saved and DB load avoided against cache cluster cost. A 95% hit rate means the DB sees 20× less read load, which can mean far fewer or smaller DB instances and replicas.
**In the interview:** quantify: "95% hit rate takes DB reads from 50K/s to 2.5K/s."

### Compression reduces bandwidth and storage — 3–10× reduction for JSON/text data
Compress HTTP responses (gzip/Brotli), Kafka batches (zstd/LZ4), stored logs and data-lake files (Parquet + zstd/snappy), and backups. Text and JSON typically shrink 3–10×, which cuts egress fees, storage cost and transfer time at modest CPU cost. Don't recompress already-compressed media (JPEG, MP4).
**In the interview:** an easy efficiency win to mention.

### Auto-scaling to zero — Lambda, Cloud Run, ECS Fargate: no cost when no traffic (ideal for batch workloads)
Pay nothing when idle: serverless functions, Cloud Run or Knative services, KEDA-scaled workers that go to zero replicas when queues are empty, and dev or test environments shut down at night. The trade-off is cold-start latency on the first request. Great for internal tools, scheduled jobs and spiky event processing.
**In the interview:** good for non-production environments and infrequent workloads.

### Database read replicas cost tradeoff — cheaper than sharding; only add when primary is read-saturated
Replicas are the simplest way to scale reads: no application rewrite beyond read/write routing, but each one is a full-cost instance with its own storage. Before adding them, try query and index optimisation and caching, which are usually much cheaper. Add replicas when the primary is read-saturated, and shard only when **writes** or data size exceed one primary.
**In the interview:** "optimise → cache → replicas → shard", in that order of cost and complexity.
