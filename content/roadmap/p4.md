## Caching strategies

### Cache-aside (lazy loading) — app checks cache, fetches DB on miss, populates cache
The application owns the logic: `GET` from the cache, and on a miss read the DB, `SET` into the cache with a TTL, and return. On writes, update the DB and then **delete** the cache key (don't overwrite it, which avoids races between concurrent writers). Only data that's actually requested gets cached, and if the cache goes down the app still works, just slower.
**In the interview:** your default caching pattern. Say "cache-aside with TTL plus delete-on-write".

### Read-through — cache layer fetches from DB on miss transparently to application
Like cache-aside, but the **cache library or provider** loads from the DB on a miss, so application code just calls `cache.get(key)`. Examples: a Caffeine `LoadingCache` with a loader function, DynamoDB DAX, NCache. Cleaner code, same consistency trade-offs.
**In the interview:** mention it as a variant. Behaviour is the same as cache-aside.

### Write-through — write to cache and DB synchronously; reads always hit cache
Every write updates the cache and the DB in the same request path. The cache is always fresh for written keys, so reads hit. Writes get slower (two writes), you cache data that might never be read, and a failure between the two writes can still leave them inconsistent.
**In the interview:** good for read-after-write-heavy data like user settings. Pair it with a TTL.

### Write-behind (write-back) — write to cache only, async flush to DB later; risk of data loss
Writes go only to the cache, and a background process **batches** them into the DB later. Write latency is very low and bursts are absorbed (view counts, likes, game state). If the cache node dies before flushing, those writes are **lost**, and the DB lags behind.
**In the interview:** fine for counters and analytics. Never for payments or orders.

### Refresh-ahead — cache proactively refreshes keys before they expire based on access patterns
Hot keys get reloaded in the background **before** their TTL expires (e.g. once 80% of the TTL has passed and the key is still being accessed), so users never hit a miss on popular data. Caffeine's `refreshAfterWrite` does this. It wastes some work refreshing keys that would have gone cold anyway.
**In the interview:** combine it with "stale-while-revalidate" for hot keys to avoid stampedes.

### Negative caching — cache "not found" result with short TTL to prevent DB hammering on missing keys
When the DB says a key doesn't exist, cache that fact (a sentinel such as `NULL`) for a short TTL (30–60 s). Repeated lookups for missing users or URLs then stop hitting the DB. The TTL must be short, so a newly created item becomes visible quickly, or delete the negative entry on create.
**In the interview:** the first defence against **cache penetration**.

### Cache warming / pre-warming — populate cache before traffic spike (cold start problem)
A freshly deployed or restarted cache is empty, so the first wave of traffic all misses and floods the DB. Warm it by preloading known hot keys (top products, today's sale items, popular configs) from logs or analytics, and gradually shift traffic to new cache nodes.
**In the interview:** important before flash sales and launches, and after cache failovers.

### Cache busting — append content hash to URLs to force new cache entries on deploy
Browsers and CDNs cache by URL. Put a content hash or version in the filename or query (`app.9f3c1.js`, `?v=42`) so each new deploy produces new URLs, which are fetched fresh. Old versions simply age out, with no purge needed. Build tools (Vite, webpack, Next.js) do this automatically.
**In the interview:** "hashed asset names with long TTLs, short TTL on the HTML" is the standard answer.

## Eviction policies & expiry

### LRU — Least Recently Used: evict the least recently accessed item (most common default)
When the cache is full, evict the item that hasn't been accessed for the longest time. Recency is a good predictor for most workloads. It's implemented with a hash map plus a doubly linked list for O(1) operations, and Redis uses an *approximated* LRU (it samples keys). Its weakness: a one-off big scan evicts genuinely hot items.
**In the interview:** implementing an LRU cache is a classic LLD/DSA question (LeetCode 146).

### LFU — Least Frequently Used: evict item with fewest accesses in time window
Evict the item accessed the fewest times, usually with frequency counters that decay over time so yesterday's hits don't count forever. It keeps long-term popular items and resists scans. Pure LFU adapts slowly when popularity shifts. Redis has `allkeys-lfu`, and Caffeine's W-TinyLFU combines frequency and recency very effectively.
**In the interview:** "LFU for stable popularity, such as a product catalogue; LRU for recency-driven data, such as sessions."

### MRU — Most Recently Used: evict most recently accessed (good for sequential scans)
Evict the item used most recently. That sounds backwards, but it's right for **cyclic or sequential access**: when you scan a large file repeatedly, the item just read won't be needed again for the longest time. Databases use variants of it for full-table-scan buffers.
**In the interview:** niche. Know that it exists, and why.

### ARC — Adaptive Replacement Cache: dynamically balances LRU and LFU based on workload
ARC keeps two lists, items seen once (recency) and items seen at least twice (frequency), plus "ghost" lists of recently evicted keys. It adapts the split between the two based on which ghost list gets hits. It's self-tuning and scan-resistant. Used in ZFS and some databases.
**In the interview:** niche. "Adaptive between recency and frequency" is enough.

### TTL (Time To Live) — key expires after fixed duration, lazy deletion on access
Each key gets an expiry (`SET k v EX 300`). Expired keys are treated as missing. In Redis they're deleted **lazily** when accessed, plus by active sampling. The TTL bounds staleness even if invalidation fails. Choose it based on how stale the data may safely get.
**In the interview:** always put a TTL on cache entries. It's your safety net.

### Active expiry — background thread scans for expired keys (Redis probabilistic scan)
Lazy expiry alone would leave never-accessed expired keys using memory. Redis runs an active cycle about 10 times a second: it samples 20 keys that have TTLs, deletes the expired ones, and repeats if more than 25% were expired. That keeps memory in check without scanning every key.
**In the interview:** detail-level. Mention it to show you know Redis internals.

### Redis maxmemory-policy — allkeys-lru, volatile-lru, allkeys-random, noeviction
This decides what Redis does at the memory limit. **allkeys-lru / allkeys-lfu**: evict any key (best for pure caches). **volatile-lru / volatile-lfu / volatile-ttl**: only evict keys that have a TTL (mixed cache + persistent data). **allkeys-random / volatile-random**. **noeviction**: return errors on writes (for queues or data you can't lose).
**In the interview:** "allkeys-lru (or lfu) for the cache cluster."

### Staggered TTLs — add small random jitter to TTL to prevent cache avalanche
If thousands of keys are cached at the same moment with the same TTL (after a deploy or warm-up), they all expire together and hit the DB at once. Add random jitter, e.g. `TTL = 3600 + random(0, 300)` seconds, so expirations spread out.
**In the interview:** a one-line fix that interviewers like.

## Cache failure modes & solutions

### Cache stampede / thundering herd — mass cache miss triggers simultaneous DB requests
A hot key expires (or the cache restarts), and thousands of concurrent requests all miss at once, all query the DB for the same thing, and the DB collapses. It's dangerous for expensive queries on popular keys (the homepage, flash-sale products).
**In the interview:** expect it as the follow-up to "we added a cache". Know three fixes: locking, early refresh, stale-while-revalidate.

### Mutex lock to prevent stampede — only one request fetches, others wait and read populated cache
On a miss, try to take a short lock (`SET lock:key 1 NX EX 5`). The winner loads from the DB and fills the cache. Losers wait briefly and retry the cache, or serve a stale value. In-process, use a single-flight or `computeIfAbsent`-style loader. The lock needs an expiry so a crashed holder doesn't block everyone.
**In the interview:** the most common stampede fix to describe.

### Probabilistic early re-expiration (PER) — randomly refresh before TTL expires to prevent stampede
As a key approaches expiry, each read refreshes it early with a probability that rises as expiry gets closer (the "XFetch" algorithm weights this by how expensive the recompute is). Usually exactly one request refreshes early, and the key never actually expires under load. There's no lock to manage.
**In the interview:** an elegant alternative to locks. Naming it shows depth.

### Hot key problem — single key overwhelms one Redis node (e.g., celebrity tweet)
In Redis Cluster, a key lives on one shard. A viral tweet or a flash-sale SKU read 500K times a second can saturate that node's CPU or network while the other nodes sit idle, and adding nodes doesn't help because the key can't split.
**In the interview:** detect hot keys (`redis-cli --hotkeys`, client-side metrics), then apply the fixes below.

### Hot key solution — local in-process L1 cache (Caffeine/Guava) + L2 Redis; key replication to N slots
1) An **L1 in-process cache** on each app server with a short TTL (1–5 s) absorbs most reads before they reach Redis. 2) **Replicate the key**: store copies as `key#0 … key#9` across slots and read a random copy (writes update all of them). 3) Read from Redis replicas. 4) Precompute and push the content to a CDN.
**In the interview:** "L1 local cache plus key replication" is the classic answer.

### Cache penetration — query for non-existent key repeatedly bypasses cache and hammers DB
Requests for keys that don't exist (random IDs, a bot or an attack) always miss the cache, because there's nothing to cache, so every one hits the DB. Fixes: **negative caching**, a **bloom filter** of valid keys, input validation (reject malformed IDs), and rate limiting.
**In the interview:** distinguish it from stampede (an existing key expiring) and avalanche (many keys expiring at once).

### Bloom filter for cache penetration — reject requests for keys known not to exist
Keep a bloom filter of every valid ID (e.g. RedisBloom, or in memory). On a request, if the filter says "definitely not present", return 404 immediately without touching the cache or DB. False positives only let a few bad requests through. Add new IDs on creation. Deletions need a counting filter or periodic rebuilds.
**In the interview:** a neat use of probabilistic data structures in caching.

### Cache avalanche — mass TTL expiry at the same time causes thundering herd on DB
Many keys expire simultaneously, or the whole cache cluster goes down, and the full read load lands on the DB. It's the stampede problem at system scale. Fixes: TTL jitter, a highly available cache (replicas, cluster), warm-up after restarts, and protecting the DB with rate limits or circuit breakers.
**In the interview:** "the DB must survive a cold cache, or the cache must never be cold."

### Staggered TTL + circuit breaker to handle cache avalanche
Prevention: randomise TTLs so expirations spread out. Protection: put a **circuit breaker or concurrency limit** on DB calls from the cache-miss path, so when misses spike you serve stale data, defaults or 503s for non-critical requests instead of letting the DB fall over. Then recover gradually while the cache refills.
**In the interview:** prevention plus protection is a strong two-part answer.

### Cache consistency — dual write problem: cache + DB atomicity impossible without distributed transaction
Updating the DB and the cache are two separate operations, and a crash or race between them leaves the cache stale. Classic race: A reads the old value (miss) → B updates the DB and deletes the key → A writes the old value into the cache. Mitigations: delete instead of update, TTLs as a backstop, **delayed double delete**, versioned values, or CDC-driven invalidation.
**In the interview:** acknowledge that perfect consistency is impractical and bound staleness with TTLs.

### Event-driven cache invalidation — use CDC (Debezium → Kafka) to invalidate on DB change
Debezium tails the DB's WAL or binlog and publishes every row change to Kafka. An invalidation consumer deletes or updates the matching cache keys. Every change is caught, including ones made by other services or manual fixes, in commit order, with no dual writes in application code.
**In the interview:** the most robust invalidation design for larger systems.

## Caching layers & tools

### Client-side cache — browser cache, service worker, localStorage (for static assets)
The fastest cache sits on the user's device. The HTTP cache is controlled by Cache-Control and ETag. **Service workers** enable offline use and custom caching strategies (PWA). **localStorage/IndexedDB** keep app data. Mobile apps cache in local SQLite. You can't purge it remotely, so version your URLs.
**In the interview:** mention it for static assets and offline-capable apps.

### In-process cache — Caffeine (JVM), Guava Cache, Node.js Map/LRU cache
Data lives in the application's own memory: nanosecond access with no network hop. **Caffeine** is the modern Java choice (W-TinyLFU eviction, async loading, refresh). Downsides: each instance has its own copy (inconsistency between servers), memory is limited by the heap (adds GC pressure), and the cache is lost on restart.
**In the interview:** good for small, hot, rarely changing data (config, feature flags, reference data) and as an L1 cache.

### Distributed cache — Redis, Memcached, Apache Ignite
A shared cache cluster that all app instances use, at roughly 0.2–1 ms per network call. It's consistent across servers, survives app restarts and scales independently. **Redis** is the default; **Memcached** is a simple multi-threaded key-value cache; **Ignite/Hazelcast** are in-memory data grids with compute and SQL.
**In the interview:** "Redis Cluster with replicas" is the standard choice.

### Memcached vs Redis — Memcached: multi-threaded, pure cache; Redis: rich data types, persistence, Lua
**Memcached**: strings only, multi-threaded (scales up on big machines), no persistence or replication, LRU, very simple. **Redis**: rich data structures, persistence (RDB/AOF), replication, Sentinel and Cluster, pub/sub, streams, Lua scripting and transactions. Its core is mostly single-threaded, with threaded I/O in newer versions.
**In the interview:** "Redis unless we need nothing but a simple, massive key-value cache."

### Two-level cache architecture — L1 in-process (nanoseconds) + L2 Redis (microseconds)
Check the local L1 first (tiny, short TTL), then Redis L2, then the DB. L1 absorbs hot keys and saves network trips, and L2 is shared and larger. Invalidation is harder: broadcast deletes to every L1 via Redis pub/sub, or keep L1 TTLs very short (seconds).
**In the interview:** the answer for hot keys and ultra-low-latency reads.

### CDN edge cache — CloudFront, Fastly, Cloudflare cache static and semi-static content
CDN PoPs cache responses close to users. That suits static assets, images and video segments, and also semi-static API responses (product listings, public profiles) with short TTLs and `stale-while-revalidate`. Use surrogate keys or tags for targeted purges.
**In the interview:** for read-heavy public content, the CDN is the most effective cache layer.

### Reverse proxy cache — Nginx proxy_cache, Varnish Cache for HTTP response caching
A cache sitting in front of your app servers stores full HTTP responses according to cache headers. **Varnish** is a dedicated HTTP accelerator with a configurable policy language (VCL), and **Nginx proxy_cache** is built in. It shields the app from repeated identical requests, and is useful when a CDN isn't an option (internal apps) or as an extra layer.
**In the interview:** one line in the request path: "Nginx can also cache hot responses."

### Database query result cache — application-level, careful with invalidation
Cache the results of expensive queries (aggregations, reports) keyed by query and parameters. MySQL's built-in query cache was removed in 8.0 because invalidating on every table write killed concurrency, so do it at the application layer with explicit TTLs or event-based invalidation. Materialised views are another option.
**In the interview:** good for dashboards and leaderboards that tolerate staleness.

### Redis Cluster for horizontal cache scaling — 16384 hash slots, add nodes to expand
When one Redis node isn't enough (memory or throughput), Redis Cluster spreads the 16,384 slots across several primaries, each with replicas for failover. Add nodes and migrate slots online to grow. Clients must be cluster-aware, and multi-key operations need keys in the same slot (hash tags).
**In the interview:** "Redis Cluster, 6 shards × 1 replica" is a concrete-sounding answer.

### Cache sizing estimation — working set size (hottest 20% of data), benchmark hit rate target >95%
Don't cache everything, cache the **working set**. Popularity is usually skewed (80/20 or Zipf), so a cache holding the hottest ~20% gets most of the hits. Example: 100M items × 1 KB = 100 GB total, so cache about 20 GB, and add headroom for overhead and replicas. Measure the hit rate and aim for over 90–95% on hot paths.
**In the interview:** show the arithmetic. It's a nice estimation moment.

### Cache eviction monitoring — track eviction rate; high eviction means cache is too small
Watch the **hit rate**, **evictions per second**, memory use, latency and key count. A high eviction rate with a falling hit rate means the cache is too small for the working set (or TTLs are too long and fill it with cold data). A sudden drop in hit rate means something wrong with keys or invalidation, like a deploy that changed the key format.
**In the interview:** part of the observability story for any cache.
