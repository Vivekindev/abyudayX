## Probabilistic & approximate structures

### Bloom filter — space-efficient probabilistic set: no false negatives, tunable false positive rate
A bit array of m bits plus k hash functions. **Add**: set the k bits at `h1(x)…hk(x)`. **Query**: if any of those bits is 0, the item is **definitely absent**; if all are 1, it's **probably present**. You get no false negatives and a tunable false-positive rate, in roughly 10 bits per item for 1% FP, whatever the item size. Plain bloom filters don't support deletion.
**In the interview:** "a bloom filter in front of the expensive lookup to skip guaranteed misses."

### Bloom filter FP rate — (1 − e^(−kn/m))^k where k=hash functions, n=items, m=bits
For n items in m bits with k hashes, the false-positive probability ≈ (1 − e^(−kn/m))^k. The optimal k = (m/n)·ln 2. Rules of thumb: about 9.6 bits per item gives 1% FP (k ≈ 7), and 14.4 bits per item gives 0.1%. Example: 1 billion URLs at 1% FP ≈ 1.2 GB.
**In the interview:** being able to size one ("about 10 bits per item for 1%") impresses.

### Bloom filter use cases — Cassandra SSTable key lookup, Redis key existence, DB query cache penetration
**Databases/LSM trees** (Cassandra, RocksDB, HBase): skip SSTables that can't contain the key. **Cache penetration defence**: reject IDs that don't exist before hitting the DB. **Web crawlers**: "have I seen this URL?" **Username availability** pre-checks, malicious URL lists in browsers, avoiding recommending already-seen items.
**In the interview:** name two uses, including the LSM read path.

### Counting Bloom filter — allows deletions by using counters instead of bits
Replace each bit with a small counter (e.g. 4 bits). Add increments the k counters, remove decrements them, and a query checks that all are greater than zero. This supports deletions at the cost of 3–4× the memory, and counters can overflow. Useful when set membership changes (e.g. caches tracking currently cached keys).
**In the interview:** "use a counting bloom filter, or a cuckoo filter, if we need deletes."

### Cuckoo filter — more space-efficient than Bloom for same FP rate, supports deletions, better cache locality
Stores short **fingerprints** in a cuckoo hash table, where each item has two possible buckets and existing entries get evicted and relocated on collision. It supports deletion, is more space-efficient than Bloom at low FP rates (under ~3%), and needs fewer memory accesses per lookup. Inserts can fail as the table fills up. RedisBloom offers both.
**In the interview:** niche. Mention it as the deletion-capable alternative.

### HyperLogLog — cardinality estimation: count distinct values with ~1.5% error using O(m) space
Hash each item and use the first bits to pick one of m registers. Each register stores the **maximum number of leading zeros** seen; long zero runs are rare, so they indicate many distinct items. A harmonic mean across registers gives the estimate. It counts **billions of uniques in kilobytes** with about 1–2% error, and sketches are **mergeable** (union across days or servers).
**In the interview:** "unique visitors per page in Redis HLL instead of storing every user ID."

### HyperLogLog in Redis — PFADD (add), PFCOUNT (estimate), PFMERGE (combine); used for daily active users
`PFADD dau:2026-11-09 user42` adds an element, `PFCOUNT dau:2026-11-09` returns the estimated distinct count (~0.81% standard error), and `PFMERGE wau dau:mon … dau:sun` combines sketches for weekly uniques. Each key uses at most ~12 KB however many users there are. You can't list members or remove items.
**In the interview:** quote the 12 KB figure and the mergeability.

### Count-Min Sketch — frequency estimation in data streams: O(ε,δ) space, approximate top-K
A d × w grid of counters with d hash functions. To increment x, add 1 to one counter per row. To estimate x, take the **minimum** of its d counters. Collisions only ever **over-count**, never under-count. The width controls error (ε) and the depth controls confidence (δ). Combined with a min-heap, it tracks **heavy hitters / top-K** in fixed memory.
**In the interview:** "trending hashtags: count-min sketch plus heap per time window."

### MinHash — estimate Jaccard similarity between sets; used for near-duplicate detection
Jaccard similarity = |A∩B| / |A∪B|. MinHash applies k hash functions and keeps the **minimum** hash value of each set's elements per function. The fraction of matching minimums between two signatures estimates their Jaccard similarity. Documents become small fixed-size signatures (e.g. of word shingles) that are cheap to compare. Used for near-duplicate pages, plagiarism detection and clustering.
**In the interview:** use in a web crawler for detecting near-duplicate content (alongside SimHash).

### Locality-Sensitive Hashing (LSH) — hash similar items to same bucket; approximate nearest neighbor
Hash functions designed so that **similar items collide** with high probability. Banding MinHash signatures, or random hyperplanes for cosine similarity, puts candidates in the same buckets, so you only compare items within a bucket instead of every pair: sublinear approximate nearest-neighbour search. Used for dedup, recommendations and early vector search (now mostly HNSW).
**In the interview:** "LSH turns an O(n²) all-pairs comparison into bucket lookups."

## Hashing & distribution

### Consistent hashing — arrange nodes on ring; key maps to next clockwise node; only K/N keys remap on node change
Hash nodes and keys onto the same ring (0…2³²−1). A key belongs to the first node clockwise from its position. Adding a node only steals the keys in one arc, and removing a node hands its keys to its successor, so only about **K/N keys move** instead of nearly all of them with `hash % N`. Used by Cassandra, DynamoDB, Riak, Memcached clients and CDNs.
**In the interview:** explain it with a quick drawing of the ring and one node joining.

### Virtual nodes (vnodes) — each physical node owns N virtual positions on ring; better load balance
With one point per node, arcs are uneven and a failed node's load lands entirely on one neighbour. Giving each physical node many virtual points (e.g. 100–256) evens out the arc sizes statistically, spreads a failed node's load across many peers, and lets bigger machines take more vnodes (weighting).
**In the interview:** always mention vnodes right after consistent hashing.

### Consistent hashing math — with V vnodes per node, variance of load = O(1/V); common: V=150
With one position per node, load imbalance can be large (the biggest arc may be several times the average). With V virtual nodes per server, the relative standard deviation of load shrinks roughly as 1/√V, so the variance drops as O(1/V). Around 100–200 vnodes keeps every node within a few percent of average. Cassandra historically used 256 tokens per node, and newer versions default lower with smarter allocation.
**In the interview:** "~150 vnodes per node keeps load within a few percent."

### Rendezvous hashing (HRW) — score = hash(key + node), assign to highest score; O(1) per lookup
For each key, compute `score = hash(key, node)` for every node and pick the **highest** (Highest Random Weight). If a node leaves, only its keys move, each to its next-highest node, with no ring and no vnodes. Each lookup is O(N) over the node count, cheap for small clusters, and it extends naturally to "top-k nodes" for replication. Used in some CDNs and in Kafka-related tooling.
**In the interview:** a nice alternative to mention, simpler than a ring.

### Jump consistent hash — O(1) space, deterministic, minimal disruption; used in Guava
Google's algorithm maps a key to one of N buckets with a tiny loop of arithmetic (O(log N) time, O(1) memory), and when N grows to N+1 only 1/(N+1) of keys move. The limitation is that buckets must be numbered 0…N−1: you can only add or remove at the end, not take out an arbitrary node. Guava has `Hashing.consistentHash`.
**In the interview:** good for sharding data across numbered shards, not for arbitrary node failures.

### Geohash — encode (lat, lng) to base32 string; proximity = shared prefix; grid cells of varying size
Interleave bits of longitude and latitude by repeatedly bisecting the world, then encode as base32: `tdr1y…` is Bangalore. Each extra character means a smaller cell (6 chars ≈ 1.2 km × 0.6 km). Nearby points usually **share prefixes**, so proximity search becomes a string prefix lookup on any index or KV store.
**In the interview:** "geohash6 as an indexed column; query the cell plus its neighbours."

### Geohash edge cases — cells near the poles, cells on the prime meridian; requires neighbor search
Two points metres apart can sit across a cell boundary with completely different prefixes (especially at the equator and prime meridian, where the top-level split happens). So you must search the target cell **plus its 8 neighbours**. Cells also become distorted (narrower) toward the poles. After fetching candidates, compute exact distances.
**In the interview:** say "plus 8 neighbours" or the interviewer will ask.

### Quadtree — recursively subdivide 2D space into 4 quadrants; density-adaptive; used in Uber, Twitter
Start with the world, and split any cell holding more than N points into 4 children, recursively. Dense cities get deep, fine cells and empty oceans stay coarse, so it **adapts to density**. To find nearby points, descend to the user's leaf and expand to neighbouring leaves until you have enough results. It's usually kept in memory, and suits mostly static points (restaurants).
**In the interview:** "a quadtree for Yelp-style static places; geohash/H3 in Redis for moving drivers."

### R-tree — spatial index for rectangles and polygons; used in PostGIS, MySQL Spatial, SQLite R*Tree
A balanced tree where each node holds bounding rectangles that contain its children, like a B-tree for 2D shapes. It answers "which shapes intersect this area?" and nearest-neighbour queries efficiently, and it's the standard spatial index in databases (PostGIS GiST, MySQL spatial, SQLite R*Tree). It handles polygons (delivery zones, geofences), not just points.
**In the interview:** "PostGIS with a GiST (R-tree) index for delivery-zone polygons."

### Google S2 — spherical geometry using Hilbert curve; uniform cell sizes at each level; used by Uber, Foursquare
S2 projects the Earth onto the 6 faces of a cube and subdivides each face hierarchically (30 levels), ordering cells along a **Hilbert curve** so nearby cells usually have nearby 64-bit IDs. Cells have roughly uniform area at each level and no pole distortion. "Region coverers" turn any circle or polygon into a set of cell ranges for fast index queries. Used by Google Maps, Foursquare and MongoDB's 2dsphere index.
**In the interview:** "S2 cell IDs as indexed integers; cover the search circle with cells."

### Uber H3 — hexagonal hierarchical grid; constant area per cell; better for analytics than quadtree
H3 tiles the globe with **hexagons** at 16 resolutions. Every neighbour is the same distance away (unlike squares, which have diagonal neighbours), so k-ring neighbourhoods, smoothing and movement models are simple. It's ideal for aggregating supply and demand, **surge pricing zones**, heatmaps and ETA features. Cells are 64-bit IDs with parent/child relationships.
**In the interview:** the strong answer for ride-sharing location analytics.

## Indexing & lookup structures

### B+ tree — all data in leaf nodes linked in sorted order; O(log N) search + efficient range scans; used in all RDBMS
Internal nodes hold only routing keys (so the fan-out is high, hundreds per page), and all values or row pointers live in the leaves, which are **linked** for sequential range scans. Height stays around 3–4 levels for billions of rows, and splits and merges keep it balanced. It's the backbone of relational indexes and many file systems.
**In the interview:** explain why range queries and ORDER BY are cheap with it.

### LSM tree — MemTable → immutable SSTable → leveled compaction; write-optimized; used in Cassandra, RocksDB, LevelDB
Writes go to a WAL and an in-memory sorted **memtable**. When full, it's flushed as an immutable sorted **SSTable**. Background **compaction** merges SSTables into larger levels, dropping overwritten and deleted entries. Writes are sequential and fast. Reads may check several levels, and compaction causes write amplification. Used in Cassandra, RocksDB, LevelDB, HBase, ScyllaDB and InfluxDB.
**In the interview:** "LSM for write-heavy workloads like chat messages and metrics."

### LSM read path — check bloom filter (each level) → check SSTable index → read data block; amortized O(log^2 N)
A point read checks the memtable(s), then each level from newest to oldest: the SSTable's **bloom filter** (skip it if the key is definitely absent), then the sparse index or fence pointers to find the block, then the (possibly cached) block itself. It stops at the first match, because newer entries win. Bloom filters keep this to about one disk read. Range scans must merge iterators from every level.
**In the interview:** connects bloom filters, caching and compaction strategy.

### Skip list — probabilistic balanced structure; O(log N) average search/insert; used in Redis sorted sets
A sorted linked list with extra "express lanes": each node is promoted to the level above with probability ½, so searches skip ahead and descend, averaging O(log N). It's simpler than balanced trees and easy to make concurrent. Redis sorted sets use a skip list plus a hash table, and LevelDB/RocksDB memtables use skip lists.
**In the interview:** "why ZADD and ZRANK are O(log N) in Redis."

### Trie (prefix tree) — O(m) lookup by prefix where m = key length; used in autocomplete, IP routing
Each node represents a prefix and its children extend it by one character. Lookup and insert cost O(key length), independent of how many keys exist, and all keys with a given prefix sit in one subtree. Store the **top-K completions at each node** for instant autocomplete. Also used for IP longest-prefix-match routing and spell-checkers.
**In the interview:** the core of the typeahead design.

### Compressed trie (Patricia/Radix tree) — merge single-child nodes; O(m) space instead of O(m²)
A plain trie wastes nodes on long chains with no branching. A radix tree collapses each chain into a single edge labelled with the whole substring, so nodes ≈ number of keys and memory drops drastically while lookup stays O(m). Used in routers (IP tables), HTTP routers (path matching), Redis internals (streams, cluster slots) and Ethereum's Patricia Merkle trie.
**In the interview:** an optimisation to mention when sizing an in-memory trie.

### Inverted index — term → postings list (docID, frequency, position offsets); foundation of all search engines
Instead of document → words, store **word → list of documents** containing it (the postings), with term frequencies and positions for phrase queries and ranking. A query intersects or unions the postings lists of its terms, sorted by doc ID so they can be merged quickly. Lucene, Elasticsearch and Google are built on it.
**In the interview:** the first sentence of any search design.

### Term dictionary — sorted list of all terms; binary search or trie for lookup; stored in SSTable-like format
Maps each distinct term to its postings list location. Lucene stores it in immutable segment files, using an **FST** (finite-state transducer, a compressed trie-like automaton) as an in-memory index into the on-disk terms. That allows fast exact, prefix and fuzzy lookups with little memory. Terms are sorted, so range and prefix queries are efficient.
**In the interview:** niche. Explains how Elasticsearch looks up terms quickly.

### Merkle tree — hash tree: leaf = hash(data), parent = hash(children); detect inconsistencies between replicas
Hash each data block (a leaf), then hash pairs of hashes upward to a single root. Two parties compare roots: equal means everything matches. If they differ, recurse only into the subtrees whose hashes differ, which finds differences in O(log n) comparisons. It also proves that a block belongs to the set (Merkle proofs). Used in Git, blockchains, Cassandra/Dynamo repair, IPFS and certificate transparency.
**In the interview:** "compare replicas by exchanging hashes, not data."

### Merkle tree in Cassandra — compare replicas without transferring all data; send tree hashes instead
During `nodetool repair`, each replica builds a Merkle tree over a token range (leaves = hashes of row ranges) and replicas exchange trees. Only the leaf ranges with differing hashes get streamed between nodes. Terabytes are compared by sending kilobytes of hashes. Repair must run more often than `gc_grace_seconds` so deletes propagate.
**In the interview:** a concrete real-world use of Merkle trees.

### Segment tree — range query (sum, min, max) in O(log N) with O(N) space; used in real-time analytics
A binary tree over an array where each node stores an aggregate (sum, min, max) of its segment. Range queries and point updates both take O(log N), and lazy propagation supports range updates. It's more a DSA/competitive-programming structure, but the idea appears in time-series rollups and order-book price-level aggregation.
**In the interview:** rarely in system design. Know it for coding rounds.

### Fenwick tree (Binary Indexed Tree) — range sum in O(log N) with simpler implementation than segment tree
An array-based structure where index i stores a partial sum over a range defined by its lowest set bit. Prefix sums and point updates take O(log N) with a few lines of code and minimal memory. It's less flexible than a segment tree (it needs invertible operations like sum). Used for frequency counts, order statistics and cumulative metrics.
**In the interview:** coding-round material. A quick definition is enough here.

## Unique ID generation

### UUID v4 — 128-bit random; globally unique with 2^122 possibilities; not sortable, no ordering
122 random bits (the rest are version and variant bits). Collisions are practically impossible, and any node generates IDs with no coordination. Downsides: 16 bytes (36 characters as text), **no time ordering**, and random insertion points that fragment B-tree indexes (page splits, poor cache locality), especially for clustered primary keys.
**In the interview:** fine for opaque external IDs. Avoid it as a clustered primary key at scale.

### UUID v7 (new standard) — 48-bit Unix timestamp ms + 74-bit random; sortable, monotone within ms
Standardised in RFC 9562 (2024): a millisecond Unix timestamp prefix plus random bits (with optional counters for monotonicity within a millisecond). IDs are **time-ordered**, so inserts append to the end of B-tree indexes, while staying globally unique without coordination, in standard UUID format. Increasingly supported by databases and libraries.
**In the interview:** "UUIDv7 primary keys: sortable and coordination-free."

### ULID — 48-bit timestamp + 80-bit random; lexicographically sortable; URL-safe base32 encoding
Like UUIDv7 in spirit: 48 bits of millisecond timestamp plus 80 random bits, encoded as 26-character Crockford base32 (`01HF8…`), so string sort order equals time order. It's URL-safe and readable. It was popular before UUIDv7 was standardised.
**In the interview:** an alternative to UUIDv7. Mention either.

### Twitter Snowflake ID — 64-bit: 1 sign bit + 41 timestamp (ms, 69yr range) + 10 machine ID + 12 sequence (4096 IDs/ms)
A compact, roughly time-sortable 64-bit integer generated locally on each worker: the timestamp from a custom epoch in the high bits (so numeric order ≈ time order), then a worker ID (assigned via config or ZooKeeper), then a per-millisecond counter. Up to 4,096 IDs per millisecond per worker, about 4M per second. Used, with variants, by Twitter, Discord and Sony (Sonyflake).
**In the interview:** draw the bit layout. It's a common question.

### Snowflake clock skew problem — if system clock goes back, ID generation pauses or errors
IDs depend on the wall clock. If NTP moves the clock **backwards**, the generator could produce duplicates or out-of-order IDs. Mitigations: track the last timestamp and refuse or wait until the clock passes it again, alert on large jumps, use a monotonic clock offset from a fixed start time, and run NTP in slew mode (gradual adjustment).
**In the interview:** the expected follow-up after you describe Snowflake.

### Instagram shard ID — 41-bit epoch ms + 13-bit shard ID + 10-bit sequence; generated in PostgreSQL
Instagram generated IDs inside each Postgres shard with a PL/pgSQL function: 41 bits of milliseconds since a custom epoch, 13 bits of logical shard ID (8,192 shards), and 10 bits of a per-shard auto-increment sequence (1,024 IDs per millisecond per shard). IDs are time-sortable and **encode their shard**, so any ID can be routed directly to the right shard.
**In the interview:** "embed the shard ID in the ID" solves lookups by ID in sharded systems.

### NanoID — URL-safe alphabet, configurable length, cryptographically random, similar collision prob to UUID
A tiny library producing random string IDs from a URL-safe alphabet (A–Za–z0–9_-) with configurable length. The default 21 characters gives about 126 bits of randomness, similar to UUIDv4 but shorter. Good for public-facing IDs, short links and tokens. Not sortable.
**In the interview:** an option for short, unguessable public IDs.

### Ticket server (Flickr-style) — centralized DB auto-increment; simple but single point of failure
A dedicated database hands out IDs with auto-increment (Flickr used `REPLACE INTO` on a one-row table). For HA, run **two** servers with odd and even IDs (`auto_increment_increment=2`, offsets 1 and 2). It's simple, yielding compact numeric IDs, but it's a network hop per ID (mitigate by fetching ranges) and ordering across the two servers isn't strict.
**In the interview:** mention it as the simplest centralised option before Snowflake.

### Monotonic IDs — crucial for sort order in databases and for Kafka partition ordering; avoid UUID as PK
Increasing IDs make B-tree inserts append-only (fast, compact), give natural ordering for feeds and cursor pagination, and let consumers detect gaps or reordering. Random UUIDv4 primary keys scatter writes across the index. Prefer BIGINT identity columns, Snowflake or UUIDv7. Beware that strictly sequential IDs leak business volume and are guessable, so don't expose them as-is publicly.
**In the interview:** "time-ordered IDs for PKs, opaque tokens for public URLs."
